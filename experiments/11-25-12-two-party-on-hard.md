# 11/25/12 · 在第一条 0/3 任务上跑 2 人协议：两次都失败，但失败点不同

**日期**：2026-11-25（Asia/Shanghai）
**任务**：`tasks/moreitertools-1248`（单轮基线 0/3，见 11/25/11）
**脚本**：`scripts/run_protocol.py --task ... --rounds 2`

## 目的

第一次做**有意义的**协作实验：任务单轮 0/3，看 2 人协议能不能救回。

## 结果 A：上下文瘦身版（11/25/8 的改动仍在）

| 次 | 第 1 轮 | 第 2 轮 | 结论 | token |
|---|---|---|---|---|
| 1 | 复核 5 条 | 提案 0 份 | `rejected`：片段找不到 | 122516 |
| 2 | 复核 6 条 | 提案 0 份 | `rejected`：片段不唯一 | 66410 |
| 3 | 复核 8 条 | 提案 0 份 | `rejected`：片段找不到 | 65335 |

三次**全部败在"提案不合法"**，而不是测试红：

```
more_itertools/more.py: 找不到 SEARCH 片段（首行：'def __contains__(self, value):'）
more_itertools/more.py: SEARCH 片段出现在 2 处（'def __len__(self):'）
```

根因：第二轮抽掉了 `current_file`（11/25/8 为省 67% token 做的），
模型只能凭记忆写片段——在 5000 行的 `more.py` 上必然猜错。

## 结果 B：恢复全文（回滚 11/25/8 的瘦身）

| 次 | 第 1 轮 | 第 2 轮 | 结论 | token |
|---|---|---|---|---|
| 1 | 复核 8 条 | 提案 0 份 | `rejected`：片段找不到 | 172044 |
| 2 | 复核 6 条 | 提案 0 份 | `rejected`：片段找不到 | 172236 |
| 3 | 复核 6 条 | 提案 0 份 | `rejected`：片段找不到 | 174314 |

**仍然 0/3**，而且失败消息变得更有信息量：

```
找不到 SEARCH 片段（首行：'def __contains__(self, elem):'）   ← 原文是 value，不是 elem
找不到 SEARCH 片段（首行：'distance = stop - start'）
```

模型**有全文**，却把签名记成了 `(self, elem)`。这是"上下文稀释"：
 файл 5000 行塞进去，模型实际只扫了一部分，然后凭印象补全。

## 结论

1. **11/25/8 的 67% 成本优化是错的**——省的是 token，赔的是第二轮能不能编辑。
   已回滚：提案每轮都给完整文件；省 token 的余地留给复核提示。
2. **给全文也不保证抄对片段**。SEARCH/REPLACE 依赖逐字匹配，文件越长越不可靠。
3. **2 人协议在这条 0/3 任务上仍是无增益**，但要把原因说准：
   不是"协作思路不行"，是**提案格式在长文件上不可靠**，两轮都卡在提案合法性上，
   根本没走到"测试红不红"那一步。

两档都没有增益，但**原因不同**：中档是"给了机会也没把握住"，难档是"连提案都递不上去"。

> **更正（11/25/15 追加）**：本文档里"模型把签名猜错了（elem vs value）"这句是**错的**。
> `numeric_range.__contains__(self, elem)` 的 `elem` 是正确的——文件里同时存在
> `bucket.__contains__(self, value)`（第 1183 行）与 `numeric_range.__contains__(self, elem)`（第 2336 行）。
> 真实原因是**多行片段整体无法逐字匹配**，而我们的报错只说"找不到（首行：…）"，
> 把差异点掩盖了。已修：报错现在会指出第几行不一致。

## 下一步（方向已明确）

SEARCH/REPLACE 对长文件不友好，而**执行循环（后端 B）恰好有 grep/sed 可以取到逐字片段**。
所以下一步应该用后端 B 跑这条 0/3 任务，而不是继续调协议提示词——
让模型先 `grep` 到确切文本再编辑，比让它凭记忆写片段可靠得多。

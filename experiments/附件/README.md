## 一、字段口径

| 列 | 含义与取值 |
|---|---|
| 实验编号 / 组别 | 归属哪次实验、哪个对照组 |
| 任务ID / 日期 / run_id | 运行标识；`run_id` 内嵌的是**本地时间**（Asia/Shanghai） |
| 供应商 / 模型 / 协议 | 本次运行实际使用的组合 |
| **契约哈希** | 契约的 sha256 前 16 位。**2026-11-28 之前的运行未记录此字段**，一律标「缺失」；此后的运行会写入 `run_start` |
| 模型调用数 | 该次运行实际发生的模型调用次数（按 `model_response` 事件计数） |
| tests / lint / api / diff | 四类闸门各自的结论：`通过` / `未通过` / `未进入闸门` |
| 闸门结论 | `全绿` / `未通过` / `未进入闸门` |
| 最终状态 | `accepted` / `rejected` / `escalated` / `budget_exhausted` / `error` / `缺失` |
| 失败主因 | 按统一规则归类，规则见下 |
| token | 该次运行的 token 总量 |
| **审计位置** | 指向 `audit-摘录.jsonl` 的行号区间，可直接 `sed -n 'A,Bp'` 取出完整时间线 |
| 备注 | 1285 的替换关系等特殊情况 |

### 关键的三个"不假装"

1. **`未进入闸门` ≠ `未通过`**。提案不合法或调用失败的运行根本没有 `gate_report`，
   不能算成"测试没通过"。
2. **`缺失` 是真缺**。`contract_hash` 在 2026-11-28 之前没记录；不要事后补算冒充当时的值。
3. **调用错误也保留**。失败的运行同样是一行，不删除、不合并。

## 二、失败主因的归类规则

按优先级判定：

1. `run_end.reason` 含「提案不合法 / 输出不合法」→ **提案不合法**
2. 状态为 `error` 或含「模型调用失败」→ **调用错误**
3. 状态为 `budget_exhausted` → **预算耗尽**
4. 有 `gate_report` 且有两项及以上未通过 → 用「；」连接，如 `测试未通过；lint 新增问题`
5. 其余无法判定 → **待核实**

## 四、怎么按 run_id 查日志

```bash
# 1. 在 CSV 里找到目标 run_id 的「审计位置」，形如 audit-摘录.jsonl:L586-L589
# 2. 取出该区间
sed -n '586,589p' experiments/附件/audit-摘录.jsonl
```

典型时间线是四条事件：

```
run_start      → task_id / model / protocol / contract_hash
model_response → usage / latency / finish_reason
gate_report    → 四类闸门与 signature（tests:1|lint:1|api:1|diff:1）
run_end        → outcome / tokens / calls / duration_ms / reason
```

## 五、重新生成

```bash
python scripts/export_runs.py            # 默认读 runs/audit.jsonl，写本目录
```

脚本自带分组条数校验：期望 100/60/3/12/12/12，任何一组数量不符都会**拒绝写出文件**，
避免导出后才发现分组规则错了。

# 实验记录

> 一条硬规则：**成功和失败都要记。**
> 一次没跑通的尝试，信息量往往比一次跑通更大——它标出了边界在哪。

## 这里放什么

| 放这里 | 不放这里 |
|---|---|
| 实验目的、设置、结果、结论、局限 | 原始日志与逐条轨迹（在 `runs/`，**不入库**） |
| 复现命令 | 大段源码（给出文件路径与行号即可） |
| 失败原因，以及**当时是怎么误判的** | 只写"通过/未通过"而不写数字 |
| 关键数字的抄录 | 只引用 `runs/` 里的路径而不抄数字 |

最后一条尤其重要：`runs/` 被 gitignore，随时可能被清掉。
**结论里的每个数字，必须在本目录的文档里有一份副本。**

## 编号：月/日/次数/实验简称

| 部分 | 含义 | 例 |
|---|---|---|
| 月/日 | 实验执行日期 | `11/24` |
| 次数 | **当天第几次实验**，从 1 开始，只增不改 | `2` |
| 实验简称 | 两三个词，能一眼看出做了什么 | `两人协议修复` |

**文档内**写完整编号：`11/24/2`。
**文件名**把 `/` 换成 `-`（斜杠会变成目录层级）：

```
11-24-1-精确断言.md
11-24-2-两人协议修复.md
11-24-3-三人协议.md
11-25-1-真实仓库任务.md
```

作废的实验保留编号，在文末标注「已作废」并说明原因；编号不复用。

## 每份记录的必填字段

1. **编号与日期**（含时区）
2. **目的**：想验证什么，预期是什么
3. **设置**：模型、任务、预算、代码路径（哪个脚本）
4. **结果**：数字，不是形容词
5. **结论**：成立 / 不成立 / 无法判断
6. **局限**：样本量、天花板、提示词路径差异等
7. **复现**：一条能跑的命令

## 累计的方法论坑

1. **n=1 会骗人**：11/24/1 首轮得出"四组结果完全相关"，n=3 后不成立。
2. **单任务会饱和**：两个模型两条件都满分，条件差异被天花板吞掉。
3. **提示词路径不同就不可比**：11/24/2 与 11/24/3 的用户提示构造不同，token 不能直接对比。
4. **Windows 换行会伪造 diff**：写文件若经 Python 文本模式，`\n` 变 CRLF，整文件都算改动（11/25/1 出现过 6001 行假 diff）。
5. **推理模型会吃光输出预算**：正文为空、`finish_reason=length`，不报错但也没答案。

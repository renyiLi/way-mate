# 本科毕业设计（论文）开题报告

**题目：基于可执行验收契约的多模型协作软件交付工作台的设计与实现**

> 说明：本稿为初稿骨架，已按"工程为主、研究为辅"的本科定位收敛范围。参考文献需按学校格式（GB/T 7714）重新排版，并在知网/arXiv 上逐条核对卷期页码后再定稿。

## 一、选题背景与意义

### 1.1 背景

以大语言模型为核心的代码智能，已从"行级补全"走向"任务级交付"：给定一个仓库和一条 Issue，模型能够定位缺陷、修改代码并提交补丁。SWE-bench 等基准的提出，使这类能力第一次有了可比较的度量，顶尖系统在 SWE-bench Verified 上的解决率已由最初的个位数提升至 50% 以上。

但"能生成"不等于"能交付"。真实的小团队与教学场景中，交付的门槛不在生成速度，而在三件事：

1. **验收不可执行**——"改好了吗"依赖人眼判断，标准在动手之后才临时形成；
2. **协作缺客观裁决**——多个模型各说各话时，谁对谁错没有裁判；
3. **过程不可追溯**——出了问题无法回答"是哪一步、哪个模型、依据什么改的"。

本课题即针对上述三点，构建一个以"可执行验收契约"为中心的多模型协作交付工作台。

### 1.2 研究问题

- **RQ1（核心）**：将验收标准前置为机器可执行的契约（测试、静态检查、接口冻结、改动预算），能否在无人干预的情况下稳定判定 AI 交付物是否合格，并驱动自动修复？
- **RQ2**：在契约裁决的前提下，多模型非对称分工（拆解／实现／审查）相比单模型直出，在通过率、修复轮次与成本上表现如何？
- **RQ3**：模型适配层能否在不改动编排逻辑的前提下替换供应商，从而应对模型下线与接口变更？

### 1.3 意义

- **工程意义**：给出一套可复用的"契约即裁判"交付范式与参考实现，模型可替换、过程可审计、结果可重放。
- **实用意义**：面向课程设计、小型外包、开源维护等"低风险、高重复"的代码任务，降低人工验收成本。
- **教学意义**：把"需求—契约—实现—验收"的软件工程主干流程显式化，可作为工程训练的载体。

## 二、国内外研究现状

### 2.1 仓库级代码修复

HumanEval、MBPP 等函数级基准之后，SWE-bench 将评测推进到真实仓库与真实 Issue 层面。围绕该基准，出现两类路线：一类是复杂智能体框架，通过多轮工具调用与环境交互逐步逼近修复；另一类是**极简流水线**。后者以 Agentless 为代表，用"定位—修复—验证"三段式流程，以远低于前者的成本取得了相当甚至更优的结果，提示"流程纪律"可能比"智能体复杂度"更关键。AutoCodeRover 等工作则借助程序结构与测试信息改进定位环节。

**启示**：本课题不应追求"模拟一家 AI 软件公司"，而应构建纪律明确的流水线与客观闸门。

### 2.2 多模型／多智能体协作

MetaGPT、ChatDev 等框架以角色分工与结构化通信模拟软件开发组织；多智能体辩论（Multi-Agent Debate）与自一致性（Self-Consistency）则在推理任务上证明"多意见聚合"可提升正确率。但在代码任务上，这类方法的收益并不稳定：成本随模型数与轮数线性增长，而"模型互评"缺乏客观依据，容易退化为风格趋同的相互认可。

**启示**：多模型的正确用法不是"对称投票"，而是"非对称分工 + 客观裁决"。CodeT 用生成测试筛选候选解的思路，正是把裁判权交还给可执行的检查。

### 2.3 评测与验收

现有评测多关注 pass@k 类指标，面向"模型能力比较"而非"交付合格判定"。LLM-as-a-Judge 类方法虽被广泛使用，但存在偏好偏差与不可复现问题，难以作为交付验收的唯一依据。将验收转化为可执行检查（测试、lint、接口契约、改动预算），在工程上更可靠，也更易审计。

### 2.4 现状评述

综合来看，存在三个空白：其一，验收标准普遍后置，缺少前置化、可执行的契约表达；其二，多模型协作缺少客观裁判，多以互评替代验证；其三，交付过程缺少全链路审计与重放能力。本课题以此为切入点。

## 三、研究内容与目标

### 3.1 研究内容

1. **可执行验收契约 DSL 与闸门引擎**：定义 YAML 契约（测试用例、静态检查、公开接口冻结、改动预算、修复轮次上限），实现闸门执行器与结果归一化。
2. **多模型统一适配层**：以统一接口封装不同供应商的对话、工具调用、结构化输出与流式响应，归一化工具调用方言差异，统一 token 计量与重试退避。
3. **交付编排状态机**：需求解析 → 契约确认 → 任务分解 → 角色分派 → 沙箱执行 → 闸门判定 → 修复循环 → 签核归档，含终止条件与失败降级。
4. **沙箱执行与审计重放**：隔离执行环境、资源与时限约束；全链路记录提示、响应、工具调用、补丁、闸门结果与人工决策，支持按 run_id 重放。
5. **工作台前端**：项目／任务／契约／运行／审查／签核六个视图，支持补丁与闸门结果并排审查。

### 3.2 研究目标（可量化）

- 在自建 ≥20 条带隐藏测试的修复任务集上，契约闸门可自动判定合格性，误判率可人工复核；
- 引入契约闸门与修复循环后，任务最终通过率相较"单次生成"有可测量的提升；
- 模型供应商可在配置层面替换，替换后编排层代码零改动；
- 任一历史运行可按 run_id 完整重放，审计记录覆盖全部模型调用与决策点。

### 3.3 非目标（明确不做，用于控制范围）

- 不支持任意编程语言与任意仓库形态，限定为 Python + pytest 生态；
- 不实现自动合并主干与生产部署；
- 不承诺服务水平（SLA）与多人并发协作；
- 不追求在公开基准上刷新 SOTA。

## 四、技术路线与关键设计

### 4.1 总体架构

```
┌──────────────────── 工作台前端（六视图） ────────────────────┐
│  项目  任务  契约  运行  审查  签核                          │
└───────────────────────────┬─────────────────────────────────┘
                            │ HTTP / SSE
┌───────────────────────────▼─────────────────────────────────┐
│                      编排服务（状态机）                       │
│  需求解析 → 契约确认 → 分解 → 分派 → 执行 → 闸门 → 修复循环   │
└──────┬──────────────┬──────────────┬──────────────┬─────────┘
       │              │              │              │
┌──────▼─────┐ ┌──────▼─────┐ ┌──────▼─────┐ ┌──────▼──────┐
│ Provider   │ │ 契约引擎   │ │ 沙箱执行器 │ │ 审计与产物库 │
│ 注册表     │ │ (闸门)     │ │ (容器)     │ │ (append-only)│
│ DS/Kimi/.. │ │            │ │            │ │              │
└────────────┘ └────────────┘ └────────────┘ └──────────────┘
```

### 4.2 契约 DSL（示例）

```yaml
task_id: fix-parser-edgecase
repo: ./fixtures/repo_a
doD:
  tests:
    - "pytest tests/test_parser.py -q"
  lint:
    tool: ruff
    max_new: 0
  api:
    frozen: ["pkg.parser.parse"]
  diff:
    max_files: 5
    max_lines: 200
loop:
  repair_rounds: 3
  stop_on: all_green
  on_exhausted: escalate_to_human
```

### 4.3 关键设计

- **闸门即裁判**：所有判定由可执行检查给出，模型意见仅作为审查视图中的参考信息，不参与合格性计算。
- **非对称三角色**：拆解者（出计划与改动点）、实现者（产补丁）、审查者（对照契约挑刺），三者可由不同模型担任，亦可同一模型兼任，通过配置切换以支持消融实验。
- **修复循环与终止**：以"闸门未全绿且轮次未用尽"为继续条件；连续两轮无改进即提前终止，避免无效消耗。
- **上下文预算与仓库检索**：以失败测试到源码的映射、符号引用检索为主选取证据文件，在固定 token 预算下按相关性排序，超预算截断并记录。
- **可重放性**：外部模型响应落盘为 fixture，支持离线回放，既用于调试，也用于答辩演示的稳定性保障。

### 4.4 技术选型

| 层次 | 选型 | 理由 |
|---|---|---|
| 后端 | Python + FastAPI | 与代码任务生态一致，异步流式支持好 |
| 前端 | Vue 3 + Vite | 上手快，组件生态成熟 |
| 存储 | SQLite（开发）/ PostgreSQL（演示） | 降低部署门槛，便于迁移 |
| 沙箱 | Docker（WSL2 承载） | 隔离可靠，Windows 下稳定 |
| 检查工具 | pytest、ruff、mypy | 与契约项一一对应 |
| 模型接入 | DeepSeek、Kimi（必备）；Codex/OpenAI 兼容接口（可选第三家） | 保证两家可用即可完整运行，第三家作为可插拔性验证 |

## 五、创新点（工程型）

1. **以可执行契约为中心的交付闭环**：将验收标准前置为机器可判定的契约，使"是否合格"脱离人的主观判断，并直接驱动修复循环。
2. **非对称角色分工 + 契约裁决**：以客观检查替代多模型互评，规避对称投票的成本膨胀与趋同风险。
3. **全链路审计与离线重放**：模型响应落盘为可回放 fixture，使交付过程可追溯、演示可复现，同时降低对供应商可用性的依赖。

## 八、风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 模型接口变更或下线 | 系统不可用 | 适配层隔离 + 供应商注册表；契约与编排不感知具体厂商 |
| 第三家（Codex）额度不稳定 | 实验组数不足 | 必备两家保证闭环；第三家作为可插拔性验证，缺失时以录制回放替代 |
| 模型输出不确定 | 演示失败 | 响应落盘 fixture，答辩使用固定回放 |
| 范围蔓延 | 无法按期完成 | 以"非目标"清单为边界，新增需求进入展望章节 |
| 沙箱逃逸或资源耗尽 | 安全与稳定性 | 容器隔离、只读挂载、CPU/内存/时长上限、网络默认关闭 |
| 论文查重 | 学术规范 | 正文自撰，AI 仅用于提纲与文献整理，按学校要求披露使用情况 |

# 本科毕业设计（论文）开题报告

**题目：基于可执行验收契约的多角色协作代码交付系统设计与实现**

**英文题目：** Design and Implementation of a Multi-Role Collaborative Code Delivery System Based on Executable Acceptance Contracts

> 说明：本稿含 2026 年 11 月已完成的工程基础与初步实验数据，第八章之后为后续计划。
> 提交前请务必自行核对标 ⚠️ 的三处表述（见文末"提交前须知"）。

## 一、选题背景与意义

### 1.1 背景：瓶颈已从"生成"移到"判定"

以大语言模型为核心的代码智能，两年内从行级补全走到任务级交付：给定仓库与 Issue，模型可定位缺陷、修改代码、提交补丁。SWE-bench 等基准使这类能力第一次具备可比度量，主流系统的解决率已从个位数提升至 50% 以上。

然而工程实践中真正的成本并不在生成。生成一段代码只需数秒与几分钱，**判定这段代码能不能交付，仍需一名工程师阅读 diff、运行测试、确认没有破坏别的东西**。生成越便宜，判定越成为瓶颈——AI 把"写"的成本压到接近零，却把"验"的成本原样留给了人。

由此产生三个具体问题：

**其一，验收标准后置且不可执行。** "改好了吗"依赖人眼判断，标准在动手之后才临时形成，既无法自动执行，也无法在事后复现。

**其二，多模型协作缺少客观裁判。** 当多个模型给出不同方案时，谁对谁错没有依据；现有做法多让模型互评，而模型互评既不可靠也不可审计。

**其三，交付过程不可追溯。** 出了问题无法回答"是哪一步、哪个模型、依据什么改的"，也无法把一次成功或失败的交付完整重放。

### 1.2 本文的切入点

本文不试图让模型"更会写代码"，而是**把判定从人眼移到可执行契约**：动手之前先由人确认一份机器可执行的验收契约（测试命令、静态检查阈值、接口冻结、改动预算、精确断言），此后由闸门判定交付是否成立，模型只负责产出，不参与判定。

由此得到一条可检验的主线：

> **模型是可替换的工人，契约是不可替换的裁判。**

### 1.3 意义

- **工程意义**：给出"契约即裁判"的交付范式与参考实现，模型可替换、过程可审计、结果可重放。
- **方法意义**：使不同模型、不同协作规模可在**同一闸门、同一任务集**下被对照测量，为"多模型协作是否有效"提供可复现的实验方法——现有工具大多不具备这一能力。
- **教学意义**：把"需求—契约—实现—验收"的工程主干显式化，可作为工程训练的载体。

## 二、国内外研究现状

> 下列项目的 star 数为 2026 年 11 月 24 日通过 GitHub API 实测，仅用于刻画生态格局，不代表质量评价。

### 2.1 通用编码智能体

这一层是当前生态的主体，代表项目包括 codex（13.6 万）、gemini-cli（10.9 万）、OpenHands（9.4 万）、cline（7.2 万）、aider（5.0 万）、continue（3.7 万）。它们把"读仓库、改文件、跑命令"封装为可交互的智能体，工程成熟度很高。

学术路线上，SWE-agent（2.1 万）以 issue 到 patch 的端到端流程建立范式；Agentless（2.1 千）则用"定位—修复—验证"的三段式极简流水线，以远低于复杂智能体的成本取得相当甚至更优的结果，提示**流程纪律可能比智能体复杂度更关键**；AutoCodeRover 借助程序结构与测试信息改进定位环节。

**对本课题的启示**：不应追求"模拟一家 AI 软件公司"，而应构建纪律明确、判定客观的流水线。

### 2.2 多智能体协作框架

MetaGPT（7.1 万）以"第一家 AI 软件公司"为口号，用角色分工与结构化通信模拟软件开发组织；autogen（6.2 万）、crewAI（6.1 万）、LangGraph（4.5 万）提供编排基础设施；多智能体辩论与自一致性在推理任务上证明"多意见聚合"可提升正确率。

但这类方法在代码任务上的收益并不稳定：成本随模型数与轮数线性增长，而**"模型互评"缺乏客观依据**，容易退化为风格趋同的相互认可。CodeT 用生成测试筛选候选解的思路，正是把裁判权交还可执行检查。

**对本课题的启示**：多模型的正确用法不是"对称投票"，而是"非对称分工 + 客观裁决"。

### 2.3 多模型接入与国产化实践

国内已有工程实践走在前列：oh-my-coder（201 星）支持 DeepSeek、GLM 等 12 家以上国产模型并做多智能体协作；magi-code（221 星）为本地优先的多智能体客户端；feikong-teams（157 星）提供多智能体圆桌讨论模式。这些项目在**接入广度与产品形态**上已相当成熟。

**对本课题的启示**：多模型接入本身已不构成创新点，本课题不应在此竞争，而应把多模型作为**受控实验的自变量**。

### 2.4 验收与闸门

与本文最接近的是一批规模很小的新项目：skillgate（10 星）提出"与模型无关的确定性完成线闸门"；proof-loop（12 星）提出仓库内验证协议与验收标准；qikly（23 星）从验收标准生成测试套件再收敛代码；contract-driven-development（2 星）以多份契约加分级守卫约束 AI 编程。

此外，代码审查类工具规模较大（阿里 open-code-review 5.6 万、PR Agent 1.7 万），但它们解决的是"审查建议"，不承担"交付判定"职责。

**对本课题的启示**：方向真实存在且尚未成型——**全部相关工作均小于 25 星，且为单仓库、单模型、无对照测量**。这既是机会，也意味着可借鉴的工程先例有限。

### 2.5 现状评述：三个空白

1. **验收标准后置**：缺少可前置、可执行、可复现的契约表达；
2. **协作缺客观裁判**：多模型场景下以互评替代验证，结论不可审计；
3. **缺少可比测量**：现有工具面向"帮人干活"，不面向"产出可比较的实验数据"，因而"多模型是否更好"始终缺乏同条件证据。

本文以这三个空白为切入点。

## 三、研究内容与目标

### 3.1 研究内容

1. **可执行验收契约 DSL**：以 YAML 描述五类验收项——测试命令、静态检查新增阈值、公开接口冻结、改动预算（文件数 / 行数 / 禁止路径）、精确断言（须逐字出现的字符串）；字段严格校验，拼错即报错。
2. **四类闸门与判定归一化**：tests / lint / api / diff，逐项输出结构化结果，作为唯一判定依据。
3. **精确断言的静态提取**：用 AST 从 `pytest.raises(match=...)` 反推"必须逐字出现"的字符串，自动生成契约条目，附来源行号与漂移检查，解决"验收要求藏在测试里、模型只能揣摩"的问题。
4. **三座位协作协议**：提案 / 复核 / 裁决三个座位固定，模型数量只决定排班；2 人、3 人、3 人双轨三种协议共用一台状态机。
5. **审计与回放**：全链路记录提示、响应、闸门结果、token 与延迟，支持按运行标识重放。
6. **多供应商适配**：统一的能力协商、错误分类与降级登记，一个适配器覆盖多个兼容端点，新增供应商不改编排层。

### 3.2 研究目标（可量化）

- 在自建任务集（≥20 条，按难度分层）上，闸门可自动判定合格性，判定结果可人工复核；
- 引入精确断言后，同类任务的首次通过率与 token 成本有可测量的改善；
- 模型供应商可在配置层替换，替换后编排层代码零改动；
- 任一历史运行可按运行标识完整重放，审计覆盖全部模型调用与判定点。

### 3.3 适用边界与非目标

**适用边界（本课题的核心论断之一）**：可执行验收契约仅适用于**存在客观判据**的交付任务。判据的可获得性决定契约强度，与所属行业无关。对不存在客观判据的任务（营销创意、观点生成等），本机制只能做结构与一致性检查，必须显式转人工。

**非目标**：

- 不追求在公开基准上刷新最优成绩；
- 不支持任意编程语言，限定 Python + pytest 生态；
- 不实现自动合并主干与生产部署；
- 不实现多用户并发协作；
- 不做跨行业的落地实现（金融、电商等场景仅在边界讨论中作为同构推论提及，不作为工作量主张）。

## 四、技术路线与关键设计

### 4.1 总体架构

```
┌──────────────── 工作台前端（任务 / 运行 / 审查 / 签核）────────────────┐
└───────────────────────────────┬─────────────────────────────────────────┘
                                │ HTTP
┌───────────────────────────────▼─────────────────────────────────────────┐
│                        协议机（状态机）                                  │
│   提案 → 复核 → 裁决 → 闸门 → 未绿则反馈并进入下一轮                      │
└──────┬──────────────┬──────────────┬──────────────┬─────────────────────┘
       │              │              │              │
┌──────▼─────┐ ┌──────▼─────┐ ┌──────▼─────┐ ┌──────▼──────┐
│ 供应商注册表│ │ 契约与闸门  │ │ 沙箱执行器  │ │ 审计与产物库 │
│ 多端点多模型│ │ 唯一裁判    │ │ 隔离运行    │ │ 可重放       │
└────────────┘ └────────────┘ └────────────┘ └─────────────┘
```

### 4.2 契约示例

```yaml
task_id: fix-parser-inline-comment
repo: .
doD:
  tests:
    - cmd: pytest tests/test_parser.py -q
      timeout_s: 120
  lint: {tool: ruff, max_new: 0}
  api:  {frozen: [pkg.parser.parse_kv]}
  exact:
    - exception: ValueError
      contains: "missing '='"
      source: "tests/test_parser.py:25"
      origin: auto
  diff: {max_files: 5, max_lines: 120, forbid: [tests/]}
loop: {repair_rounds: 3, on_exhausted: escalate_to_human}
```

### 4.3 可验证性分类

把闸门按"可验证性"而非"行业"分类，是本设计的关键抽象：

| 类型 | 判定方式 | 例子 |
|---|---|---|
| 执行型 | 运行程序看退出码 | 单元测试、校验脚本 |
| 结构型 | 模式与必填项 | JSON Schema、字段完整性 |
| 一致性型 | 跨源比对 | 合计勾稽、口径一致 |
| 约束型 | 白名单 / 区间 | 禁止路径、改动预算、合规词表 |
| 主观型 | **不判定，显式转人工** | 文案质量、观点正确性 |

最后一行是设计判断力所在：明确声明"这一类不判"，比声称"什么都能判"更可信。

### 4.4 三座位协议

| 协议 | 排班 | 分歧由谁消解 |
|---|---|---|
| 2 人 | 提案 + 复核 | 只能交闸门 |
| 3 人单轨 | 提案 + 复核 + 裁决 | 裁决消解一部分，闸门终裁 |
| 3 人双轨 | 双提案 + 裁决 + 复核 | 裁决选提案，闸门终裁 |

**铁律**：只有闸门能宣布交付成立。复核认为有问题而闸门全绿，交付成立（模型可能误报）；复核认为无问题而闸门红，交付不成立（模型可能漏报）。

裁决座位只裁"结论是否成立"，不得新增结论、不得评价代码质量——否则它与闸门冲突，成本翻倍而信息量为零。

### 4.5 审计与可重放

每次运行写入 JSONL：运行标识、基线提交、座位排班、逐次模型调用的输入摘要与原始输出、token、延迟、降级标记、逐闸门结果、终止原因。

模型响应同时落盘为回放素材，使同一实验可离线重跑——这既是论文数据可复现的基础，也使演示不依赖网络与账号状态。

## 五、创新点

1. **以可执行契约为唯一裁判的交付闭环**：判定权从模型移交给契约，使"是否合格"可自动执行、可复现，并使多模型场景下的争议有客观出口。
2. **精确断言的静态提取**：从测试断言反推"须逐字出现"的约束并纳入契约，把隐含的验收要求显式化，同时提供契约与测试的漂移检查。
3. **座位固定、人数可变的协作协议**：三种协作规模共用一台状态机，使"协作规模"成为可对照实验的自变量，而非三套互不相干的实现。
4. **可验证性决定适用边界**：提出并论证"契约强度取决于任务可验证度、与行业无关"这一边界结论，明确机制的适用与失效条件。

## 六、实验设计

### 6.1 任务集

自建 20 条以上修复任务，按**单模型通过率**分为易 / 中 / 难三档。分层的理由来自初步实验的教训：若任务对多数模型都过于简单，各条件均达上限，无法区分差异（详见 6.4）。

### 6.2 对照与基线

- **主对照**：有无精确断言（同一代码路径，仅契约副本差异）；
- **协作对照**：单轮单模型 / 2 人协议 / 3 人协议；
- **消融**：逐一移除复核座位与裁决座位，观察通过率下降幅度（边际贡献）。

### 6.3 指标

首次通过率、最终通过率、平均修复轮次、token 消耗、墙钟时间、人工介入次数、复核结论的采纳率与被丢弃率。

### 6.4 已获初步结果（2026 年 11 月）

单条任务，三模型 × 两条件 × 各 3 次：

| 模型 | 无精确断言 | 有精确断言 | 平均 token | 平均耗时 |
|---|---|---|---|---|
| deepseek-chat | 0/3 | 3/3 | 999 → 1046 | 1.8s → 2.3s |
| kimi-k3-1-pro | 3/3 | 3/3 | 5513 → 2308（−58%） | 110s → 46s |
| deepseek-v4-flash | 3/3 | 3/3 | 2207 → 2030 | 8.3s → 6.3s |

三项观察：

1. **救回效应**：首个模型由三次全败变为三次全胜，效应稳定；
2. **成本效应**：第二个模型结果不变但 token 与耗时各降约 58%，说明精确约束减少的是"推测该满足什么"的试错；
3. **天花效应**：第三、第四个模型在两条件下均满分，说明单条任务对它们过于简单，无法区分条件。

另在 2 人协议的真实运行中观察到：首轮复核提出的两条结论均因缺少证据被规则丢弃，第二轮闸门转绿而仍存一条阻断结论，系统按"闸门终裁"判定交付成立——两条协议条款在真实模型上得到验证。

### 6.5 方法论教训

初次实验仅每格 1 次，曾得出"四组结果与某特征完全相关"的结论；重复 3 次后该结论不再成立。

**据此确定三条实验纪律**：任务集必须难度分层；每格不少于 3 次；只报告有重复支撑的结论。该纪律本身将写入论文实验章节。

## 九、风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 任务集过易致天花效应 | 条件间无差异，实验无结论 | 按单模型通过率分层，难档优先 |
| 模型行为不确定 | 单次结果不可信 | 每格 ≥3 次，报告分布而非单值 |
| 推理模型输出预算被耗尽 | 返回空正文而不报错 | 能力表登记固定参数与预算下限，空正文按失败计 |
| 多供应商接口变更 | 系统不可用 | 适配层隔离 + 配置化能力表 + 录制回放 |
| 范围蔓延至其他行业 | 各域皆浅，答辩失焦 | 以"可验证性分类"为边界，跨域仅作论断不作实现 |
| 私有仓库 CI 额度受限 | 自动化验证中断 | 已转公开仓库；本地等价检查脚本兜底 |
| 论文查重 | 学术规范 | 正文自撰，模型仅用于评审与提纲，按学校要求披露 |

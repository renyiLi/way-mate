# 基于可执行验收契约的多角色协作代码交付系统设计与实现

**本科毕业设计（论文）**

2026 年 11 月

---

## 摘要

大语言模型使代码生成的成本急剧下降，但“这段代码能不能交付”仍依赖工程师阅读 diff、运行测试并人工确认，判定由此成为新的瓶颈。本文设计并实现一个以可执行验收契约为唯一判定依据的多角色代码交付系统：动手之前由人确认契约（测试命令、静态检查阈值、接口冻结、改动预算、精确断言），模型只负责产出补丁，交付是否成立由四类闸门判定，模型不参与判定。

系统以 Python 实现，包含契约 DSL 与严格校验、tests/lint/api/diff 四类闸门、基于 AST 的精确断言提取、提案/复核/裁决三座位协议机、两套执行后端（一次生成与多步循环）、多供应商适配与 JSONL 审计。仓库现有约 4,000 行源码与 84 条离线测试，并在 4 条真实仓库修复任务上运行。

实验表明：（1）精确断言使一个模型由 0/3 提升为 3/3，另一个模型 token 消耗降低 58%（实验 11/24/1）；（2）真实仓库任务最终可由后端 A 交付成立，最小修复 1 行（实验 11/25/1）；（3）闸门能把“4 条测试过 3 条”精确判为不可交付（实验 11/25/5）；（4）2 人协议在当前任务与模型上未观察到通过率增益，累计 1/8，成本约为单轮的 4.8 倍（实验 11/25/7），根因之一是复核结论的字段语义与系统定义不匹配（实验 11/25/8）。本文据此给出系统的适用边界：契约与闸门适用于存在客观判据的交付任务；多角色协作的收益尚未被证实，不能作为默认配置。

**关键词**：可执行验收契约；代码交付；闸门；多角色协作；大语言模型

> 英文摘要按学院模板补写；本文数字均标注实验编号，来源见 `experiments/`。

## 第 1 章 绪论

### 1.1 研究背景

以大语言模型为核心的代码智能，在两年内从行级补全走到任务级交付：给定仓库与 Issue，模型可以定位缺陷、修改代码、提交补丁。SWE-bench 等基准使这类能力第一次具备可比度量，主流系统的解决率已从个位数提升到 50% 以上[1]。生成一段代码只需要数秒与几分钱，工程实践中的主要成本却不在生成。

真正的成本在判定。一段补丁能不能交付，仍要由工程师阅读 diff、运行测试、确认没有破坏其他功能。生成越便宜，判定越成为瓶颈：AI 把“写”的成本压到接近零，却把“验”的成本原样留给了人。由此产生三个具体问题。

**其一，验收标准后置且不可执行。** “改好了吗”依赖人眼判断，标准在动手之后才临时形成，既无法自动执行，也无法在事后复现。

**其二，多模型协作缺少客观裁判。** 当多个模型给出不同方案时，谁对谁错没有依据。现有做法多让模型互评，而模型互评既不可靠也不可审计。

**其三，交付过程不可追溯。** 出了问题无法回答“是哪一步、哪个模型、依据什么改的”，也无法把一次成功或失败的交付完整重放。

### 1.2 研究切入点

本文不试图让模型“更会写代码”，而是把判定从人眼移到可执行契约：动手之前先由人确认一份机器可执行的验收契约，此后由闸门判定交付是否成立，模型只负责产出，不参与判定。

由此得到一条可检验的主线：**模型是可替换的工人，契约是不可替换的裁判。** 模型之间可以争论，但只有闸门能宣布交付成立。

### 1.3 研究内容

本文的研究内容由六部分组成。

1. **可执行验收契约 DSL**：以 YAML 描述五类验收项——测试命令、静态检查新增阈值、公开接口冻结、改动预算（文件数/行数/禁止路径）、精确断言（须逐字出现的字符串）；字段严格校验，拼错即报错。
2. **四类闸门与判定归一化**：tests、lint、api、diff 逐项输出结构化结果，作为唯一判定依据。
3. **精确断言的静态提取**：用 AST 从 `pytest.raises(match=...)` 反推“必须逐字出现”的字符串，自动生成契约条目，附来源行号与漂移检查。
4. **三座位协作协议**：提案、复核、裁决三个座位固定，模型数量只决定排班；2 人、3 人、3 人双轨三种协议共用一台状态机。
5. **两套执行后端**：后端 A 一次调用产出全部改动；后端 B 在仓库中多步探查、编辑、自测，最终归一到补丁。两者共用同一套闸门。
6. **审计与多供应商适配**：全链路记录提示、响应、闸门结果、token 与延迟；统一能力协商、错误分类与降级登记。

### 1.4 主要工作与贡献

1. **以可执行契约为唯一裁判的交付闭环。** 判定权从模型移交给契约，使“是否合格”可自动执行、可复现，并使多模型场景下的争议有客观出口。系统在真实仓库任务上验证了闭环可运行（实验 11/25/1）。
2. **精确断言的静态提取与漂移检查。** 把测试断言里隐含的逐字要求提进契约，使隐含验收要求显式化；对照实验显示它能救回一个模型、并显著降低另一个模型的成本（实验 11/24/1）。
3. **座位固定、人数可变的协议机与双后端。** 三种协作规模共用一台状态机，两套执行后端共用一套闸门，使“协作规模”与“执行方式”成为可对照实验的自变量，而不是三套互不相干的实现。
4. **可复现的实验方法与一条负结果。** 本文把“成功与失败都记录”作为实验纪律，给出 2 人协议在当前任务与模型上无增益、成本约 4.8 倍的证据（实验 11/25/7、11/25/9），并定位到复核字段语义这一具体根因（实验 11/25/8）。负结果不是装饰，它标出了方法的适用边界。

### 1.5 论文组织

第 1 章给出背景、切入点与研究内容；第 2 章综述国内外研究现状并指出三个空白；第 3 章做需求分析；第 4 章给出系统设计；第 5 章说明实现与关键问题；第 6 章报告实验，包括失败实验与负结果；第 7 章总结并给出后续工作。

## 第 2 章 国内外研究现状

### 2.1 通用编码智能体

这一层是当前生态的主体。工程侧的代表项目包括 codex、gemini-cli、OpenHands[10]、cline、aider、continue，它们把“读仓库、改文件、跑命令”封装为可交互的智能体，工程成熟度很高；大语言模型用于软件工程也已有系统综述[13]。学术路线上，SWE-agent 以 issue 到 patch 的端到端流程建立范式[4]；Agentless 用“定位—修复—验证”的三段式极简流水线，以远低于复杂智能体的成本取得相当甚至更优的结果[2]，提示流程纪律可能比智能体复杂度更关键；AutoCodeRover 借助程序结构与测试信息改进定位环节[3]；仓库级检索方面，RepoCoder[14] 通过迭代检索改进了跨文件上下文。

对本课题的启示是：不应追求“模拟一家 AI 软件公司”，而应构建纪律明确、判定客观的流水线。本文的后端 B 正是在这一判断下选择“多步循环 + 单一编辑格式”，而不是堆叠角色与工具。

### 2.2 多智能体协作框架

MetaGPT 以角色分工与结构化通信模拟软件开发组织[5]；ChatDev 用对话链组织设计、编码、测试等阶段[6]；AutoGen、CrewAI、LangGraph 提供编排基础设施；多智能体辩论与自一致性在推理任务上证明“多意见聚合”可以提升正确率[7][8]。

但这类方法在代码任务上的收益并不稳定：成本随模型数与轮数线性增长，而模型互评缺乏客观依据，容易退化为风格趋同的相互认可。CodeT 用生成测试筛选候选解的思路，正是把裁判权交还可执行检查[9]。

对本课题的启示是：多模型的正确用法不是“对称投票”，而是“非对称分工 + 客观裁决”。本文的三座位协议据此设计：复核只提可疑之处，裁决只裁结论是否成立，最终判定始终归闸门。

### 2.3 多模型接入与国产化实践

国内已有工程实践走在前列：oh-my-coder 支持 DeepSeek、GLM 等十余家国产模型并做多智能体协作；magi-code 为本地优先的多智能体客户端；feikong-teams 提供多智能体圆桌讨论模式。这些项目在接入广度与产品形态上已相当成熟。

对本课题的启示是：多模型接入本身已不构成创新点，本课题不应在此竞争，而应把多模型作为受控实验的自变量。本文的能力协商与降级登记，目的不是“支持更多家”，而是让“换一家模型”不改变编排层代码，从而使模型成为可替换的工人。

### 2.4 验收与闸门

与本文最接近的是一批规模很小的新项目：skillgate 提出“与模型无关的确定性完成线闸门”；proof-loop 提出仓库内验证协议与验收标准；qikly 从验收标准生成测试套件再收敛代码；contract-driven-development 以多份契约加分级守卫约束 AI 编程。此外，代码审查类工具规模较大（如 open-code-review、PR Agent），但它们解决的是“审查建议”，不承担“交付判定”职责。

这批工作的共同点是：方向真实存在，但尚未成型——多为单仓库、单模型、无对照测量。这既是机会，也意味着可借鉴的工程先例有限。

### 2.5 现状评述：三个空白

1. **验收标准后置**：缺少可前置、可执行、可复现的契约表达；
2. **协作缺客观裁判**：多模型场景下以互评替代验证，结论不可审计；
3. **缺少可比测量**：现有工具面向“帮人干活”，不面向“产出可比较的实验数据”，因而“多模型是否更好”始终缺乏同条件证据。

本文以这三个空白为切入点。与上述工作相比，本文的差异不在“再做一个智能体”，而在把判定权交给契约、把协作规模做成可对照变量，并把失败实验一并记录下来。第 6 章将说明：这条路走通了“判定”，但还没有走通“协作收益”。

## 第 3 章 需求分析

### 3.1 用户角色与使用场景

系统面向单用户本地使用，但同一用户在不同阶段扮演三种角色。

| 角色 | 做什么 | 关心什么 |
|---|---|---|
| 任务作者 | 选仓库与 PR、生成任务配方、写契约、校验红绿 | 契约是否写全、任务是否可复现 |
| 运行者 | 选任务、模型、后端、协议，发起一次或一批交付 | 通过率、成本、失败原因 |
| 审查者 | 看闸门明细与审计、决定接受或退回 | 判定是否可信、过程是否可追溯 |

单用户本地意味着不做登录、权限与多租户；三种角色的区分落实为“操作入口”与“产物形态”，而不是账号体系。

### 3.2 功能需求

| 编号 | 需求 | 说明 |
|---|---|---|
| FR1 | 任务库 | 管理 `tasks/<id>/task.json` 与 `contract.yaml`，记录基线提交、测试补丁与红绿校验 |
| FR2 | 契约编辑与校验 | YAML 描述五类验收项；未知字段、类型错误、缺必填项立即报错 |
| FR3 | 四类闸门 | tests / lint / api / diff 逐项判定，输出结构化结果；`all_green` 是唯一交付结论 |
| FR4 | 精确断言 | 从 `pytest.raises(match=...)` 静态提取；带来源行号；提供契约与测试的漂移检查 |
| FR5 | 三座位协议 | 提案 / 复核 / 裁决；2 人、3 人、双轨三种排班；轮次、预算、证据规则可配 |
| FR6 | 双执行后端 | 后端 A 一次生成；后端 B 多步循环；统一归一到补丁，交同一套闸门 |
| FR7 | 审计与追溯 | JSONL 记录运行标识、模型调用、闸门结果、token 与延迟 |
| FR8 | 多供应商适配 | 统一封套与能力表；缺失能力降级并登记，换供应商不改编排层 |
| FR9 | 运行报告 | 把一次运行的闸门明细、成本、结论汇总为可读报告；回放列为后续工作 |
| FR10 | 批量实验 | 任务 × 配置批量运行，产出可汇总的原始记录 |

### 3.3 非功能需求

| 编号 | 需求 | 约束 |
|---|---|---|
| NFR1 | 可复现 | 依赖版本钉死；每条结论附复现命令；实验记录与原始日志分离 |
| NFR2 | 可追溯 | 每次运行有唯一 `run_id`；模型调用与闸门判定均可按 `run_id` 定位 |
| NFR3 | 单用户本地 | 不做多用户并发、权限与云端部署 |
| NFR4 | 受限执行 | 命令限定在工作目录内执行，带超时；当前版本不是安全沙箱，边界见 3.4 |
| NFR5 | 可扩展 | 新增供应商只改配置与适配层；新增任务只加配方与契约 |
| NFR6 | 成本可控 | 单次运行有调用与 token 预算；超限终止并记录终止原因 |

### 3.4 边界与非目标

**适用边界**：可执行验收契约只适用于存在客观判据的交付任务。判据的可获得性决定契约强度，与所属行业无关。对不存在客观判据的任务（营销创意、观点生成等），本机制只能做结构与一致性检查，必须显式转人工。

**非目标**：

- 不追求在公开基准上刷新最优成绩；
- 不支持任意编程语言，限定 Python + pytest 生态；
- 不实现自动合并主干与生产部署；
- 不实现多用户并发协作；
- 当前版本不提供安全沙箱、HTTP 服务与工作台前端，三者列为后续工作。

### 3.5 典型用例：跑一次真实交付

1. 任务作者用 `prepare_task.py` 按配方克隆仓库、应用测试补丁、校验“旧源码红、加修复绿”；
2. 运行者用 `run_once.py`（后端 A）或 `run_runtime.py`（后端 B）发起一次交付；
3. 系统调用模型，把输出解析为补丁，写入工作区；
4. 四类闸门依次运行，输出逐项结果与 `all_green`；
5. 审查者按 `run_id` 查看审计与闸门明细，决定接受或退回；
6. 一次运行的全部事件写入 `runs/audit.jsonl`，关键数字抄录进 `experiments/` 的记录。

### 3.6 小结

需求的核心不是“功能多”，而是“判定可信、过程可查”。因此 FR3（闸门）与 FR7（审计）是硬需求，FR9（报告）与 FR10（批量）是效率需求，HTTP、前端、沙箱不在本期范围内。

## 第 4 章 系统设计

### 4.1 总体架构

系统采用“薄入口 + 厚内核 + 可替换边界”的分层结构。入口是一组命令行脚本；内核由契约、闸门、协议机、执行后端、适配器与审计组成；边界是可替换的供应商、任务与工作区。

```
┌──────────────────── 入口层（CLI 脚本）────────────────────┐
│ prepare_task  run_once  run_runtime  run_protocol  baseline │
└───────────────────────────┬────────────────────────────────┘
                            │
┌───────────────────────────▼────────────────────────────────┐
│ 编排层  delivery（单轮） / protocol.machine（多座位）        │
│ 座位、轮次、预算、补丁归一化、终止条件                        │
└───┬──────────────┬──────────────┬──────────────┬───────────┘
    │              │              │              │
┌───▼────┐   ┌─────▼─────┐  ┌─────▼─────┐  ┌─────▼─────┐
│ 适配器  │   │ 契约/闸门  │  │ 执行后端   │  │ 审计       │
│ 多供应商│   │ 唯一裁判   │  │ A / B      │  │ JSONL      │
└────────┘   └───────────┘  └───────────┘  └───────────┘
```

图中未画出的 HTTP 服务与工作台前端属于规划内容，当前版本不提供；论文不把它们写成已实现。

### 4.2 契约 DSL

契约是系统的“唯一裁判”，因此设计目标是**可读、可校验、不可含糊**。

| 段 | 字段 | 作用 |
|---|---|---|
| `doD.tests` | `cmd`、`timeout_s` | 验收命令；退出码非 0 即失败 |
| `doD.lint` | `tool`、`max_new` | 静态检查新增问题上限；与基线比较 |
| `doD.api` | `frozen` | 冻结的公开符号；缺失即失败 |
| `doD.exact` | `exception`、`contains`、`source`、`origin` | 必须逐字出现的字符串及其来源 |
| `doD.diff` | `max_files`、`max_lines`、`forbid` | 改动预算与禁止路径 |
| `loop` | `repair_rounds`、`on_exhausted` | 修复轮次上限与耗尽后的处理 |

解析器对未知字段、类型错误与缺必填项一律报错，不做“尽量理解”。理由是：契约一旦容忍拼写错误，闸门就可能在一个空契约上宣布通过。

```yaml
task_id: tabulate-366
repo: .
doD:
  tests: [{cmd: "python -m pytest test/test_output.py::test_github_multiline -q", timeout_s: 120}]
  lint: {tool: ruff, max_new: 0}
  api: {frozen: []}
  exact: []
  diff: {max_files: 3, max_lines: 40, forbid: [test/]}
loop: {repair_rounds: 3, on_exhausted: escalate_to_human}
```

### 4.3 四类闸门

| 闸门 | 输入 | 通过条件 | 主要失败形态 |
|---|---|---|---|
| tests | 命令 argv、超时 | 所有命令退出码为 0 | 功能没做对、只对一部分 |
| lint | 工具、基线、上限 | 新增问题数不超过 `max_new` | 越改越乱 |
| api | 冻结符号列表 | 符号仍可导入 | 顺手破坏外部接口 |
| diff | 文件数、行数、禁止路径 | 未超预算、未触碰禁止路径 | 大面积重写、改测试代替改代码 |

四类闸门是并列关系，不是加权关系：任何一项失败，`all_green` 为假。判定归一化只做一件事——把“通过/失败”与可读明细放进同一个结构，供入口、审计与实验共用。

### 4.4 精确断言

测试里的 `pytest.raises(ValueError, match="missing '='")` 包含一条逐字约束，但模型只能从 traceback 里揣摩。精确断言的提取分三步：

1. 用 AST 遍历测试函数，找到 `pytest.raises` 调用；
2. 读取 `match` 参数，过滤含正则元字符的模式（宁可少收，不可错收）；
3. 生成 `exact` 条目，记录异常类型、字符串、来源文件与行号，`origin=auto`。

人工写的条目 `origin=manual`。`extract_exact.py --check` 在 CI 中比对“契约里声明的”与“测试里实际的”，防止契约与测试漂移。

### 4.5 三座位协议

| 协议 | 排班 | 分歧由谁消解 |
|---|---|---|
| `2p.single` | 提案 + 复核 | 只能交闸门 |
| `3p.single` | 提案 + 复核 + 裁决 | 裁决消解一部分，闸门终裁 |
| `3p.dual` | 双提案 + 裁决 + 复核 | 裁决先选提案，闸门终裁 |

状态机的主动线是：提案 → 复核 →（裁决）→ 闸门 → 未绿则带失败明细进入下一轮。**铁律**：只有闸门能宣布交付成立。复核认为有问题而闸门全绿，交付成立（模型可能误报）；复核认为无问题而闸门红，交付不成立（模型可能漏报）。

复核结论必须带证据；没有证据的结论按 R-2 规则丢弃，不进入阻断。裁决只裁“结论是否成立”，不得新增结论、不得评价代码质量——否则它会与闸门冲突，成本翻倍而信息量为零。

### 4.6 两套执行后端

| 维度 | 后端 A（direct） | 后端 B（runtime） |
|---|---|---|
| 形态 | 一次调用产出全部改动 | 多步：探查 + 编辑 + 自测 |
| 上下文 | 任务 + 失败输出 + 目标文件全文 | 任务 + 失败输出，自行 grep |
| 编辑 | 整文件或 SEARCH/REPLACE | `edit:` 块 + SEARCH/REPLACE |
| 成本结构 | token 由目标文件大小决定，近似常数 | 每次只读几十行，但调用次数多 |
| 风险 | 大文件写不完、截断 | 只读不写、预算耗尽 |

两套后端最终都归一到 `Patch`，交同一套闸门。这样“执行方式”成为实验变量，而不是两套判定标准。

### 4.7 数据与审计

任务由 `task.json` 与 `contract.yaml` 描述；`task.json` 记录仓库、基线提交、任务陈述、目标测试、目标文件、难度档与红绿校验结果。运行由 `run_id` 标识，审计事件包括 `run_start`、`model_request`、`model_response`、`gate_report`、`runtime_run`、`run_end`。

任务状态为“草稿 / 就绪”，运行状态为“运行中 / 接受 / 拒绝 / 升级人工 / 错误”。状态不是装饰：它决定了重跑、对比与统计时哪些记录可用。

### 4.8 错误处理与降级

| 情况 | 处理 |
|---|---|
| 供应商不支持严格 JSON Schema | 降级为 `json_object`，登记 `degraded` |
| 只接受固定 temperature | 强制取值并登记 |
| 推理吃光输出预算、正文为空 | 按失败计，不当作“空提案”放过 |
| 调用超时、限流 | 可重试错误重试；不可重试错误记为失败运行 |
| 预算耗尽 | 终止并记录 `budget_exhausted`，不宣布通过 |

降级不是隐藏：每一次降级都写入审计，避免实验结论把“能力差异”误读成“模型差异”。

### 4.9 安全与边界

补丁路径在解析层拒绝绝对路径与 `..`，`diff.forbid` 拦下触碰测试目录的改动。密钥只从环境变量或 `.env` 读取，日志只允许掩码。需要明确的是：当前执行环境 `LocalEnvironment` 只隔离工作目录与超时，**不是安全沙箱**；它不提供断网、只读挂载与 CPU/内存限额。这一限制在第 7 章列为后续工作，论文不把它写成“沙箱”。

### 4.10 小结

设计的核心是“把判定与生成分开”：契约与闸门负责判定，协议机与后端负责生成，审计负责追溯。分开之后，模型可以替换、后端可以替换、协作规模可以对照，而判定标准不动。

## 第 5 章 系统实现

### 5.1 技术栈与代码组织

系统以 Python 3.11 实现，运行时只依赖 PyYAML；pytest 与 ruff 仅用于开发与 CI。源码放在 `src/dbw/`，按职责分为契约、闸门、精确断言、协议、适配器、执行后端、审计与交付编排八组模块，约 4,000 行（不含测试）。

| 模块 | 职责 |
|---|---|
| `contract.py` | 契约解析、严格校验、数据类 |
| `gates.py` | tests / lint / api / diff 四类闸门与报告 |
| `exact.py` | 精确断言的 AST 提取与漂移检查 |
| `protocol/` | 封套、能力协商、分内接口、三座位协议机 |
| `adapters/` | OpenAI 兼容适配器、错误分类 |
| `runtime/` | 后端 B 的循环、本地环境、工作区快照与差异 |
| `delivery.py` | 后端 A 的单轮交付编排 |
| `audit.py` | JSONL 审计与运行标识 |
| `edit_format.py` | SEARCH/REPLACE 编辑格式 |

入口是一组脚本（`prepare_task.py`、`run_once.py`、`run_runtime.py`、`run_protocol.py`、`baseline.py`），它们只做参数解析与结果打印，核心逻辑在库内，保证“实验里跑的”和“手工跑的”是同一条代码路径。

### 5.2 契约解析

契约用 `dataclass` 建模：`Contract` 持有 `task_id`、`repo`、`tests`、`lint`、`api`、`exact`、`diff` 与 `loop`；`TestSpec` 保存命令、超时与解析后的 argv；`ExactSpec` 保存异常类型、字符串、来源与来源方式。

解析器维护每类节点的允许键集合，出现未知键立即抛出带路径的错误（例如 `doD.diff.max_file` 会提示“未知字段”）。类型错误、缺必填项、空测试列表同样报错。这样做的代价是写契约时更啰嗦，收益是闸门不会在“拼错的契约”上给出通过。

### 5.3 闸门实现

四类闸门共享一个命令执行函数 `_run(argv, cwd, timeout_s)`：以参数列表而非 shell 字符串执行，避免引号与管道带来的注入面；超时返回专用退出码 124，命令不存在返回 127。

- **tests**：逐条执行契约中的命令，解析 pytest 输出里的 passed/failed/error/skipped 计数；任一命令退出码非 0 即失败，并保留末尾若干行作为证据。
- **lint**：先跑基线，再跑打补丁后的 ruff，比较“新增问题数”与 `max_new`；只罚新增，不罚历史遗留。
- **api**：在打补丁后的工作区尝试导入冻结符号，缺失即失败；不冻结时直接通过并注明。
- **diff**：用 git 取改动文件与行数，检查文件数、行数与 `forbid` 路径；禁止路径命中即失败。

`GateReport` 固定四项、顺序固定，`all_green` 只有在四项全通过时为真。入口、审计与实验都只读这个字段，不各自计算。

### 5.4 精确断言的实现

`exact.py` 用 `ast` 遍历测试文件，定位 `pytest.raises` 调用，读取 `match` 关键字；含正则元字符的模式直接跳过，避免把正则当字面量收进契约。提取结果带 `source`（文件:行号）与 `origin=auto`，人工补充的条目为 `origin=manual`。

`extract_exact.py --check` 把“契约里声明的精确断言”与“测试里实际存在的”做集合比对，差异即失败；该检查已接入 CI，防止测试改了而契约没改。

### 5.5 协议机的实现

`ProtocolRunner` 持有座位表、协议标识、轮次上限与预算。座位表允许同一模型坐多个座位，此时 `self_played=true`，实验记录必须标出，否则会把“自演”误读成“多模型”。

每轮流程是：构造提案提示 → 调用提案模型 → 解析补丁 → 复核模型给出结论 →（裁决模型消解分歧）→ 跑闸门 → 若未全绿，把失败明细带入下一轮。复核结论必须带证据；无证据的结论按 R-2 丢弃。

11/25/4 之前，单轮后端与协议机各自拼提案提示，协议机多塞了一段完整 doD，导致“单轮 vs 2 人”不可比。此后新增 `render_propose_prompt(task, contract)` 作为唯一构造点，并加测试断言两处提示逐字相同（实验 11/25/4）。这是方法学修复，不是功能修复：不统一提示词，后续所有协作对比都不可信。

### 5.6 两套执行后端

**后端 A** 由 `delivery.deliver_once` 实现：一次调用，要求模型返回整文件内容或 SEARCH/REPLACE 编辑，解析为 `Patch` 后写入工作区，再跑四类闸门。它需要任务配方给出目标文件；不给目标文件时，模型容易凭空猜结构（实验 11/25/1 第 6 次）。

**后端 B** 由 `MiniSweRuntime` 实现：模型在仓库里执行 bash 命令、读文件、输出 `edit:` 块，循环直到提交哨兵或预算耗尽。工作区快照与差异由 `workspace.py` 负责；本地环境 `LocalEnvironment` 负责执行命令与超时。B 不依赖“告知目标文件”，它自己 grep（实验 11/25/2）。

SEARCH/REPLACE 是两套后端共用的编辑格式：只给要替换的几行，不重写整份文件。11/25/1 的失败序列说明，编辑格式是瓶颈而不是循环——整文件重写在 1000 行文件上会截断或陷入只读循环，换成片段替换后一次通过。

### 5.7 适配器与降级

`OpenAICompatAdapter` 把不同供应商的差异收进一个薄层：统一请求封套、超时、重试、错误分类与响应摘要。能力表在启动前实测并落盘，记录是否支持 `json_schema`、`tools`、`seed`、上下文上限与固定 temperature。

不支持严格 JSON Schema 时降级为 `json_object`，只接受固定 temperature 时强制取值，推理模型输出预算不足时按失败计——三类情况都写入审计的 `degraded` 字段。降级不是隐藏，否则实验会把“接口差异”误读成“模型能力差异”。

### 5.8 审计

每次运行生成唯一 `run_id`，事件以 JSONL 追加写入：`run_start` 记录任务、基线提交、供应商、模型、契约摘要与能力表；`model_request` 记录座位、阶段与提示长度；`model_response` 记录 token、延迟、降级、请求与响应摘要以及原始文本；`gate_report` 记录逐项结果；`runtime_run` 记录后端 B 的轨迹、终止原因与改动；`run_end` 记录结论、轮次与预算。

审计是“可追溯”的实现，不是“可回放”的实现：原始响应已经落盘，但当前版本没有按 `run_id` 离线重跑的工具，这一点在第 7 章明确列为未完成。

### 5.9 实现中修掉的关键问题

| 问题 | 现象 | 修法 | 实验 |
|---|---|---|---|
| Windows 换行伪造 diff | 写文件经文本模式，`\n` 变 CRLF，整份文件算改动（6001 行假 diff） | 一律 `write_bytes(content.encode("utf-8"))` | 11/25/1 |
| 推理模型空正文 | `finish_reason=length`、正文为空，却不报错 | 空正文按失败计，提高预算或换模型 | 11/25/1、11/25/7 |
| 提示词路径分叉 | 单轮与协议的提案提示不同，token 不可比 | `render_propose_prompt` 唯一入口 + 逐字相同测试 | 11/25/4 |
| 超时硬编码 120s | 长补丁复核必超时，整批崩 | 提为 `request_timeout_s`，CLI 可传 | 11/25/7 |
| 适配器异常冒泡 | 一次超时打断整批实验 | 协议机捕获 `AdapterError`，记为一次失败运行 | 11/25/7 |
| 复核 `gate` 字段语义 | 模型把“问题类别”填进 gate，结论 100% 被丢弃 | 加 `category` 字段、未知 gate 降级保留 | 11/25/8、11/25/9 |

### 5.10 测试与持续集成

仓库现有 84 条离线测试，覆盖契约解析、四类闸门、精确断言、协议机、编辑格式与运行时；测试不需要 API Key。CI 在 Ubuntu 上跑 Python 3.10 与 3.11 两个矩阵，执行 `ruff check`、`extract_exact.py --check` 与 `pytest -q`。

需要说明两点局限：其一，CI 不跑真实仓库端到端，也不跑 Windows，E004 暴露的 CRLF 问题不会被 CI 抓到；其二，测试以单元与离线集成为主，没有覆盖率门槛。

### 5.11 运行方式

单用户本地运行，步骤是：安装依赖、在 `.env` 中配置供应商密钥与端点、用 `test_connection.py` 实测并生成能力表、用 `prepare_task.py` 准备任务、用 `run_once.py` 或 `run_runtime.py` 发起交付、用 `run_protocol.py` 发起多座位协议。所有运行写入 `runs/audit.jsonl`，关键数字抄录到 `experiments/` 的记录。

当前版本没有 HTTP 服务、工作台前端与安全沙箱；它是一套可运行的命令行系统与库，不是完整的 Web 工作台。

### 5.12 小结

实现层面最重要的不是代码量，而是三条约束：判定只有一处（闸门）、提示只有一处（`render_propose_prompt`）、落盘只有一种写法（`write_bytes`）。三条约束各自对应一类曾经真实发生过的错误。

## 第 6 章 实验与结果

### 6.1 实验方法

本文的实验记录以“月/日/次数”编号（如 11/25/6），成功与失败都记录；原始日志在 `runs/`（不入库），结论与关键数字抄录在 `experiments/`，每条结论附一条可复现命令。这样做的原因很实际：`runs/` 随时可能被清掉，论文里的每个数字必须有一份可查的副本。

实验使用 4 条真实仓库修复任务，全部来自 `astanin/python-tabulate`：

| 任务 | 上游 PR | 正确修复规模 |
|---|---|---|
| tabulate-366 | #366 | 1 行 |
| tabulate-386 | #386 | 4 行 |
| tabulate-410 | #410 | 删除 10 行 / 新增 4 行 |
| tabulate-362 | #362 | 1 行新增 / 7 行删除 |

任务来自公开仓库；缺陷数据集如 BugsInPy[11]、Defects4J[12] 提供了类似的“真实缺陷 + 测试”思路。主要指标为通过率（四类闸门全绿）、token、耗时、模型调用次数、修复轮次与失败闸门。对照包括：有无精确断言、后端 A/B、单轮/2 人/3 人协议。每格尽量重复 3 次；n=1 的结果一律标为“初步观察”，不写成结论。

### 6.2 任务集与单轮基线

实验 11/25/6 用后端 A、`deepseek/deepseek-chat`，对 4 条任务各跑 3 次，得到单轮基线：

| 任务 | 通过 | 平均 token | 平均耗时 | 失败闸门 |
|---|---|---|---|---|
| tabulate-366 | 3/3 | 33,607 | 2,030 ms | — |
| tabulate-386 | 3/3 | 33,891 | 1,482 ms | — |
| tabulate-410 | 2/3 | 34,221 | 2,211 ms | tests |
| tabulate-362 | 1/3 | 33,675 | 1,970 ms | tests |

合计 9/12，用时约 50 秒（实验 11/25/6）。按“3/3 易、1–2/3 中、0/3 难”的分档规则，366 与 386 属易，410 与 362 属中；**没有 0/3 的难档任务**。这个事实直接限制了第 6.6 节协作实验的解释力：没有“单轮稳定失败”的任务，就无法真正检验“协作能否救回”。

基线还给出两个反直觉的事实。其一，**token 与任务难度几乎无关**：四条任务都在 33.6k–34.2k 之间，差异小于 2%。原因是后端 A 每次都把目标文件全文放进上下文，token 由文件大小决定，是近似常数而不是变量（实验 11/25/6）。其二，**n=1 再次被推翻**：11/25/3 单跑时 #362 被记为“难档、A/B 均失败”，重复 3 次后有 1 次通过；单次运行只能算线索（实验 11/25/3、11/25/6）。

### 6.3 单轮交付：编辑格式是瓶颈

实验 11/25/1 在 #366 上连续失败 6 次，第 7 次才成立。失败序列比成功本身更有信息量：

| 次 | 后端 | 设置 | 结果 | token |
|---|---|---|---|---|
| 1 | A | 输出预算 3072/8192 | 正文为空，`finish=length` | 3,872 |
| 2 | A | 整文件重写 | 3001 行改动、`rationale=PLACEHOLDER`、pytest 退出码 4 | 1,572 |
| 3 | B | 12 步 | 只读不写，0 改动 | 19,913 |
| 4 | B | + 注入失败输出，16 步 | 仍只读不写 | 57,568 |
| 5 | B | + `write:` 动作 + 只读催办，14 步 | 仍只读不写 | 41,144 |
| 6 | A | + SEARCH/REPLACE，不给目标文件 | 片段猜错，片段不存在 | — |
| 7 | A | + SEARCH/REPLACE，给目标文件内容 | 四闸全绿，1 文件 / 1 行 | 33,529 |

由此得到三条结论（实验 11/25/1）：

1. **编辑格式是瓶颈，不是循环**。第 2–5 次失败都源于“要交出整份 1000 行文件”：后端 A 直接截断，后端 B 则不断读文件凑内容、永远凑不齐。换成 SEARCH/REPLACE 后一次通过。
2. **单轮后端需要目标文件**。第 6 次模型凭空猜结构；给了文件内容后立刻改对。“是否告知目标文件”必须作为受控变量写进方法。
3. **闸门抓到了管道 bug，不是模型 bug**。一次运行里模型改对了、测试也过了，但 diff 报 6001 行改动；原因是写文件走了 Python 文本模式，`\n` 被翻译成 CRLF，整份文件“全变了”。如果没有 diff 闸门，这次会被判为通过，而交付物是一个所有行都变过的文件。

后续三条任务验证了流水线的可复用性：#386 由后端 A 一次通过（实验 11/25/4），#410 由 A 改对 2 行、4 条测试过 3 条，被闸门判为不可交付（实验 11/25/5），#362 在 n=1 时两个后端都失败（实验 11/25/3）。

**#410 是闸门价值最直接的证据**：如果只看“测试从 4 红变 1 红”，很容易误判为“基本修好了”；四类闸门加指定测试节点，把“部分正确”精确地判成了“不可交付”（实验 11/25/5）。

### 6.4 双后端对比

实验 11/25/2 在 #366 上对比后端 A 与 B：

| 指标 | 后端 A | 后端 B |
|---|---|---|
| 结论 | 交付成立 | 交付成立 |
| 闸门 | 四类全绿，1 文件 / 1 行 | 相同 |
| 模型调用 | 1 次 | 10 次 |
| token | 33,529 | **19,340（−42%）** |
| 是否需告知目标文件 | 需要 | 不需要，自行 grep |

后端 B 用 10 步完成“定位—阅读—编辑—自测—提交”，没有再出现 11/25/1 里“只读不写”的死循环；关键差异是有了 `edit` 块。B 比 A 省 42% token，原因是 A 必须把 1000 行文件塞进上下文，而 B 每次只读几十行（实验 11/25/2）。

这条结果只适用于一道 1 行修复：B 有 10 次串行调用，实际耗时明显长于 A，但该实验没有统计墙钟时间；任务变复杂后，B 的优势可能收窄甚至反转。因此第 7 章把“多文件难任务上的 A/B 成本反转点”列为后续工作。

### 6.5 精确断言的效果

实验 11/24/1 在手写 fixture 任务上做 3 模型 × 2 条件 × 3 次对照，唯一变量是契约副本里有没有 `exact` 段：

| 模型 | 无 exact | 有 exact | 平均 token | 平均耗时 |
|---|---|---|---|---|
| `deepseek-chat` | 0/3 | **3/3** | 999 → 1,046 | 1.8s → 2.3s |
| `deepseek-v4-1-flash` | 3/3 | 3/3 | 2,207 → 2,030（−8%） | 8.3s → 6.3s |
| `kimi-k3-1-pro` | 3/3 | 3/3 | 5,513 → **2,308（−58%）** | 110.4s → **46.0s** |

合计 6/9 → 9/9；`doubao` 只有 n=1，未计入（实验 11/24/1）。三项观察：

- **救回效应成立**：`deepseek-chat` 三次全败变三次全胜，效应稳定；
- **成本效应只在一个模型上明显**：`kimi` 结果不变而 token、耗时各降约 58%，说明它原本在“猜该满足什么”；
- **天花效应**：`flash` 两条件均满分，该任务对它太简单，无法区分条件。

这项实验只有一条任务、一个难度，不能外推到其他任务；它证明的是“精确断言在这个任务上有效”，不是“精确断言普遍有效”。

### 6.6 多角色协议：一条负结果

#### 6.6.1 协议可运行

实验 11/24/2 在 fixture 上（摘掉 exact，故意制造确定性失败）跑 2 人协议：第 1 轮闸门红，把失败明细反馈给提案座位，第 2 轮转绿，10,286 token、4 次调用。复核首轮提出 2 条结论，全部因缺少证据被 R-2 丢弃；第 2 轮闸门全绿但仍有 1 条阻断结论，系统按“闸门终裁”判交付成立（实验 11/24/2）。这条运行验证了三件事：修复循环可用、证据规则在真实模型上生效、判定权没有被外包给模型。

实验 11/24/3 加裁决座位跑 3 人协议，首轮即全绿，裁决没有被触发，4,900 token、2 次调用，结论是“无法判断”（实验 11/24/3）。唯一有效的观察是：在“一次就对”的任务上，3 人协议的两轮上限是浪费；座位数应按任务难度决定，而不是一律开三方。

#### 6.6.2 在中等难度任务上没有增益

实验 11/25/6 显示 #362 的单轮基线是 1/3，于是实验 11/25/7 用 2 人协议在 #362 上跑 3 次：

| 次 | 第 1 轮 | 第 2 轮 | 结论 | token | 调用 |
|---|---|---|---|---|---|
| 1 | 红 | 红 | `escalated` | 144,881 | 4 |
| 2 | 红 | 复核返回空正文 | `rejected`（基础设施失败） | 188,266 | 5 |
| 3 | 红 | **绿** | `accepted` | 149,357 | 4 |

有效通过 1/3（第 2 次因复核模型空输出作废），与单轮基线 1/3 相同；平均 token 约 160,000，是单轮 33,675 的**约 4.8 倍**（实验 11/25/7）。更关键的是，复核每轮提出 3–5 条结论，**当时记为全部因缺少证据被丢弃**（11/25/8 复查后修正为 gate 字段语义）；它消耗了预算，却没有给提案方有效信息。

#### 6.6.3 成本改进与根因定位

实验 11/25/8 做了两处改进：第二轮不再重发整份文件，复核提示不带全文；复核结论必须给测试名或行号。结果 token 从 160,835 降到 53,055（**−67%**），但通过 0/3；样本太小，不能下“变差”的结论（实验 11/25/8）。

把丢弃原因打出来后，12 条被丢弃的结论全部是同一个原因：模型把 `gate` 理解成了“这条问题属于什么类别”，填的是 `deliverable-completeness`、`root_cause_accuracy`、`测试通过`、`最小改动与定位`，而系统定义是“这条结论对应四类闸门中的哪一个”。语义错位导致 100% 被丢弃（实验 11/25/8）。

实验 11/25/9 又做了三处修复：加 `category` 字段、给 gate 枚举示例、未知 gate 不再整条丢弃。三次运行里，gate 取值仍然是模型自创的类别名，没有一条落在 tests/lint/api/diff 上；2 人协议三次实验累计 **1/8** 有效通过，单轮基线是 1/3，没有证据显示协作有增益（实验 11/25/9）。

#### 6.6.4 对负结果的解释

这不是“协作一定无效”的证明。它成立的条件很具体：4 条同仓库任务、`deepseek-chat` 提案、`flash` 复核、2 轮、没有 0/3 难档任务；在这个设置下，2 人协议没有把“偶尔能做对”变成“稳定能做对”，成本却高了数倍。

根因有两层。表层是复核字段语义：模型不肯按系统的枚举填 gate，导致结论被丢弃；深层是角色分工：强制复核结论挂到某个闸门上，本质是让复核者当小裁判，这与“只有闸门能判定”的核心主张相矛盾。实验 11/25/9 因此把 `gate` 降级为可选，让复核彻底变成“建议者”（实验 11/25/9）。

### 6.7 失败模式

| 失败模式 | 例子 | 原因 | 闸门反应 |
|---|---|---|---|
| 写不完 | 11/25/1 第 2 次 | 整文件重写、输出截断 | tests / diff 红 |
| 改错地方 | 11/25/3 后端 A | 在异常之后补一句永远执行不到的修复 | tests 红 |
| 只读不写 | 11/25/3 后端 B | 12 步都在 grep，未输出 edit 块 | tests 红 + 空文件算改动 |
| 空正文 | 11/25/1、11/25/7 | 推理吃光输出预算 | 按失败计 |
| 假 diff | 11/25/1 | CRLF 让整份文件“全变了” | diff 红（抓到管道 bug） |
| 部分正确 | 11/25/5 | 4 条测试过 3 条 | tests 红，判不可交付 |
| 字段语义错位 | 11/25/8、11/25/9 | 复核把类别填进 gate | 结论被丢弃，协议空转 |

失败模式比通过率更有信息量：它标出了系统在哪种条件下失效。尤其是“部分正确”和“假 diff”两类，前者说明闸门能防止“基本修好了”的误判，后者说明闸门不仅判模型，也判管道。

### 6.8 方法学教训

1. **n=1 会骗人**：11/24/1 首轮得出“四组结果完全相关”，n=3 后不成立；11/25/3 单跑把 #362 记为“难档”，11/25/6 重复 3 次后变成 1/3。
2. **单任务会饱和**：11/24/1 里两个模型两条件都满分，条件差异被天花板吞掉。
3. **提示词路径不同就不可比**：11/24/2 与 11/24/3 的提案提示不同，token 不能直接比；11/25/4 统一为 `render_propose_prompt` 后才成立。
4. **Windows 换行会伪造 diff**：写文件若经文本模式，CRLF 会让整份文件算改动；一律 `write_bytes`。
5. **推理模型会吃光输出预算**：正文为空、`finish_reason=length`，不报错但也没答案；必须按失败计。
6. **字段语义是接口的一部分**：同一份提示，模型对 `gate` 的理解可能与设计者完全不同；枚举、示例、降级三件事缺一不可。

### 6.9 有效性威胁

- **任务分布**：4 条任务全部来自 tabulate 一个仓库，模型可能熟悉该仓库；结论不能外推到其他仓库或跨文件任务。
- **模型覆盖**：单轮主要用 `deepseek-chat`，复核用 `flash`；`kimi` 作复核时三次空正文，`doubao` 只有 n=1。
- **重复次数**：除 11/24/1 与 11/25/6 外，多数格子是 n=1 或 n=3，1/3 与 2/3 的差别可能只是抖动。
- **难度分布**：没有 0/3 的难档任务，协作实验只能测“偶尔能做对”的任务，不能回答“协作能否救回稳定失败”。
- **基础设施失败**：空正文、超时导致有效样本减少，11/25/7 的 1/3 已排除一次基础设施失败。
- **成本口径**：11/25/2 没有统计墙钟时间；11/25/6 的 token 是后端 A 的常数成本，不代表后端 B。
- **任务集与提示词在实验期间仍在变**：11/25/4 统一提示词、11/25/8 改复核规则，跨实验比较必须看清这些变更。

### 6.10 小结

本章的证据可以概括为四句话：

1. **契约与闸门可行**：4 条任务中 2 条由后端 A 交付成立，1 条“部分正确”被精确拒绝，1 条在 n=1 时两个后端都失败（实验 11/25/1、11/25/4、11/25/5、11/25/3）。
2. **编辑格式是单轮交付的关键**：SEARCH/REPLACE 解决了“写不完”，但没有解决“改错地方”（实验 11/25/1、11/25/3）。
3. **双后端各有代价**：后端 B 在一次任务上省 42% token，但调用次数多、更慢；后端 A 的成本近似常数，由文件大小决定（实验 11/25/2、11/25/6）。
4. **多角色协作没有跑出增益**：2 人协议累计 1/8，成本约 4.8 倍；根因是复核字段语义与角色分工，而不是“模型不够聪明”这一句空话（实验 11/25/7、11/25/8、11/25/9）。

## 第 7 章 总结与展望

### 7.1 工作总结

本文围绕“生成便宜、判定昂贵”这一瓶颈，设计并实现了一个以可执行验收契约为唯一判定依据的多角色代码交付系统。系统把判定从人眼移到契约：契约在动手前由人确认，模型只负责产出，四类闸门负责判定，审计负责追溯。

主要工作包括：契约 DSL 与严格校验、四类闸门、精确断言的 AST 提取与漂移检查、三座位协议机、两套执行后端、SEARCH/REPLACE 编辑格式、多供应商适配与 JSONL 审计。系统以 Python 实现，仓库现有约 4,000 行源码与 84 条离线测试，并在 4 条真实仓库任务上运行。

### 7.2 主要结论

1. **契约作为唯一裁判是可行的**。在 #366、#386 上，后端 A 最终交付成立（#366 经 7 次尝试）；在 #410 上，闸门把“4 条测试过 3 条”精确判为不可交付。判定不依赖模型自评，而依赖可执行检查。
2. **精确断言能改变模型行为，但证据范围有限**。在手写 fixture 上，它使一个模型 0/3→3/3，使另一个模型 token 降 58%；只有一条任务，不能外推。
3. **编辑格式与上下文策略决定单轮成败**。整文件重写会截断或陷入只读循环；SEARCH/REPLACE 加目标文件能一次通过；后端 B 用 `edit` 块后收敛，并在一次任务上省 42% token。
4. **多角色协作在当前设置下没有增益**。2 人协议累计 1/8，与单轮 1/3 相比没有改善，成本约 4.8 倍；改进上下文后 token 降到 53,055（实验 11/25/8），但通过率仍为 0/3。根因是复核字段语义与角色分工，不是协议机本身不能运行。
5. **失败必须被记录，负结果也是结论**。本文的 12 份实验记录里，失败与成功同等重要；它们标出了方法的边界：没有 0/3 难档任务时，协作实验回答不了“能否救回”。

### 7.3 局限

- 任务集只有 4 条，全部来自一个仓库，未做跨仓库、多文件、重构类任务；
- 单轮主要测一个模型，复核主要测一个模型，模型覆盖不足；
- 多数格子 n=1 或 n=3，没有统计显著性；
- 没有 0/3 难档任务，协作实验的解释力受限；
- 系统没有 HTTP 服务、工作台前端、安全沙箱与回放工具；当前是命令行系统与库；
- 后端 A/B 的成本对比只有一道任务，且缺少墙钟时间；
- 精确断言的对照实验只有一条 fixture 任务。

### 7.4 后续工作

1. **任务集扩到 20 条并跨仓库**：按单轮通过率分层，重点补 0/3 难档；只有存在稳定失败，才能检验“协作能否救回”。
2. **把复核改成建议者**：`gate` 改为可选，新增 `category`；复核只提可疑之处与证据，不参与阻断；用对照实验看建议是否改善下一轮提案。
3. **补回放**：把已落盘的模型响应做成离线回放层，使同一实验不依赖网络与账号；这是“可复现”从审计走向重放的关键一步。
4. **补系统外壳**：HTTP 服务与三视图界面（任务、运行审查、报告）；前端界面列为后续工作。
5. **补安全边界**：容器化执行、断网、只读挂载、CPU/内存限额；当前 `LocalEnvironment` 只是受限执行环境，不是沙箱。
6. **补成本模型**：把后端 A 的常数成本与后端 B 的可变成本做成选择策略，按任务规模选后端。

### 7.5 结语

本文最重要的结论不是“系统能跑”，而是“判定可以被契约接管，而协作的收益必须被证明”。在 4 条真实任务上，契约与闸门站住了；多角色协作没有站住。把这条负结果写出来，比把它藏起来更有价值：它告诉后续工作，应该先去找真正难的任务，而不是继续调提示词。

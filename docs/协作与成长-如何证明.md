# 协作能力与成长能力：怎么定义、怎么证明

> 两个卖点本身没问题，问题在"说法"。凡是不能用数字回答的主张，答辩时都会被问穿。
> 本文把两句话翻译成可测量的指标、可执行的实验、和必须守住的边界。

---

## 0. 一条必须先划的边界

**成长的上限是契约。系统可以越来越会干活，但不能自己改验收标准。**

理由不是保守，而是自洽性：如果系统能改写"什么算干完"，闸门就从客观裁判退化成自证，整个系统的立论当场崩塌。

所以：

| 允许成长 | 禁止成长 |
|---|---|
| 怎么拆任务 | 契约里写什么算通过 |
| 用哪个模型坐哪个座位 | 测试命令与阈值 |
| 改哪几个文件、怎么改 | 允许改哪些路径（forbid） |
| 从历史失败里学到教训 | 自动放宽 `max_lines` 让自己过 |

这条边界写进论文，是**设计原则**，不是限制；它同时也是答辩时"你这不是自说自话吗"的最强防御。

## 1. 协作能力：三个数字，缺一不可

只说"通过率更高"没用——简单任务单模型也能过，会把差异稀释掉。三个指标必须一起报：

### ① 协作增益率（Collaboration Gain）

```
CG = |单模型失败 ∩ 协作通过| / |单模型失败|
```

分母只算单模型翻车的任务。这个数字才回答"协作到底救回了什么"。
如果单模型失败 20 条、协作救回 6 条 → CG = 30%。

### ② 协作代价比（Cost Ratio）

```
CR = 协作 token 总消耗 / 单模型 token 总消耗
```

必须与 CG 同表。只报"通过率高"不报"贵了几倍"，是耍流氓，老师一眼看穿。

目标形态：**CG 高、CR 低**。CG 20% 但 CR 3.0 就不划算，要如实说。

### ③ 边际贡献（Marginal Contribution）

```
MC(座位) = 全配置通过率 − 去掉该座位的通过率
```

分别去掉提案、复核、裁决，各测一次。

这个指标防的是最致命的质疑：**"你那个第三方是不是摆设？"**
如果去掉裁决后通过率不降，说明裁决座位没价值——那就该砍掉，而不是硬留。

## 2. 成长能力：一个定义，三层机制

### 2.1 定义

> 成长 = 系统把过去的运行结果沉淀为可用资产，使**后续同类任务**的表现发生变化（更好或更省）。

注意"同类任务"四个字：不要求跨领域迁移，只要求在同类任务上变好。这是本科能做出的范围，也是能证明的范围。

### 2.2 三层机制（按性价比排序，只做前两层）

| 层 | 做什么 | 依赖 | 工时 | 是否必做 |
|---|---|---|---|---|
| **L1 记忆** | 从审计日志提炼经验，检索相似案例注入提案上下文 | 已有 `audit.jsonl` | 12h | 必做 |
| **L2 策略** | 按历史统计决定"这个任务该开 2 人还是 3 人" | L1 + 已有运行数据 | 10h | 必做 |
| **L3 画像** | 记录用户改契约的习惯，下次预填草案 | 契约确认界面 | 20h | 可选，时间紧就砍 |

**L2 是关键**：它让"成长"直接改善"协作"，两个卖点合成一个闭环——

> 协作产生更多可比较的运行（多视角、多轮尝试），成长消费这些数据；
> 成长反过来让协作更省（学会哪种任务不必开三方）。

这句话就是你论文摘要里最有分量的一句。

### 2.3 记忆的最小数据结构

```python
@dataclass(frozen=True)
class Episode:
    run_id: str
    signature: str          # 任务指纹：契约字段 + 语言 + 文件数 + 失败闸门
    protocol: str           # 2p.single / 3p.single
    seats: dict             # 谁坐了哪个座位
    outcome: str            # accepted / escalated / rejected
    rounds: int
    tokens: int
    gate_failures: tuple[str, ...]   # 哪几个闸门红过
    lesson: str             # 一句话教训（规则生成，不是模型自由发挥）
```

检索用**规则指纹 + Jaccard**，不引入向量库/embedding：

- 不新增依赖（答辩机器装不上库的风险归零）
- 可解释（能说清"为什么认为这两条任务相似"）
- 样本几十条时，向量检索的收益本来就不显著

### 2.4 注入什么：教训，不是答案

> **只注入"教训"，不注入"完整成功补丁"。**

如果注入完整补丁，模型会抄；在留出任务集上立刻原形毕露，而且你也失去了"泛化"这个卖点。

注入格式（放进提案提示词的历史区块）：

```
## 同类任务的历史经验（仅供参考，不是规则）
1. [失败] 把 value 按 '#' 切分 → URL 里的 # 被截断，测试未覆盖
   教训：行内注释只认「空白 + #」，不要按 # 直接切
2. [成功, 1 轮] 同类任务：先校验 '=' 再加明确异常消息，改动 4 行通过
```

## 3. 方法学红线：不能用"同一题跑两次"证明成长

这是本节最重要的一条。同一题跑两次，第二次变好只说明**它记住了这道题**，不是成长。答辩时被问到这一点，全盘皆输。

正确做法：

```
任务集 A（10 条）── 跑一遍，积累经验 ──▶ 记忆库
任务集 B（10 条，同类但不同题）── 只在 B 上测 ──▶ 学习曲线
```

三条纪律：

1. **B 集不参与任何调参**，包括提示词调优。它从建好那天起就封存。
2. **B 集任务不得出现在 A 集**，签名不同、文件名不同、缺陷不同。
3. **消融必须有对照组**：同一批 B 集任务，跑两次——一次关闭记忆检索，一次开启。差值才是成长的贡献。

## 5. 成本与从哪砍

新增工时：**L1 12h + L2 10h + 实验 8h ≈ 30h**。

从这三处腾出来：

| 砍掉 | 省 | 影响 |
|---|---|---|
| `3p.dual` 只做演示、不进实验 | 15h | 少一组数据，但双轨本来就是"对称投票"的对照，砍了不影响主线 |
| 协作接口只保留 2 人协议 | 12h | 它本来就是保底，不做卖点 |
| 联调期从 30h 压到 22h | 8h | 风险项，靠"主干永远可运行"的纪律对冲 |

**绝对不要做的三件事**：

1. 不要微调模型（成本高、周期长、且不是软件工程贡献）；
2. 不要上 embedding / 向量库（多一个依赖，几十条样本收益不明确）；
3. 不要让系统自动改契约（见第 0 节，会让闸门失效）。

### 插进排期

## 6. 答辩问答预案

**Q：你怎么证明"越来越贴合使用者"？**
A：在 10 条从未参与调参的留出任务上，对比"开记忆/关记忆"两组：首次通过率从 X% 到 Y%，平均修复轮次从 A 到 B，token 从 C 到 D。学习曲线在第 N 次运行后趋于平稳，说明收敛而非过拟合。

**Q：这会不会是它记住了题目？**
A：留出集 B 的 10 条任务从未出现在记忆库里，任务签名与 A 集无交集（附签名清单）。且注入的是教训文本，不是完整补丁。

**Q：三个模型的协作是不是摆样子？**
A：边际贡献实验：去掉裁决座位后通过率下降 P 个百分点，去掉复核座位下降 Q 个百分点。同时代价比 CR 为 R 倍——我们在论文里明确写了它在什么条件下不划算。

**Q：系统会不会为了通过而改验收标准？**
A：架构上不允许。契约只能由人确认和修改，系统的写权限止于代码文件；`diff.forbid` 会拦下任何触碰测试的补丁。这是设计原则，见第 4 章。

**Q：成长和协作是两件事，为什么要放一个系统里？**
A：因为数据流是单向闭合的：协作产生多视角运行数据，成长消费这些数据做组队决策，组队决策又降低下一次协作的成本。这是"越用越省"而不是"越用越强"——后者我们不敢承诺。

最后这句要记住：**"越用越省"是能证明的，"越用越聪明"是吹的。** 论文里只说前者。

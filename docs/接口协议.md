# 接口协议规格书 v0.1

> 范围：P0 底层三方协议（Codex / Kimi / DeepSeek），P1 三个分内接口（写作 / 审计 / 协作），
> P2 两种协议形态（2 人 / 3 人）。实现见 `src/dbw/protocol/`。

---

## 0. 设计立场：座位固定，人数可变

**接口数量不等于流程数量。** 如果每个接口都手写 2 人与 3 人两套流程，会得到 3 × 2 = 6 条互不相同的实现路径，既没有时间测试，也无法解释"3 人为什么更好"。

本规格把两者拆开：

| 概念 | 是否随规模变化 | 说明 |
|---|---|---|
| **座位（Seat）** | 不变化，恒为 3 个 | 提案 / 复核 / 裁决，永远是这三个职责 |
| **模型数量** | 2 或 3 | 只决定"一个模型能不能兼两个座位" |
| **流程（状态机）** | 不变化 | 提案 → 复核 → 裁决 → 闸门，一份代码 |

于是 2 人协议和 3 人协议是**同一台状态机的两种排班**：

| 协议编号 | 排班 | 谁负责消解分歧 |
|---|---|---|
| `2p.single` | 提案 + 复核 | **只能交给闸门**（无第三方） |
| `3p.single` | 提案 + 复核 + 裁决 | 裁决在模型层消解一部分，闸门终裁 |
| `3p.dual` | 双提案 + 裁决 + 复核 | 裁决先选提案，闸门终裁 |

**铁律（贯穿全部协议）：只有闸门能宣布交付成立。**
复核说有问题而闸门全绿 → 交付成立（模型误报）；复核说没问题而闸门红 → 交付不成立（模型漏报）。
模型之间可以争论，但不能投票决定"合不合格"。

## 1. P0 底层三方协议

与供应商无关的调用契约。**这一层不做编排、不做业务判断、不含提示词。**

### 1.1 能力协商

启动时必须知道每家支持什么，不允许靠猜。

| 能力 | 含义 | 不满足时的处理 |
|---|---|---|
| `supports_tools` | 原生函数调用 | 无降级，报 `CapabilityError` |
| `supports_json_schema` | 结构化输出（严格模式） | 降级为 `json_object` + 提示词约束，**登记 degraded** |
| `supports_json_object` | 仅保证是合法 JSON | 降级为纯文本 + 本地解析，**登记 degraded** |
| `supports_seed` | 可复现采样 | 忽略 seed，**登记 degraded** |
| `max_context` | 上下文上限 | 超限直接失败，不自动截断（截断会悄悄改变语义） |

默认能力表（`KNOWN_CAPABILITIES`，**必须实测**后写死，不得沿用厂商宣传）：

```
deepseek  tools✓  json_schema✗  seed✓(接受，未验确定性)  context 64k
kimi      tools✓  json_schema✗  seed✗                 context 128k
codex     tools✓  json_schema✓  seed✓                 context 200k
```

> **实测记录（2026-11-23，deepseek-chat）**：`response_format=json_schema` 返回
> `HTTP 400: This response_format type is unavailable now`；`json_object`、`tools`、`seed` 均被接受。
> 因此 DeepSeek 的每一次结构化输出都走 `json_object` 降级，审计里 `degraded=true` 必然出现。
> **这条直接影响实验结论**：DeepSeek 与 Codex 的结构化输出严格性不同，混合对比时必须分组。

> **实测记录（2026-11-24，火山方舟）**：`GET /api/v3/models` 可直接列出账号内模型及其能力元数据
> （`features.structured_outputs`、`features.tools`），不必猜模型名。三个模型的 `json_schema` /
> `tools` / `seed` 全部支持。但 `kimi-k3-1-pro` 返回
> `HTTP 400: temperature only 1 is allowed for this model` —— 这是**参数取值域**限制，不是能力缺失。
>
> 因此能力协商必须覆盖三类情况，缺一不可：
>
> | 情况 | 例子 | 处理 |
> |---|---|---|
> | 能力缺失 | DeepSeek 无 `json_schema` | 降级并登记 |
> | 参数取值域受限 | Kimi 只接受 `temperature=1` | 强制取值并登记（`fixed_temperature`） |
> | 输出预算被推理吃掉 | 推理模型 `max_tokens` 过小时 `content` 为空但 `finish_reason=length` | 提高预算或显式报错，不得当作空输出放过 |

> **R-P0-1**：能力表必须落盘成文件，且能手工覆盖。厂商改接口时改配置，不改代码。

### 1.2 请求封套

```json
{
  "messages": [{"role": "system", "content": "..."}, {"role": "user", "content": "..."}],
  "response_schema": {"type": "object", "..." : "..."},
  "tools": [],
  "max_tokens": 4096,
  "temperature": 0.2,
  "seed": null,
  "timeout_s": 120,
  "idempotency_key": "run-7f3a:proposer:propose:1"
}
```

> **R-P0-2**：`idempotency_key` 每次调用必填，格式 `run_id:seat:phase:seq`。它同时是回放键：同键必返回同一条录制响应。

### 1.3 响应封套

```json
{
  "model": "deepseek-chat",
  "text": "{\"files\": {...}}",
  "tool_calls": [],
  "finish_reason": "stop",
  "usage": {"prompt": 1200, "completion": 300, "cached": 800, "total": 1500},
  "latency_ms": 2400,
  "degraded": false,
  "degraded_reason": "",
  "request_digest": "sha256(请求体)",
  "raw_digest": "sha256(响应体)"
}
```

> **R-P0-3**：`usage` 与两个 digest 必填。没有 digest 的调用视为不可审计，不得进入实验数据。

### 1.4 方言归一化

三家都会在 JSON 前后加解释文字，Kimi 常包 ```json 围栏。统一由本地解析器处理，**绝不猜**：

解析顺序：围栏内 → 首个 `{` 到末个 `}` → 全文。
全部失败则抛 `PayloadError`，由协议机带着错误信息重试一次（第 2 次仍失败即判定该座位输出不合法）。

> **R-P0-4**：禁止用正则"修补"模型输出（例如把单引号改双引号）。修补会让错误数据看起来合法。

### 1.5 错误分类

| 类别 | HTTP / 场景 | 是否重试 | 编排层动作 |
|---|---|---|---|
| `TransientError` | 408 / 429 / 5xx / 超时 | 是，指数退避最多 3 次 | 重试耗尽后降级或终止 |
| `PermanentError` | 400 / 401 / 403 / 404 / 422 | 否 | 立即失败，记录并终止该座位 |
| `CapabilityError` | 请求了不支持的能力且无法降级 | 否 | 换供应商或终止 |
| `BudgetExceeded` | token / 调用数 / 耗时超限 | — | **正常终止**，保留已有证据 |

> **R-P0-5**：`BudgetExceeded` 不是异常事故，是协议的正常出口（`outcome=budget_exhausted`）。

### 1.6 降级登记

> **R-P0-6**：任何降级必须写入审计（`degraded=true` + 原因）。否则"三家模型对比"里混入了不同规格的输出，实验数据即为假。

典型必须登记的降级：
- Kimi 走 `json_object` 而非 `json_schema`（严格性下降）
- 忽略 `seed`（不可复现）
- 复核输出退回纯文本解析

### 1.7 回放

> **R-P0-7**：正式实验的每一次调用，其响应必须落盘为 fixture（按 `idempotency_key` 索引），此后可用回放适配器完全离线重跑同一实验。

这是答辩稳定性的保障，也是"可复现性"章节的实现基础：断网、欠费、模型下线都不影响演示。

### 1.8 可插拔

> **R-P0-8**：新增供应商只需实现 `capabilities()` 与 `complete()` 并注册，编排层代码零改动。

验证方式：答辩时现场注册第四家，跑同一任务，观察协议行为不变。

## 2. P1 三个分内接口

**"分内协议"的定义 = 输出模式 + 不变量 + 禁止事项。**
不是流程——流程统一在 P2。接口只回答一件事：这份输出合法吗？

### 2.1 写作接口（authoring）

| 项 | 内容 |
|---|---|
| 输入 | 任务描述、契约（doD 全文）、失败闸门明细 |
| 输出 | `{"files": {"相对路径": "完整文件内容"}, "rationale": "..."}` |
| 闸门 | 代码闸门（tests / lint / api / diff） |

不变量：

- **A-1** `files` 非空，值为**完整文件内容**，不是补丁片段（MVP 取舍，见 §6）；
- **A-2** 路径必须是仓库内相对路径，禁止绝对路径与 `..`；
- **A-3** 触碰契约 `diff.forbid` 路径的提案直接丢弃，不进闸门（早失败省一次沙箱运行）；
- **A-4** `rationale` 非空——说不出为什么改，就不该改；
- **A-5** 文件数不得超过 `diff.max_files`。

禁止：输出解释性散文、修改测试、批量重写无关文件。

### 2.2 审计接口（review）

| 项 | 内容 |
|---|---|
| 输入 | 任务、契约、待审交付物（补丁 / 任务图 / 结论清单） |
| 输出 | `{"findings": [{"fid","severity","gate","claim","evidence","remedy"}]}` |
| 闸门 | 验真后的结论闸门 |

不变量：

- **R-1** `gate` 必须属于 `{tests, lint, api, diff}`——只准对准契约项，不准对"风格"；
- **R-2** `evidence` 必填，空证据的结论**直接丢弃**并计数（防编造问题）；
- **R-3** `severity` 只能是 `BLOCKER / MAJOR / MINOR`，只有 `BLOCKER` 可阻断；
- **R-4** `fid` 唯一；
- **R-5** 找不到问题时输出 `{"findings": []}`，禁止为显得有用而编造；
- **R-6** 审计接口作为工作负载时（`3p` 审计），复核座位输出的是**裁决**而非新结论——审计自身也要多模型验真。

禁止：给重构建议、评价架构、报告契约之外的问题。

### 2.3 协作接口（collab）

| 项 | 内容 |
|---|---|
| 输入 | 任务、契约 |
| 输出 | `{"nodes": [{"id","goal","dod":[...],"depends_on":[...]}]}` |
| 闸门 | 任务图闸门（`dag_gate`：无环 / 无悬空依赖 / 每节点有验收命令） |

不变量：

- **C-1** 节点 id 唯一；
- **C-2** 每节点至少一条**可执行**的 `dod`（如 `pytest tests/x.py::test_y`）；
- **C-3** `depends_on` 只能引用本图节点；
- **C-4** 必须是 DAG；分解方案本身也要过闸门，与代码交付共用同一判定机制。

禁止：写实现代码、给出无法执行的验收描述（"确保质量"这类）。

## 3. P2 两种协议

### 3.1 统一时序

```
            ┌──────────────────────────────────────────┐
            │ 每轮（attempt = 1..repair_rounds+1）       │
            └──────────────────────────────────────────┘
   P1 提案 ──► P2 复核 ──► [P2.5 裁决] ──► P3 闸门 ──► 全绿?
      ▲                                        │           │
      │                                        │ 红        是
      └──────────── 反馈：未通过闸门 + 阻断结论 ─┘           ▼
                                                     ACCEPTED
```

终止条件（四出口之一）：

| 出口 | 触发 |
|---|---|
| `accepted` | 闸门全绿 |
| `escalated` | 轮次用尽，或连续 `no_improvement_limit` 轮闸门签名不变（防无效消耗） |
| `rejected` | 输出连续不合法（结构错误 / 违反不变量） |
| `budget_exhausted` | 调用数 / token / 耗时超预算 |

**闸门签名** = 各闸门 `名字:通过与否` 的连接串。签名不变即"改了半天没变化"，提前收手。

### 3.2 两人协议（`2p.single`）

| 座位 | 职责 |
|---|---|
| 提案（A） | 产出交付物 |
| 复核（B） | 找契约违反，附证据 |

时序：

```
P1  A 产出提案
P2  B 复核 → findings
P3  闸门判定（findings 不参与判定，只作为下一轮反馈）
P4  红 → 把「未通过闸门」+「阻断结论」喂回 A，回到 P1
```

**结构性缺陷（必须写进论文）**：2 人协议没有第三方，"复核误报"只能靠闸门解除——但闸门只判合格与否，不告诉系统"这条结论是错的"。所以 2 人协议容易在误报上浪费轮次。

这恰恰说明：**2 人协议的价值不在质量，而在成本**；3 人协议的价值不在"更多意见"，而在**能把误报挡在轮次之外**。

### 3.3 三人协议 · 单轨（`3p.single`）

| 座位 | 职责 |
|---|---|
| 提案（A） | 产出交付物 |
| 复核（B） | 找契约违反，附证据 |
| 裁决（C） | **只裁"结论是否成立"**，不裁"代码好不好" |

时序：

```
P1  A 产出提案
P2  B 复核 → findings
P2.5 C 逐条裁决：upheld / rejected / insufficient
P3  闸门判定（仍然与裁决无关）
P4  红 → 反馈（含被 upheld 的阻断结论），回到 P1
```

裁决边界（**R-A-1**，违反即协议失效）：

- 裁决者**不得新增结论**——否则它变成第二个复核座位，成本翻倍而信息量为零；
- 裁决者**不得评判代码质量**——否则它变成第二个裁判，与闸门冲突；
- `insufficient` 按不成立处理，但必须说明缺什么证据。

### 3.4 三人协议 · 双轨（`3p.dual`）

用于高风险任务（改动跨模块、契约项多）。两个提案者**独立**产出，裁决者按契约选一个：

```
P1a  A 产出提案甲
P1b  A' 产出提案乙（提示词明确要求独立，不与甲协商）
P1c  C 二选一（choice = 0/1，须给理由）
P2   B 复核被选中的那个
P2.5 C 裁决阻断结论
P3   闸门
```

用途：这是"对称投票"的**受控形态**，成本 ×2，只在小样本对照实验中使用（第 6 章消融：单轨 vs 双轨）。

> **R-P2-1**：双轨必须记录 `proposal_count=2`，且两个提案的 `request_digest` 必须不同——否则说明提示词没让模型真正独立，实验无效。

### 3.5 座位分配矩阵

| 接口 | 2 人 | 3 人（单轨） | 3 人（双轨） |
|---|---|---|---|
| 写作 | 实现者 + 审计者 | + 裁决者 | 双实现者 + 裁决 + 审计 |
| 审计 | 审计者A 出问题 + 审计者B 验真 | + 裁决者 | 双审计者 + 裁决 |
| 协作 | 规划者 + 挑漏者 | + 裁决者 | 双规划者 + 裁决 |

**同一模型兼两个座位是允许的，但必须标注 `self_played=true`。**

> **R-P2-2**：`self_played=true` 的运行不得与不同模型的运行混在同一张表里比较。这是实验数据可信度的底线。

### 3.6 座位与模型的解耦

配置示例（`seats.yaml`，W2 落地）：

```yaml
authoring:
  two_party:
    proposer: deepseek
    reviewer: kimi
  three_party:
    proposer: deepseek
    reviewer: kimi
    arbiter: codex
  three_party_dual:
    proposer: deepseek
    proposer_b: codex
    reviewer: kimi
    arbiter: codex
```

> 这是"每部分最少 2 个模型、最多 3 个模型"的落地形式：**同一接口配三份排班，协议机只认排班，不认厂商**。

## 4. 审计：协议产生的每条记录

每次运行写入 `runs/audit.jsonl`，事件类型：

| 事件 | 关键字段 |
|---|---|
| `run_start` | `run_id, task, seats, interface, contract_hash` |
| `model_request` | `seat, provider, phase, prompt_chars` |
| `model_response` | `model, usage, latency_ms, degraded, request_digest, raw_digest, raw_text` |
| `gate_report` | `attempt, report（逐项结果）, signature` |
| `run_end` | `outcome, reason, budget, rounds` |

论文第 6 章任何数字都应能在此表中定位到具体一行。

## 5. 可测性

> **R-T-1**：协议行为必须能用假适配器完整测试，不依赖任何 API Key。

已实现（`tests/test_protocol.py`，23 条）：

| 用例 | 验证的协议条款 |
|---|---|
| 2 人协议放行 | A-1..A-5 + 闸门终裁 |
| 2 人协议停滞终止 | 签名不变 → escalated |
| 裁决驳回误报 | R-A-1（裁决不新增结论） |
| 裁决维持阻断 | 阻断生效 |
| 双轨选提案 | R-P2-1 |
| 无证据结论丢弃 | R-2 |
| 审计接口自我验真 | R-6 |
| 任务图有环被拦 | C-4 |
| JSON 围栏解析 | R-P0-4 |
| 预算耗尽 | R-P0-5 |
| 同模型兼角标注 | R-P2-2 |
| 改测试被前置拦截 | A-3 |

## 6. 已知取舍与风险

| 取舍 | 后果 | 计划 |
|---|---|---|
| 写作输出"整文件内容"而非 unified diff | 大文件时 token 成本高、易越界 | 第 7 章展望：改为 search/replace 块格式 |
| 未实现流式 | 长响应期间无进度 | 非目标，界面用轮询 |
| 只支持 Python + pytest | 适用范围窄 | 非目标，契约 DSL 本身语言无关 |
| 裁决者与复核者可能同模型 | 裁决失去独立性 | 用 `self_played` 标注，实验中单列一组 |
| 2 人协议无第三方消解误报 | 可能浪费轮次 | 这正是 2p vs 3p 对比实验要量化的东西 |

**最大的设计风险**：3 人协议的成本是 2 人协议的 1.5–2 倍，而收益（减少误报浪费的轮次）只有在误报率高的任务上才显现。**如果实验发现 3p 在多数任务上不如 2p，那不是失败，那是结论**——写清楚它在什么条件下成立，比硬说"三方更好"有价值得多。

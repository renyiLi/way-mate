# 任务集：选题与挖掘标准

> 目标：20 条真实仓库的修复任务，按难度分层，能区分"有无精确断言""单轮 vs 多轮"。
> 原则：**先能用，再谈好坏。**一个跑不起来的题目，对实验的价值是零。

---

## 一、为什么必须从真实仓库挖

我们目前唯一那条任务，是在 `fixtures/repo_a` 里手写的 `parser.py`。它有 5 条测试、1 个缺陷，干净得像教科书。

代价已经显现：**三个模型里有两个两条件都满分（天花效应）**。任务太简单，条件之间就没有差异可测。

真实仓库的 value 不在"难"，在三点：

1. **真缺陷**：是被人报告、被人修过的，不是编出来的；
2. **真测试**：仓库自带测试套件，验收标准是现成的；
3. **真规模**：文件多、耦合深，模型必须先定位再修改——这正是我们要测的能力。

---

## 二、实测：环境是第一道坎（不是 issue 质量）

2026-11-24 抽查三个"零运行时依赖"的候选，用同一个干净 venv 直接 `git clone` + `pytest`：

| 仓库 | stars | 结果 | 卡在哪 |
|---|---|---|---|
| `astanin/python-tabulate` | 2.6k | ✅ 323 passed，3.2s | 无 |
| `r1chardj0n3s/parse` | 1.8k | ❌ 启动失败 | 仓库自己的 `pyproject.toml` 写了 `addopts = --cov=...`，缺 `pytest-cov` |
| `python-humanize/humanize` | 0.8k | ❌ 13 个收集错误 | 需 `pip install -e .` 由 setuptools-scm 生成 `_version.py` |

**1/3 的通过率。** 也就是说：要凑 20 条任务，候选池至少要有 40–60 个仓库。

而且注意 `parse` 的失败方式和我们在 `fixtures/repo_a` 里踩过的一模一样——**仓库继承了自己的 pytest 配置**。这类问题只能实测发现，看 README 看不出来。

## 三、五条筛选标准（按顺序执行，任何一条不过就换）

| # | 标准 | 怎么验 | 不通过就换 |
|---|---|---|---|
| 1 | **15 分钟内能跑起来** | 干净 venv + `pip install -e .` + `pytest`，全绿 | 换 |
| 2 | **测试套件 < 60 秒** | 计时 | 换（实验要跑几十次） |
| 3 | **有已合并的 bug 修复 PR**，且该 PR 同时改了源码和测试 | 见第四节 | 换 |
| 4 | **改动规模适中**：1–5 个文件，10–150 行 | 看 PR 的 `additions+deletions` | 太大换小，太小换大 |
| 5 | **不依赖网络与外部服务** | 测完看有没有 socket / DB 需求 | 换 |

第 5 条经常被忽略：有些仓库的测试会连外部 API，跑一次失败一次，而且不可复现。

## 四、从一个 PR 到一条任务：五步

以某仓库第 123 号 PR 为例（它修了 issue #120，并新增了测试）：

```
1. 定位    找到 issue #120 + 合并的 PR #123
2. 基线    取 PR #123 的父提交 parent_sha → 克隆到该提交
3. 验证    parent_sha 上跑测试：目标测试必须"红"（复现缺陷）
4. 反转    应用 PR 的测试改动 → 测试变绿，但源码未改 → 说明测试确实覆盖了缺陷
5. 定契约  源码留旧版，测试留新版 → 这就是一条任务
```

第 4 步是关键校验：**如果只应用测试改动就能让测试变绿，说明那条测试没测到缺陷**，该 PR 不能用。

### 契约怎么自动生成（省掉 80% 手写）

SWE-bench 格式的 PR 数据结构，和我们的契约字段几乎一一对应：

| PR 里的东西 | 映射到契约 |
|---|---|
| 测试文件改动的路径 | `diff.forbid` 追加 `tests/` |
| `FAIL_TO_PASS` 测试节点列表 | `doD.tests` 的 pytest 命令 |
| PR 的 `additions + deletions` | `diff.max_lines = 改动量 × 1.5` |
| PR 改动的文件数 | `diff.max_files = 改动量 × 1.5` |
| 新增测试里的 `pytest.raises(match=...)` | `exact`（已有 AST 提取器，直接复用） |

也就是说，**契约可以从 PR 半自动生成**，人只需要确认阈值是否合理。这一点值得写进论文——它说明契约不是纯手工艺术，而是可以从版本历史里推导的。

## 五、难度分层怎么做

不能靠"感觉难"，要有依据：

1. 对候选池的每条任务，先让**最便宜的模型**（`deepseek-v4-1-flash`）单轮跑 3 次；
2. 按通过次数分档：
   - **易**：3/3 通过（这类任务只用来验证"系统不破坏正常交付"）
   - **中**：1/3 – 2/3 通过（**实验主战场**）
   - **难**：0/3 通过（用来测修复循环与协作是否救得回来）
3. 目标配比 **5 : 10 : 5**。

注意：分档结果本身要写进论文，因为"哪些任务模型做不出来"是结论的一部分。

## 八、任务挖掘工具（已实现）

```
python scripts/mine_task.py --repo <仓库URL或本地克隆> --pr <PR号> --out tasks/<id>/
```

它做四件事：定位 base → 在 base 上跑一遍拿到"原有失败" → 只取 PR 的测试改动再跑，
**新增失败**才是这条任务要修的 → 叠加 PR 的源码改动，新增失败必须全部消失。

产物：`test_patch.diff`、`task.json`（含 `verified` 红绿摘要）、`contract.yaml` 草案。
`title` / `statement` / `solution_note` 三个字段仍要人工写——**任务陈述只讲症状、不给解法**，
这一步自动化不了，也不应该自动化。

几个必须知道的细节：

| 事项 | 说明 |
|---|---|
| base 的选择 | 优先用 PR 声明的 `base.sha`（GitHub API，需要能访问 github.com）；取不到时退回 `merge-base`，**但失败用例会偏多**（实测同一 PR 会从 2 条变 26 条） |
| `--base` | 离线或要复现时显式指定，优先于上面两者 |
| 离线 | 源仓库若已有 `pr<N>` 分支（本地或 `origin/pr<N>`），自动跳过联网 |
| 先减基线 | 即使 base 选偏，也会先减去"改测试前就失败的用例"，只留本次新增的 |
| 路径分隔符 | pytest 在 Windows 上输出反斜杠，工具统一成正斜杠，与 `task.json` 保持一致 |

**已对拍验证**：用 `--base 4aeb4338` 重挖 more-itertools PR #1322，
产出的 base、失败用例、红绿摘要与手工版 `tasks/moreitertools-1322` **完全一致**（2026-11-28）。

### 新踩到的坑：中文路径 + `pip install -e` 会弄坏 venv

在 `E:\随行工作台\.work\...` 下执行 `pip install -e .` 之后，venv 启动就报：

```
UnicodeDecodeError: 'gbk' codec can't decode byte 0xa1 in position 7
  File "<frozen site>", line 188, in addpackage
```

原因：editable 安装会写一个 `__editable__*.pth`，里面含中文安装路径；
`site.py` 读 `.pth` 时用本地编码（GBK），遇到中文就炸，**整个 venv 报废**。

两条可行的绕法：

1. **根本不用装**：源码在 `src/` 就 `PYTHONPATH=src`，在根目录就 `PYTHONPATH=.`；
2. 若必须装，把克隆与 venv 放到 **ASCII 路径**（如 `%TEMP%\dbw-mine`）下。

本项目的做法是第 1 条：任务工作区里直接跑 `python -m pytest`（cwd 在 `sys.path` 上），不装包。

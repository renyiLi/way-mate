## 摘要

大语言模型使代码生成的成本急剧下降，但“这段代码能不能交付”仍依赖工程师阅读 diff、运行测试并人工确认，判定成为新的瓶颈。本文设计并实现一个以可执行验收契约为唯一判定依据的多角色代码交付系统：动手之前由人确认契约（测试命令、静态检查阈值、接口冻结、改动预算、精确断言），模型只负责产出补丁，交付是否成立由四类闸门判定，模型不参与判定。

系统以 Python 实现，包含契约 DSL 与严格校验、tests/lint/api/diff 四类闸门、基于 AST 的精确断言提取、提案/复核/裁决三座位协议机、两套执行后端、SEARCH/REPLACE 编辑格式、上下文收窄、多供应商适配与 JSONL 审计。系统在 20 条真实仓库任务（2 个仓库）上运行（本文任务集，2026-11）。

实验表明：两次独立测量给出 31/60（51.7%）与 53/100（53.0%）的通过率，约 53%（实验 11/26/3、11/28/1）；闸门把 tabulate-410 的“4 条用例过 3 条”判为不可交付（实验 11/25/5）；精确断言使一个模型由 0/3 变为 3/3（实验 11/24/1）；上下文收窄使单次 token 降低 84%（实验 11/25/17）。协议对比为单轮 11/12、双提案 12/12，Fisher 双侧 p=1.0，不具统计效力（实验 11/27/3）；复核与裁决的负结果说明多角色协作的独立增益尚未被证实。单条任务的档位跨天不可复现（实验 11/28/1），凡按难度分组的统计都必须注明测量日期与次数。本文的结论是：契约与闸门可以接管判定，协作收益必须被证明。

**关键词**：可执行验收契约；代码交付；闸门；多角色协作；大语言模型

## Abstract

Large language models have sharply reduced the cost of code generation, but deciding whether a patch is deliverable still requires engineers to read diffs, run tests, and confirm that nothing else is broken. Judgment has become the bottleneck. This thesis designs and implements a multi-role code delivery system in which an executable acceptance contract is the sole basis for judgment. Before any code is written, a human confirms a contract (test commands, lint thresholds, frozen APIs, change budget, exact assertions); models only produce patches, and four gates decide whether delivery holds. Models do not participate in judgment.

The system is implemented in Python and includes a contract DSL with strict validation, four gates (tests/lint/api/diff), AST-based extraction of exact assertions, a three-seat protocol (proposer/reviewer/arbiter), two execution backends, SEARCH/REPLACE editing, context narrowing, multi-provider adaptation, and JSONL auditing. It runs on 20 real repository tasks from two repositories (the thesis task set, 2026-11).

Experiments show that two independent measurements give 31/60 (51.7%) and 53/100 (53.0%) pass rates, about 53% (Exp. 11/26/3, 11/28/1); the gates reject a patch that passes three of four tests (Exp. 11/25/5); exact assertions rescue one model from 0/3 to 3/3 (Exp. 11/24/1); context narrowing cuts tokens by 84% (Exp. 11/25/17). The protocol comparison is 11/12 for single-turn and 12/12 for dual proposals, with a two-sided Fisher p=1.0 (Exp. 11/27/3), so it is not statistically informative; negative results on the reviewer and arbiter seats mean that an independent gain from multi-role collaboration has not been established. Per-task difficulty is not reproducible across days (Exp. 11/28/1); any difficulty-based grouping must report the measurement date and repetitions. The thesis concludes that a contract can take over judgment, but the benefit of collaboration still has to be proven.

**Keywords**: executable acceptance contract; code delivery; gate; multi-role collaboration; large language model

# 第 1 章 绪论

## 1.1 研究背景

以大语言模型为核心的代码智能，在两年内从行级补全走到任务级交付：给定仓库与 Issue，模型可以定位缺陷、修改代码、提交补丁。SWE-bench [1] 等基准使这类能力第一次具备可比度量：其论文报告，当时最强模型仅能解决 1.96% 的实例；此后公开榜单的解决率持续上升（榜单数据随时间变化，本文不引用具体数值）。

但工程实践中的主要成本并不在生成。生成一段代码只需要数秒与几分钱，**判断这段代码能不能交付，仍要由工程师阅读 diff、运行测试、确认没有破坏别的东西**。生成越便宜，判定越成为瓶颈：模型把“写”的成本压到接近零，却把“验”的成本原样留给了人。

由此产生三个具体问题。

**其一，验收标准后置且不可执行。** “改好了吗”依赖人眼判断，标准在动手之后才临时形成，既无法自动执行，也无法在事后复现。模型只能从 traceback 里揣摩要求，人只能在事后争论“这算不算修好”。

**其二，多模型协作缺少客观裁判。** 当多个模型给出不同方案时，谁对谁错没有依据；现有做法多让模型互评，而模型互评既不可靠也不可审计。模型越多，争论越贵，裁决越不可信。

**其三，交付过程不可追溯。** 出了问题无法回答“是哪一步、哪个模型、依据什么改的”，也无法把一次成功或失败的交付完整重放。没有追溯，失败无法归因，成功无法复现。

## 1.2 研究切入点

本文不试图让模型“更会写代码”，而是**把判定从人眼移到可执行契约**：动手之前先由人确认一份机器可执行的验收契约，此后由闸门判定交付是否成立，模型只负责产出，不参与判定。

由此得到一条可检验的主线：**模型是可替换的工人，契约是不可替换的裁判。** 模型之间可以争论，但只有闸门能宣布交付成立。复核认为有问题而闸门全绿，交付仍然成立；复核认为没问题而闸门红，交付不成立。这条铁律不是对模型的不信任，而是为了让“是否合格”有一个不随模型状态漂移的锚点。

## 1.3 研究内容

本文的研究内容由六部分组成。

1. **可执行验收契约 DSL**：以 YAML 描述五类验收项——测试命令、静态检查新增阈值、公开接口冻结、改动预算、精确断言；字段严格校验，拼错即报错。
2. **四类闸门与判定归一化**：tests、lint、api、diff 逐项输出结构化结果，作为唯一判定依据。
3. **精确断言的静态提取**：用 AST 从 `pytest.raises(match=...)` 反推“必须逐字出现”的字符串，自动生成契约条目，附来源行号与漂移检查。
4. **三座位协作协议**：提案、复核、裁决三个座位固定，模型数量只决定排班；2 人（`2p.single`）、3 人（`3p.single`）、3 人双轨（`3p.dual`）三种协议共用一台状态机。
5. **两套执行后端**：后端 A 一次调用产出全部改动；后端 B 在仓库中多步探查、编辑、自测，最终归一到补丁。
6. **审计与多供应商适配**：全链路记录提示、响应、闸门结果、token 与延迟；统一能力协商、错误分类与降级登记。

系统在 20 条真实仓库任务（2 个仓库）上运行，包含 4 类闸门、3 种协议与 2 个执行后端（本文任务集，2026-11）。研究边界在第 3 章明确：单用户本地、Python + pytest、只处理存在客观判据的交付任务。

## 1.4 主要工作与贡献

1. **以可执行契约为唯一裁判的交付闭环。** 判定权从模型移交给契约，使“是否合格”可自动执行、可复现。系统在 20 条任务上建立了双向锚点：官方修复必绿、未修复必红；`tabulate-410` 的 4 条用例过 3 条仍被判不可交付（实验 11/25/5）。这说明闸门能拒绝“部分正确”，而不只是“全错”。

2. **精确断言的静态提取与漂移检查。** 把测试里隐含的逐字要求提进契约，使隐含验收要求显式化。对照实验显示，它能把一个模型由 0/3 提升为 3/3，并使另一个模型的 token 消耗降低 58%（实验 11/24/1）。这项效果只限于一条 fixture 任务，不能外推为“普遍有效”。

3. **座位固定、人数可变的协议机与双后端。** 三种协作规模共用一台状态机，两套执行后端共用一套闸门，使“协作规模”与“执行方式”成为可对照变量。后端 B 在一次任务上比 A 省 42% token（实验 11/25/2），但调用次数更多、更慢；这条结果同样只来自一条任务。此外，本文用“结构索引 + 报错位置窗口”收窄大文件上下文，使单次 token 降低 84%（实验 11/25/17），并用 SEARCH/REPLACE 片段替换解决了整文件重写写不完的问题（实验 11/25/1）。

4. **可复现的实验方法与一条负结果。** 本文把“成功与失败都记录”作为实验纪律。两次独立测量给出约 53% 的通过率：31/60（51.7%）与 53/100（53.0%），差 1.3 个百分点（实验 11/26/3、11/28/1）；但单条任务的档位跨天不可复现（`1285` 0/3→3/3→0/5），协议对比因天花板效应不具统计效力（实验 11/28/1、11/27/3）。因此本文不写“协作有增益”，也不写“协作无增益”，只写“当前实验测不出来”。

需要谨慎表述：**截至 2026-11，公开项目中未见把验收契约作为唯一判定依据的完整实现。** 本文不称“首创”，只说“在这个方向上补了一个可运行的实现与一组可复现的实验”。

# 第 2 章 相关技术与研究现状

## 2.1 四层生态与判定位置

以大语言模型为核心的代码智能，在两年内从行级补全走到任务级交付。围绕“模型能不能把一条 Issue 修好”，生态大致分为四层：通用编码智能体、软件工程智能体、多智能体编排、契约与闸门。前三层解决“怎么生成”，第四层才解决“怎么判定”；层数越往后，工程越薄，也越接近本文要回答的问题。

| 层 | 代表工作 | 解决什么 | 判定方式 |
|---|---|---|---|
| 通用编码智能体 | codex、OpenHands | 读仓库、改文件、跑命令 | 人审 |
| 软件工程智能体 | SWE-agent、Agentless、AutoCodeRover | Issue → 补丁 | 基准测试通过率 |
| 多智能体编排 | MetaGPT、ChatDev | 角色分工与协作 | 模型互评/测试 |
| 契约与闸门 | skillgate、proof-loop | 交付是否成立 | 契约 + 闸门 |

本章按这四层综述，并在末尾给出三个空白。需要先说明：本文不追求“覆盖所有相关工作”，只选取与“判定”直接相关的代表工作；文中星标数为 2026-11-28 查询值，仅用于刻画规模，不精确到百位，也不代表质量评价。

## 2.2 通用编码智能体

通用编码智能体是当前生态的主体。codex（13.6 万星）、OpenHands（9.4 万星）[10]、cline、aider、continue 等把“读仓库、改文件、跑命令”封装成可交互的智能体，工程成熟度很高（截至 2026-11-28 实测）。它们的目标是“帮人干活”，不是“给出可复现的交付判定”；最终是否合并仍由人决定。

学术路线上，SWE-bench [1] 把真实 Issue 与测试变成可比基准；SWE-agent [4] 以 issue 到 patch 的端到端流程建立范式；Agentless [2] 用“定位—修复—验证”的三段式极简流水线，以更低成本取得相当甚至更优的结果；AutoCodeRover [3] 借助程序结构与测试信息改进定位；RepoCoder [14] 研究仓库级检索与补全；综述 [13] 对这条路线做了系统梳理。

这些工作的共同点是：评测依赖测试通过率。测试是基准的“裁判”，不是交付的“契约”。测试通过只说明“这组用例过了”，不说明接口没被破坏、改动没有越界、异常消息符合约定。基准测试本身也有边界：测试集可能被污染，测试环境可能漂移，测试通过也可能掩盖接口破坏。本文不否认基准的价值，但认为“基准通过”与“交付成立”之间还差一层契约。

## 2.3 软件工程智能体与评测

SWE-agent 的贡献之一是 agent-computer interface（ACI），把仓库操作变成模型可用的动作空间；Agentless 反其道而行，用固定三段式流水线证明“流程纪律可能比智能体复杂度更关键”；AutoCodeRover 把程序结构与测试信息引入定位。三者的评测都建立在真实缺陷数据集上：SWE-bench [1]、BugsInPy [11]、Defects4J [12]。

这条路线与本文最接近：都以“真实仓库 + 测试”为任务形态。但它们的判定是“基准测试是否通过”，本文的判定是“契约下的四类闸门是否全绿”。前者是评测协议，后者是交付协议。差别在于：契约在动手前由人确认，除测试外还包含 lint、api、diff、exact；判定结果进入审计，可按运行标识追溯。

另一个差别是任务来源：基准任务通常由数据集维护者预先构造，本文任务由真实 PR 反向构造，测试补丁与契约一起进入任务基线；这让“红态”可复现，也让“绿态”有官方修复作为锚点。第 6 章会说明，这种构造方式并不便宜：20 条任务来自 2 个仓库，跨仓库外推仍是后续工作。

## 2.4 多智能体协作框架

MetaGPT [5]（7.1 万星）以角色分工与结构化通信模拟软件开发组织；ChatDev [6] 用对话链组织设计、编码、测试等阶段；AutoGen、CrewAI、LangGraph 提供编排基础设施；多智能体辩论 [7] 与自一致性 [8] 在推理任务上证明“多意见聚合”可以提升正确率；CodeT [9] 用生成测试筛选候选解。

但这类方法在代码任务上的收益并不稳定：成本随模型数与轮数线性增长，模型互评缺乏客观依据，容易退化为风格趋同的相互认可。从信息量看，“多意见”不自动等于“多信息”；没有客观裁判时，增加座位往往只增加争论，不增加判定依据。CodeT 的启示是把裁判权交还可执行检查；本文进一步把裁判权交给契约与闸门，模型之间可以争论，但不能投票决定“合不合格”。

这也解释了本文为什么把“协作”设计成一组可对照的座位，而不是一个更大的智能体：座位可以消融、可以计数、可以比较成本；一个更大的智能体只能整体替换，无法回答“多出来的部分值不值”。

## 2.5 多模型接入与国产化实践

国内工程实践在接入广度上走在前列：oh-my-coder 支持 DeepSeek、GLM 等十余家国产模型并做多智能体协作；magi-code 为本地优先的多智能体客户端；feikong-teams 提供多智能体圆桌讨论模式。它们的价值在“接得多、接得稳”，不在于“判定得准”。

本文不把多模型接入当作创新点。能力协商、错误分类与降级登记是工程前提；多模型是受控实验的自变量，不是卖点。这一点在第 6 章会体现：真正难的不是“再接一家”，而是“换一家之后结论还能不能比”。

接入层的工程难点不在“多”，而在“异构”：不同供应商对结构化输出、工具调用、温度参数的支持不一致，同一段提示在不同端点上的行为可能不同。本文用能力表与降级登记处理这种异构，目的是让“换模型”不改变编排层代码，也不让接口差异冒充能力差异。

## 2.6 验收与闸门

与本文最接近的是一批规模很小的新项目：skillgate（10 星）提出与模型无关的确定性完成线闸门；proof-loop（12 星）提出仓库内验证协议与验收标准；qikly（25 星）从验收标准生成测试套件再收敛代码；contract-driven-development（2 星）以多份契约加分级守卫约束 AI 编程（截至 2026-11-28 实测）。它们的共同点是：方向真实存在，但尚未成型——多为单仓库、单模型、无对照测量。

代码审查类工具规模更大，例如 open-code-review（约 5.6 万星），但它们解决的是“审查建议”，不承担“交付判定”。本文明确：审计与评审不是本文贡献；本文只做“交付判定”，不把“给建议”包装成“做判定”。

与上述工作相比，本文的差异不在“再做一个智能体”，而在三点：契约是唯一裁判、四类闸门并列、协作规模是可对照变量。具体地说，本文把“契约”从一句口号落成五类可执行项，把“判定”从一次测试落成四类闸门，把“协作”从产品形态落成三座位协议。这三件事单看都不新，但组合起来、并给出可复现实验的工作很少。

## 2.7 现状评述：三个空白

1. **验收标准后置且不可执行**：缺少可前置、可执行、可复现的契约表达；测试通过是“事后结果”，不是“事先约定”。后果是模型只能从 traceback 里揣摩要求，人只能在事后争论“这算不算修好”。
2. **协作缺客观裁判**：多模型场景下以互评替代验证，结论不可审计；模型越多，争论越贵，裁决越不可信。后果是“多角色”容易退化成“多几轮聊天”。
3. **缺少可比测量**：现有工具面向“帮人干活”，不面向“产出可比较的实验数据”，因而“多模型是否更好”始终缺乏同条件证据。后果是协作的收益与代价都说不清，只能靠个案讲故事。

这三个空白对应本文的三项工作：契约 DSL 与四类闸门、三座位协议机、可复现实验方法。第 6 章会说明：前两项站住了，第三项只站住了一半——总体通过率可复现，协作增益测不出来。

## 2.8 本文定位

本文位于第四层，借用前三层的工程经验：任务配方来自真实 PR，执行后端借鉴 SWE-agent 式循环，协议机借鉴多智能体编排。但本文的判定不依赖模型互评，而依赖可执行契约与四类闸门。

与上述工作相比，本文有三点不同。其一，判定权归属不同：不是模型投票，也不是单一测试，而是契约下的四类闸门。其二，协作是可对照变量：座位固定、人数可变，2 人/3 人/双轨共用一台状态机，因此可以消融、可以计数。其三，失败被当作结果：第 6 章会把“单条任务档位不可复现”“协议对比测不出差异”“复核座位实质失效”这些负结果写进去，而不是只报通过率。

需要谨慎表述：**截至 2026-11，公开项目中未见把验收契约作为唯一判定依据的完整实现。** 本文不称“首创”，只说“在这个方向上补了一个可运行的实现与一组可复现的实验”。第 6 章会说明，这个实现的判定站住了，协作收益还没有站住；把没站住的部分写出来，比只报好消息更接近研究的本意。

# 第 3 章 需求分析

## 3.1 需求来源与基本设定

第 1 章指出，瓶颈不在代码生成，而在交付判定。本章把这个判断转成系统需求。

基本设定只有一句话：**使用者只做验收，不写代码；系统必须能自证交付成立。** 由此推出两条硬需求。

- **判定可信**：一次交付是否成立，必须由可执行检查给出，不能由模型自评，也不能由“看起来差不多”决定。
- **过程可查**：每次运行要能回答“哪个任务、哪个模型、哪一轮、哪个闸门、为什么”，否则失败无法归因，成功无法复现。

系统的范围在需求阶段就要钉住：单用户本地、Python + pytest、只处理存在客观判据的交付任务。这个范围不是“少做一点”，而是把“可验证性”作为第一约束；超出这个约束的任务，系统只能做结构与一致性检查，必须显式转人工。

## 3.2 用户角色与使用场景

系统是单用户本地工具，但同一个人在不同阶段扮演三种角色。三种角色的区分不落实为账号体系，而落实为操作入口与产物形态。

| 角色 | 目标 | 主要入口 | 产物 |
|---|---|---|---|
| 任务作者 | 把一条真实缺陷变成可复现的任务 | `prepare_task.py` | `task.json`、`contract.yaml`、工作区 |
| 运行者 | 让模型产出补丁并得到判定 | `run_once.py`、`run_runtime.py`、`run_protocol.py`、`baseline.py` | 补丁、闸门报告、审计记录 |
| 审查者 | 判断这次运行是否可信、是否接受 | 终端输出、`runs/audit.jsonl` | 接受/退回的决定与理由 |

对应的三个典型场景是：建任务（选仓库与 PR、应用测试补丁、写契约、校验红态并记录绿态）；跑交付（选任务、模型、后端、协议，发起一次或一批运行）；看结果（读闸门明细与审计，决定接受或退回）。

## 3.3 功能需求

功能需求按“本期是否实现”标注状态。状态分四种：**已实现**（代码里存在且能跑）、**部分实现**（核心可用，但缺外围）、**未实现**（只有设计）、**本期不提供**（明确排除在本文范围外）。这样标注的目的，是防止把“计划中”写成“已支持”。

| 编号 | 需求 | 状态 | 说明 |
|---|---|---|---|
| FR1 | 任务配方与工作区准备 | 已实现 | 按配方克隆仓库、切基线、应用测试补丁、校验红态（绿态由官方修复验证并写入 `verified`） |
| FR2 | 契约解析与严格校验 | 已实现 | YAML 描述五类验收项；未知字段、类型错误、缺项立即报错；表单化编辑器未实现 |
| FR3 | 四类闸门 | 已实现 | tests / lint / api / diff 逐项判定，`all_green` 是唯一交付结论 |
| FR4 | 精确断言提取与漂移检查 | 已实现 | 从 `pytest.raises(match=...)` 提取字面量，接入 CI 检查 |
| FR5 | 三座位协议 | 已实现 | 提案 / 复核 / 裁决；2 人、3 人、双轨共用一台状态机 |
| FR6 | 两套执行后端 | 已实现 | 后端 A 一次生成；后端 B 多步循环；统一归一到补丁 |
| FR7 | 审计与追溯 | 已实现 | JSONL 记录运行标识、模型调用、闸门结果、成本；离线回放未实现 |
| FR8 | 多供应商适配 | 已实现 | 统一封套与能力表；缺失能力降级并登记 |
| FR9 | 批量基线 | 已实现 | 20 条任务 × N 次批量运行，产出可汇总的原始记录 |
| FR10 | 报告与 HTTP 服务（后端） | 本期不提供 | 后端当前只能读终端输出与 `audit.jsonl`；HTTP 接口仍是计划；工作台前端由前端实现线提供，本文不展开其实现 |
| FR11 | 安全沙箱 | 未实现 | 当前执行环境只隔离工作目录与超时，不提供断网、只读挂载与资源限额 |

需求的重点不是“功能多”，而是 FR3（闸门）与 FR7（审计）：没有闸门，判定不可信；没有审计，失败不可归因。FR10、FR11 是“让系统更好用、更安全”的需求，不是“判定成立”的前提，因此可以在本期之外。

## 3.4 非功能需求

| 编号 | 需求 | 约束与验证方式 |
|---|---|---|
| NFR1 | 可复现 | 依赖版本钉死；离线测试在 CI 中全部通过（数量以 pytest 输出为准）；CI 在 Python 3.10 / 3.11 双版本通过 |
| NFR2 | 可追溯 | 每次运行有唯一 `run_id`；模型调用与闸门判定可按 `run_id` 定位 |
| NFR3 | 单用户本地 | 不做登录、权限、多租户与云端部署 |
| NFR4 | 受限执行 | 命令限定在工作目录内执行，带超时；当前版本不是安全沙箱 |
| NFR5 | 可扩展 | 新增供应商只改配置与适配层；新增任务只加配方与契约 |
| NFR6 | 成本可控 | 多轮运行有调用与 token 预算，超限终止并记录；单轮运行有单次输出上限 |

NFR1 与 NFR2 是“论文数据可信”的基础，不是可选项。没有固定依赖，换台机器结果就变；没有 `run_id`，第 6 章的数字就无法回溯到某次运行。

## 3.5 任务配方与契约

任务配方与契约是系统的两个静态输入。任务配方描述“去哪找缺陷、用哪条测试验收”；契约描述“怎样才算交付”。

任务配方的核心是五类信息：任务标识（`id`）、仓库与基线（`repo`、`base_sha`）、任务陈述（`statement`）、目标测试（`target_test`）、目标文件（`target_files`）。此外还有测试补丁（`test_patch`）、禁止路径（`forbidden`）、红绿校验（`verified`）与实测记录（`measured`）。任务进入任务集前必须完成红绿校验：旧源码必须红，加官方修复必须绿。`prepare_task` 负责跑红态，绿态由官方修复验证并记录在 `verified`；两条都成立，任务才能用。

契约包含五类验收项：

| 验收项 | 作用 |
|---|---|
| `tests` | 指定验收命令；退出码为 0 才通过 |
| `lint` | 限定新增静态检查问题数 |
| `api` | 冻结公开符号，防止顺手破坏接口 |
| `exact` | 要求异常消息等字符串逐字出现 |
| `diff` | 限定改动文件数、行数与禁止路径 |

这五类验收项覆盖了“功能、风格、接口、精确语义、改动范围”五个维度。它们不是可选的“加分项”：缺哪一类，闸门就在哪一类上失明。

## 3.6 典型用例

| 用例 | 参与者 | 前置条件 | 主流程 | 后置/异常 |
|---|---|---|---|---|
| UC1 准备任务 | 任务作者 | 选定上游 PR 与基线 | 克隆 → 切基线 → 应用测试补丁 → 写契约 → 校验红态（绿态由官方修复验证并记录） | 红绿不符则任务作废；网络不可用可走本地镜像 |
| UC2 单轮交付 | 运行者 | 任务已就绪、能力表已生成 | 选模型 → 调后端 A → 解析补丁 → 跑四类闸门 | 提案不合法或闸门红则拒绝，并记录原因 |
| UC3 多座位协议 | 运行者 | 任务已就绪、座位已配置 | 提案 → 复核 →（裁决）→ 闸门 → 未绿则下一轮 | 轮次或预算耗尽则升级人工；复核结论需带证据 |
| UC4 审查运行 | 审查者 | 已有 `run_id` | 查闸门明细与审计 → 决定接受或退回 | 审计缺失或字段不全时，该次运行不进入实验数据 |

四个用例共用一条底线：**只有闸门能宣布交付成立**。审查者可以退回一次“闸门全绿”的交付（例如发现契约写错），但不能把一次“闸门红”的交付判成成立。

## 3.7 边界与非目标

**适用边界**：可执行验收契约只适用于存在客观判据的交付任务。判据的可获得性决定契约强度，与所属行业无关。对不存在客观判据的任务（营销创意、观点生成等），本机制只能做结构与一致性检查，必须显式转人工。

**本期非目标**：

- 不支持任意编程语言，限定 Python + pytest；
- 不实现自动合并主干与生产部署；
- 不实现多用户并发、权限与云端部署；
- 不提供安全沙箱；当前执行环境是受限执行环境，不是沙箱；
- 后端不提供 HTTP 服务；工作台前端由前端实现线提供，不在后端范围内；当前后端是命令行系统与库；
- 不提供按 `run_id` 的离线回放；当前只有审计追溯。

把这些写成“非目标”不是免责，而是让第 6 章的结论有明确适用范围：本文证明的是“契约与闸门在 20 条 Python 任务上可运行”，不是“任意语言、任意行业都能用”。

# 第 4 章 系统设计

## 4.1 设计目标与原则

第 3 章的需求可以归结为一句话：系统必须在人不读代码的前提下，对“这次交付是否成立”给出可执行、可复现的回答。围绕这句话，本章给出系统设计。

设计遵循三条原则。

**第一，判定只有一处。** 契约与闸门是唯一判定依据；模型可以争论、可以给建议，但不能宣布交付成立。复核座位认为有问题而闸门全绿，交付仍然成立；复核认为没问题而闸门红，交付不成立。这条原则不是对模型的不信任，而是为了让“是否合格”有一个不随模型状态漂移的锚点。

**第二，生成方式可替换。** 供应商、执行后端、协作规模都只影响“怎么产出补丁”，不影响“怎么判定”。换一家模型、换一种后端、换一种排班，契约与闸门不动。这样“模型是否更好”“协作是否更好”才能成为可对照的实验问题，而不是系统里写死的偏好。

**第三，过程可追溯。** 每次运行有唯一标识，模型调用、闸门结果、预算与终止原因都落到审计里。追溯不是回放：当前版本能回答“当时发生了什么”，还不能离线重跑；后者列为后续工作。

设计边界与第 3 章一致：单用户本地、Python + pytest、只处理有客观判据的交付任务。HTTP 服务、工作台前端、安全沙箱与回放不在本期范围内，本章不把它们画进已实现的架构。

## 4.2 总体架构

系统采用“薄入口 + 厚内核 + 可替换边界”的分层结构。

```text
┌──────────────────── 入口层（CLI 脚本）────────────────────┐
│ prepare_task  run_once  run_runtime  run_protocol  baseline │
└───────────────────────────┬────────────────────────────────┘
                            │
┌───────────────────────────▼────────────────────────────────┐
│ 编排层  delivery（单轮） / protocol.machine（多座位）        │
│ 座位、轮次、预算、补丁归一化、终止条件                        │
└───┬──────────────┬──────────────┬──────────────┬───────────┘
    │              │              │              │
┌───▼────┐   ┌─────▼─────┐  ┌─────▼─────┐  ┌─────▼─────┐
│ 适配器  │   │ 契约/闸门  │  │ 执行后端   │  │ 审计       │
│ 多供应商│   │ 唯一裁判   │  │ A / B      │  │ JSONL      │
└────────┘   └───────────┘  └───────────┘  └───────────┘
```

各层的职责如下。

- **入口层**：`prepare_task.py` 按任务配方准备工作区并校验红绿；`run_once.py` 跑后端 A；`run_runtime.py` 跑后端 B；`run_protocol.py` 跑 2 人/3 人协议；`baseline.py` 跑批量基线。入口只做参数解析与结果打印，不做业务判断。
- **编排层**：`delivery.py` 负责单轮交付；`protocol/machine.py` 负责多座位协议。两者共用契约、闸门与审计，区别只在“补丁由谁、分几步产出”。
- **核心层**：`contract.py` 解析并严格校验契约；`gates.py` 执行四类闸门；`exact.py` 处理精确断言。
- **边界层**：`adapters/` 适配不同供应商；`runtime/` 提供执行后端；工作区快照与差异由 `runtime/workspace.py` 负责。
- **审计层**：`audit.py` 以 JSONL 追加记录运行事件。

入口层不做业务判断、核心层不关心模型是谁，这条分界使“实验里跑的”和“手工跑的”走同一条代码路径。当前版本没有 HTTP 服务与工作台前端；图中的“入口层”就是命令行。

## 4.3 契约 DSL

契约是系统的“唯一裁判”，设计目标是可读、可校验、不可含糊。契约用 YAML 描述，包含五类验收项。

| 验收项 | 主要字段 | 判定方式 |
|---|---|---|
| `tests` | `cmd`、`timeout_s` | 命令退出码为 0 |
| `lint` | `tool`、`max_new` | 新增问题数不超过上限 |
| `api` | `frozen` | 冻结符号仍可导入 |
| `exact` | `exception`、`contains`、`source`、`origin` | 指定字符串逐字出现 |
| `diff` | `max_files`、`max_lines`、`forbid` | 改动预算与禁止路径 |

另有一个 `loop` 段，规定修复轮次上限与耗尽后的处理。契约示例：

```yaml
task_id: tabulate-366
repo: .
doD:
  tests: [{cmd: "python -m pytest test/test_output.py::test_github_multiline -q", timeout_s: 120}]
  lint: {tool: ruff, max_new: 0}
  api: {frozen: []}
  exact: []
  diff: {max_files: 3, max_lines: 40, forbid: [test/]}
loop: {repair_rounds: 3, on_exhausted: escalate_to_human}
```

解析器对未知字段、类型错误与缺必填项一律报错，不做“尽量理解”。理由是：契约一旦容忍拼写错误，闸门就可能在空契约上宣布通过；而一个空契约的“全绿”比没有闸门更危险。

## 4.4 四类闸门

四类闸门是并列关系，不是加权关系：任何一项失败，`all_green` 为假。

| 闸门 | 通过条件 | 主要防什么 |
|---|---|---|
| tests | 所有验收命令退出码为 0 | 功能没做对、只对一部分 |
| lint | 新增问题数 ≤ `max_new` | 越改越乱 |
| api | 冻结符号仍存在 | 顺手破坏外部接口 |
| diff | 未超文件/行数预算、未触碰 `forbid` | 大面积重写、改测试代替改代码 |

判定归一化只做一件事：把“通过/失败”与可读明细放进同一个结构，供入口、审计与实验共用。入口不自己算“是否可交付”，实验也不自己拼结论。

**判定语义需要说清楚**：闸门回答的是“在给定契约下是否可交付”，不是“修复在语义上是否正确”。契约写得窄，闸门就只能判窄；契约写错，闸门会忠实地判错。为降低这种风险，任务集在进入实验前做双向校验：官方修复必须全绿，未打补丁必须红。闸门是契约的执行者，不是真理的裁判；第 6 章会给出这一口径的完整说明。

**部分正确会被拒绝**：`tabulate-410` 的 4 条用例过了 3 条，闸门仍判不可交付（实验 11/25/5）。这正是设计要的效果——它防止“测试从 4 红变 1 红”被误读为“基本修好了”。

## 4.5 精确断言

测试里的 `pytest.raises(ValueError, match="missing '='")` 包含一条逐字约束，但模型只能从 traceback 里揣摩。精确断言的提取分三步：

1. 用 AST 遍历测试函数，定位 `pytest.raises` 调用；
2. 读取 `match` 参数，过滤含正则元字符的模式（宁可少收，不可错收）；
3. 生成 `exact` 条目，记录异常类型、字符串、来源文件与行号，`origin=auto`。

人工补充的条目记为 `origin=manual`。`extract_exact.py --check` 在 CI 中比对“契约里声明的”与“测试里实际的”，防止契约与测试漂移。

精确断言解决的是一个很具体的问题：验收要求藏在测试里，模型看不到，于是把异常消息“优化”得更好读，测试就红了。把它提进契约后，写作与复核两个座位都能直接看到硬约束；第 6 章的对照实验显示这一改动能把部分模型从失败救回（实验 11/24/1）。它没有解决“模型不会改代码”，只解决了“模型不知道该写什么”。

## 4.6 三座位协议

协议把“产出补丁”和“评价补丁”拆成不同座位。座位固定为三个：

| 座位 | 职责 | 不能做什么 |
|---|---|---|
| 提案 proposer | 产出补丁与理由 | 不能宣布交付成立 |
| 复核 reviewer | 指出可疑之处、给证据 | 不能判定，不能替代闸门 |
| 裁决 arbiter | 在多个提案/结论间做选择 | 不能新增结论、不能评价代码质量 |

模型数量只决定“一个模型能不能兼两个座位”，不改变流程。三种协议因此共用一台状态机：

| 协议 | 排班 | 分歧由谁消解 |
|---|---|---|
| `2p.single` | 提案 + 复核 | 只能交闸门 |
| `3p.single` | 提案 + 复核 + 裁决 | 裁决消解一部分，闸门终裁 |
| `3p.dual` | 双提案 + 裁决 + 复核 | 裁决先选提案，闸门终裁 |

主流程是：提案 → 复核 →（裁决）→ 闸门 → 未绿则带失败明细进入下一轮。**铁律**：只有闸门能宣布交付成立。复核结论必须带证据；没有证据的结论不进入阻断。裁决只裁“结论是否成立”，不得新增结论、不得评价代码质量——否则它会与闸门冲突，成本翻倍而信息量为零。

同一模型坐多个座位时，运行记录标记 `self_played=true`；否则实验会把“自演”误读成“多模型协作”。这一标记不是实现细节，而是实验可比性的前提。

## 4.7 两套执行后端

补丁可以由两种方式产出，系统把它们统一到同一个 `Patch`，再交同一套闸门。

| 维度 | 后端 A（direct） | 后端 B（runtime） |
|---|---|---|
| 形态 | 一次调用产出全部改动 | 多步：探查 + 编辑 + 自测 |
| 上下文 | 任务 + 失败输出 + 目标文件全文 | 任务 + 失败输出，自行 grep |
| 编辑 | 整文件或 SEARCH/REPLACE | `edit:` 块 + SEARCH/REPLACE |
| 风险 | 大文件写不完、截断 | 只读不写、预算耗尽 |

两套后端的存在不是为了“多一个功能”，而是为了让“执行方式”成为可对照变量：同一契约、同一闸门，只换后端，就能回答“多步探索是否比一次生成更划算”。第 6 章报告了同一任务上后端 B 省 42% token 的结果（实验 11/25/2），但该结果只来自一条任务，不能外推。

## 4.8 审计与数据模型

任务由 `task.json` 与 `contract.yaml` 描述。`task.json` 记录仓库、基线提交、任务陈述、目标测试、目标文件、难度档与红绿校验结果；`contract.yaml` 记录五类验收项与修复轮次。

运行由 `run_id` 标识。审计事件包括：

| 事件 | 关键字段 | 用途 |
|---|---|---|
| `run_start` | 任务、基线提交、供应商、模型、契约摘要 | 定位“跑的是哪一版” |
| `model_request` | 座位、阶段、提示长度 | 还原调用序列 |
| `model_response` | token、延迟、降级、摘要、原始文本 | 还原模型行为 |
| `gate_report` | 逐项结果、`all_green` | 还原判定 |
| `runtime_run` | 后端轨迹、终止原因、改动 | 还原多步过程 |
| `run_end` | 结论、轮次、预算 | 汇总 |

任务状态为“草稿/就绪”，运行状态为“运行中/接受/拒绝/升级人工/错误”。状态不是装饰：它决定重跑、对比与统计时哪些记录可用。

审计是“可追溯”的实现，不是“可回放”的实现：原始响应已经落盘，但当前版本没有按 `run_id` 离线重跑的工具。第 7 章把回放列为后续工作。

## 4.9 错误处理与降级

| 情况 | 处理 |
|---|---|
| 供应商不支持严格 JSON Schema | 降级为 `json_object`，登记 `degraded` |
| 只接受固定 temperature | 强制取值并登记 |
| 推理吃光输出预算、正文为空 | 按失败计，不当作“空提案”放过 |
| 调用超时、限流 | 可重试错误重试；不可重试错误记为失败运行 |
| 预算耗尽 | 终止并记录 `budget_exhausted`，不宣布通过 |

降级不是隐藏：每一次降级都写入审计，避免实验结论把“接口差异”误读成“模型能力差异”。这条设计直接影响第 6 章的可比性——如果 DeepSeek 与 Ark 的结构化输出严格性不同，混合对比时必须分组。

## 4.10 安全边界

补丁路径在解析层拒绝绝对路径与 `..`，`diff.forbid` 拦下触碰测试目录的改动。密钥只从环境变量或 `.env` 读取，日志只允许掩码。

需要明确的是：当前执行环境 `LocalEnvironment` 只隔离工作目录与超时，**不是安全沙箱**；它不提供断网、只读挂载与 CPU/内存限额。它可以跑“模型自己生成的命令”，但不能跑“不可信用户的命令”。这一限制在第 7 章列为后续工作，论文不把它写成“沙箱”。

## 4.11 小结

本章的设计可以概括为三句话：判定只有一处（契约与闸门），生成方式可替换（供应商、后端、协作规模），过程可追溯（`run_id` 与审计）。三者共同支撑第 3 章提出的“自证交付成立”。设计没有解决“模型能不能改对”，它解决的是“改对了没有、能不能被独立判定”。

# 第 5 章 系统实现

## 5.1 技术栈与代码组织

系统以 Python 3.11 实现，运行时只依赖 PyYAML；pytest 与 ruff 仅用于开发与 CI。源码分两部分：`src/dbw/` 是内核，约 4,200 行；`scripts/` 是入口，约 1,672 行（不计入内核行数）。仓库现有离线测试（数量以 CI 的 pytest 输出为准），CI 在 Python 3.10 与 3.11 两个版本上运行。

| 模块 | 职责 |
|---|---|
| `contract.py` | 契约解析、严格校验、数据类 |
| `gates.py` | tests / lint / api / diff 四类闸门与报告 |
| `exact.py` | 精确断言的 AST 提取与漂移检查 |
| `protocol/` | 封套、能力协商、分内接口、三座位协议机 |
| `adapters/` | OpenAI 兼容适配器、错误分类 |
| `runtime/` | 后端 B 的循环、本地环境、工作区快照与差异 |
| `delivery.py` | 后端 A 的单轮交付编排 |
| `audit.py` | JSONL 审计与运行标识 |
| `edit_format.py` | SEARCH/REPLACE 编辑格式 |

入口脚本只做参数解析与结果打印，核心逻辑在库内。这样“实验里跑的”和“手工跑的”走同一条代码路径；否则实验结论无法解释真实使用时的行为。

## 5.2 契约解析

契约用 `dataclass` 建模：`Contract` 持有 `task_id`、`repo`、`tests`、`lint`、`api`、`exact`、`diff` 与 `loop`；`TestSpec` 保存命令、超时与解析后的 argv；`ExactSpec` 保存异常类型、字符串、来源与来源方式。

解析器维护每类节点的允许键集合，出现未知键立即抛出带路径的错误。类型错误、缺必填项、空测试列表同样报错。这样做的代价是写契约时更啰嗦，收益是闸门不会在“拼错的契约”上给出通过。

`TestSpec` 在解析阶段就把命令拆成 argv，而不是留给执行阶段做字符串切分。这样既避免了引号与空格带来的歧义，也让“命令不存在”可以在执行时被明确报出（退出码 127）。

## 5.3 闸门实现

四类闸门共享一个命令执行函数 `_run(argv, cwd, timeout_s)`：以参数列表而非 shell 字符串执行，避免引号与管道带来的注入面；超时返回专用退出码 124，命令不存在返回 127。

- **tests**：逐条执行契约中的命令，解析 pytest 输出里的 passed/failed/error/skipped 计数；任一命令退出码非 0 即失败，并保留末尾若干行作为证据。
- **lint**：先跑基线，再跑打补丁后的 ruff，比较“新增问题数”与 `max_new`；只罚新增，不罚历史遗留。
- **api**：在打补丁后的工作区尝试导入冻结符号，缺失即失败；不冻结时直接通过并注明。
- **diff**：用 git 取改动文件与行数，检查文件数、行数与 `forbid` 路径；禁止路径命中即失败。

`GateReport` 固定四项、顺序固定，`all_green` 只有在四项全通过时为真。入口、审计与实验都只读这个字段，不各自计算。判定口径——闸门判的是“在给定契约下可交付”，不是“语义正确”——第 6 章会用双向锚点专门说明。

## 5.4 精确断言的实现

`exact.py` 用 `ast` 遍历测试文件，定位 `pytest.raises` 调用，读取 `match` 关键字；含正则元字符的模式直接跳过，避免把正则当字面量收进契约。提取结果带 `source`（文件:行号）与 `origin=auto`，人工补充的条目为 `origin=manual`。

`extract_exact.py --check` 把“契约里声明的精确断言”与“测试里实际存在的”做集合比对，差异即失败；该检查已接入 CI，防止测试改了而契约没改。这一检查解决的是契约漂移，不解决模型是否遵守契约；后者只能靠闸门。

## 5.5 协议机的实现

`ProtocolRunner` 持有座位表、协议标识、轮次上限与预算。座位表允许同一模型坐多个座位，此时运行记录标记 `self_played=true`；否则实验会把“自演”误读成“多模型协作”。

每轮流程是：构造提案提示 → 调用提案模型 → 解析补丁 → 复核模型给出结论 →（裁决模型消解分歧）→ 跑闸门 → 若未全绿，把失败明细带入下一轮。复核结论必须带证据；无证据的结论按 R-2 规则丢弃。

11/25/4 之前，单轮后端与协议机各自拼提案提示，协议机多塞了一段完整契约，导致“单轮 vs 2 人”不可比。此后新增 `render_propose_prompt(task, contract)` 作为唯一构造点，并加测试断言两处提示逐字相同（实验 11/25/4）。这是方法学修复，不是功能修复：不统一提示词，后续所有协作对比都不可信。

复核结论的 schema 要求 `gate` 字段取 tests/lint/api/diff 之一，但模型持续把它当作“问题类别”填写。早期实现会因此整条丢弃结论；现改为记为 `unknown` 并降级保留（`BLOCKER` 降为 `MAJOR`），但这类结论无法参与阻断，复核座位在实际运行中只剩“触发下一轮”的作用。第 6 章把它作为一条负结果报告，第 7 章提出把复核改为纯建议者的后续方案。

## 5.6 两套执行后端

**后端 A** 由 `delivery.deliver_once` 实现：一次调用，要求模型返回整文件内容或 SEARCH/REPLACE 编辑，解析为 `Patch` 后写入工作区，再跑四类闸门。它需要任务配方给出目标文件；不给目标文件时，模型容易凭空猜结构。

**后端 B** 由 `MiniSweRuntime` 实现：模型在仓库里执行 bash 命令、读文件、输出 `edit:` 块，循环直到提交哨兵或预算耗尽。工作区快照与差异由 `runtime/workspace.py` 负责；本地环境 `LocalEnvironment` 负责执行命令与超时。

SEARCH/REPLACE 是两套后端共用的编辑格式：只给要替换的几行，不重写整份文件。11/25/1 的失败序列说明了为什么必须换格式：整文件重写会产生 3001 行改动、`rationale=PLACEHOLDER`、pytest 退出码 4；换成片段替换后一次通过。编辑格式解决的是“写不完”，不是“改不对”——11/25/3 里模型改了 5 行但改错位置，闸门照样判红。

两套后端的成本结构不同。后端 A 的成本由目标文件大小决定，近似常数；后端 B 每次只读几十行，但调用次数多。同一任务上，B 用 19,340 token 完成 A 用 33,529 token 完成的事（−42%），但 B 有 10 次串行调用，实际更慢（实验 11/25/2）。这条结果只来自一条任务，第 6 章会说明它不能外推。

## 5.7 上下文收窄

大文件整份塞进上下文，既贵又容易让模型“看不过来”。上下文收窄把输入改为“结构索引 + 报错位置窗口”：先给文件的结构索引，再给失败位置前后若干行；没有行号时安全回退到全文。

在 11/25/17 的实验中，token 从 55,288 降到 9,069（−84%），一条难档任务从 0/2 变为 1/2。随后 11/26/3 的 20 条任务基线里，`moreitertools-1248` 因同一改动从 0/3 变为 2/3（实验 11/25/17、11/26/3）。这说明“任务难度”不是任务的绝对属性：同一任务、同一模型，换上下文策略，档位会变。

上下文收窄也有边界：它依赖失败输出里的行号；行号缺失时只能回退全文，收益消失。第 6 章把这一点写进有效性威胁。

## 5.8 适配器与审计

`OpenAICompatAdapter` 把不同供应商的差异收进一个薄层：统一请求封套、超时、重试、错误分类与响应摘要。能力表在启动前实测并落盘，记录是否支持 `json_schema`、`tools`、`seed`、上下文上限与固定 temperature。

不支持严格 JSON Schema 时降级为 `json_object`，只接受固定 temperature 时强制取值，推理模型输出预算不足时按失败计——三类情况都写入审计的 `degraded` 字段。降级不是隐藏，否则实验会把“接口差异”误读成“模型能力差异”。

审计以 JSONL 追加写入，事件包括 `run_start`、`model_request`、`model_response`、`gate_report`、`runtime_run`、`run_end`。`model_response` 保存 token、延迟、降级、请求与响应摘要以及原始文本；`gate_report` 保存逐项结果与 `all_green`。审计是“可追溯”的实现，不是“可回放”的实现：原始响应已落盘，但当前版本没有按 `run_id` 离线重跑的工具。

## 5.9 实现中修掉的关键问题

| 问题 | 现象 | 修法 | 实验 |
|---|---|---|---|
| Windows 换行伪造 diff | 写文件经文本模式，`\n` 变 CRLF，整份文件算改动（6001 行假 diff） | 一律 `write_bytes(content.encode("utf-8"))` | 11/25/1 |
| 推理模型空正文 | `finish_reason=length`、正文为空，却不报错 | 空正文按失败计，提高预算或换模型 | 11/25/1、11/25/7 |
| 提示词路径分叉 | 单轮与协议的提案提示不同，token 不可比 | `render_propose_prompt` 唯一入口 + 逐字相同测试 | 11/25/4 |
| 超时硬编码 120s | 长补丁复核必超时，整批崩 | 提为 `request_timeout_s`，CLI 可传 | 11/25/7 |
| 适配器异常冒泡 | 一次超时打断整批实验 | 协议机捕获 `AdapterError`，记为一次失败运行 | 11/25/7 |
| 复核 `gate` 字段语义 | 模型把“问题类别”填进 gate，结论被丢弃 | 第 6 章报告；第 7 章拟改为可选字段 | 11/25/8、11/25/9 |
| 中文路径 + editable 安装 | 安装损坏 venv | 改用非 editable 安装或英文路径 | 工程记录 |

这张表里的问题都不是“模型不够聪明”，而是工程细节。它们不写进论文，答辩时就会被问“为什么你的实验跑不出来”；写进去，反而说明系统真的跑过。

### 5.9.1 静默降级：两个 bug

工具链里还有两个没有被异常捕获的降级。其一，GitHub URL 的正则用了懒惰匹配，把 `.git` 后缀吞进仓库名，API 请求 404 后静默退回 `merge-base`；其二，用 `git cat-file -e` 的标准输出判断提交是否存在，而该命令成功时没有输出，于是永远被判为“不存在”，同样退回 `merge-base`。两个 bug 叠加时，同一条 PR 的失败用例会从 2 条变成 26 条，且不报任何错。修复方式是抽出 `parse_github_url()` 并加测试、改用返回码判断存在性、让失败原因可见；修复后自动取到的 base 与手工版一致（commit 711588b）。教训是：**降级路径必须报错**，静默降级产出的数据比崩溃更危险。

## 5.10 测试与持续集成

仓库现有离线测试（数量以 CI 的 pytest 输出为准），覆盖契约解析、四类闸门、精确断言、协议机、编辑格式与运行时；测试不需要 API Key。CI 在 Ubuntu 上跑 Python 3.10 与 3.11 两个矩阵，执行 `ruff check`、`extract_exact.py --check` 与 `pytest -q`。

需要说明两点局限：其一，CI 不跑真实仓库端到端，也不跑 Windows，11/25/1 暴露的 CRLF 问题不会被 CI 抓到；其二，测试以单元与离线集成为主，没有覆盖率门槛。第 6 章把这两点列入有效性威胁。

## 5.11 运行方式与边界

单用户本地运行，步骤是：安装依赖、在 `.env` 中配置供应商密钥与端点、用 `test_connection.py` 实测并生成能力表、用 `prepare_task.py` 准备任务、用 `run_once.py` 或 `run_runtime.py` 发起交付、用 `run_protocol.py` 发起多座位协议。所有运行写入 `runs/audit.jsonl`，关键数字抄录到 `experiments/` 的记录。

当前版本没有 HTTP 服务、工作台前端与安全沙箱；它是一套可运行的命令行系统与库，不是完整的 Web 工作台。论文不把这些未实现的能力写成已实现。

## 5.12 小结

实现层面最重要的不是代码量，而是四条约束：判定只有一处（闸门）、提案提示只有一个构造点（`render_propose_prompt`）、落盘只有一种写法（`write_bytes`）、降级路径必须报错。四条约束各自对应一类曾经真实发生过的错误。它们不是风格偏好，而是“结果可复现”的最低条件。

# 第 6 章 实验与结果分析

## 6.1 实验方法

本章的实验对象是 20 条真实仓库修复任务，来自两个仓库：`astanin/python-tabulate` 4 条，`more-itertools/more-itertools` 16 条。任务进入任务集前逐条校验：旧源码必须红，加官方修复必须绿；校验结果写入 `task.json` 的 `verified` 字段。

基线实验使用后端 A（direct）与 `deepseek/deepseek-chat`，每格 5 次，20 条任务共 100 次运行。此前另做过一轮每格 3 次、共 60 次的独立测量。两次测量使用同一任务集、同一模型、同一契约，仅重复次数不同，因此可以作为“总体通过率是否可复现”的对照。

实验记录以“月/日/次数”编号（如 11/28/1），成功与失败都记录；原始日志在 `runs/`（不入库），结论与关键数字抄录在 `experiments/`。主要指标为通过率（四类闸门全绿）、token、耗时、模型调用次数、修复轮次与失败闸门。除特别说明外，本章数字均标注实验编号。

需要先说明本章的读法：**通过率是“契约下可交付”的比例，不是“修复语义正确”的比例**。这两者的区别见 6.2 节；不理解这一点，会把“闸门判得严”误读为“模型修得差”。

## 6.2 判定口径

“闸门是否可靠”是本章最容易被追问的地方。一个不可辩护的说法是“60 次运行无一误判”：本文没有对每次运行的补丁做人工语义复核，“误判”没有可核对的真值。因此本节采用三条有验证方式的表述。

| 表述 | 依据 | 验证方式 |
|---|---|---|
| 正向锚点：20 条任务的官方修复都能通过闸门 | `prepare_task` 逐条跑过“加官方修复 → 全绿” | `task.json` 的 `verified.green_with_fix` |
| 负向锚点：未打补丁时闸门必定判不通过 | `prepare_task` 逐条跑过“旧源码 → 红” | `task.json` 的 `verified.red_without_fix` |
| 部分正确会被拒绝：`tabulate-410` 的 4 条用例过 3 条，仍判不可交付 | 实验 11/25/5 | 闸门按“全部用例通过”判定 |

因此，本文对闸门可靠性的表述是：

> 闸门的判定含义是“在给定契约下可交付”，不等于“修复在语义上正确”。本文在 20 条任务上建立了双向锚点（官方修复必绿、未修复必红），并观察到“部分正确”会被准确拒绝；但未对每次运行的补丁做人工正确性复核，因此本文不作“误判率为零”的断言。

这条口径有两个直接后果。其一，第 6.3 节的 53% 是“契约下可交付率”，不是“模型修对率”；有些失败是模型没改对，有些失败是模型改对了但引出了 lint 问题，还有些失败是提案格式不合法——闸门只负责判“交付是否成立”，不负责解释“为什么没成立”。其二，闸门判定的边界由契约决定：契约写得窄，闸门只能判窄；契约写错，闸门会忠实地判错。20 条任务的双向锚点是为了降低这种风险，但不能消除它。

## 6.4 单条任务不可复现

总体通过率是稳的，单条任务的档位却完全不是。同一任务、同一模型、同一契约，跨天结果可以翻转。

| 任务 | 11/26（3 次） | 11/27（3 次） | 11/28（5 次） |
|---|---|---|---|
| moreitertools-1285 | 0/3 | **3/3** | **0/5** |
| moreitertools-1311 | 2/3 | — | **0/5** |
| tabulate-362 | 0/3 | — | 1/5 |
| tabulate-410 | 2/3 | — | 3/5 |
| moreitertools-1248 | 2/3 | — | 4/5 |

`1285` 是最典型的例子：0/3 → 3/3 → 0/5，没有改代码、没有改契约。`1311` 从 2/3 掉到 0/5。`362` 从 0/3 变成 1/5。这些任务都卡在模型能力的边界上，采样波动就能让结果翻转；失败原因也常在“测试红”与“lint 新增问题”之间跳（实验 11/26/3、11/27/3、11/28/1）。

因此本章只写“在 2026-11-28 的 5 次测量中，6 条任务 0/5”，**不写“6 条任务属难档”**。`task.json` 里的 `tier` 只是当次测量的归类，`measured` 才是数据；论文若要分组，按当次实测通过率分组，并注明测量日期与次数。这不是措辞上的谨慎，而是这批数据给出的硬约束：单条任务的“难度”不是任务的绝对属性。

## 6.5 工程手段的效果

### 6.5.1 精确断言

实验 11/24/1 在手写 fixture 任务上做 3 模型 × 2 条件 × 3 次对照，唯一变量是契约副本里有没有 `exact` 段：

| 模型 | 无 exact | 有 exact | 平均 token | 平均耗时 |
|---|---|---|---|---|
| `deepseek-chat` | 0/3 | **3/3** | 999 → 1,046 | 1.8s → 2.3s |
| `deepseek-v4-1-flash` | 3/3 | 3/3 | 2,207 → 2,030（−8%） | 8.3s → 6.3s |
| `kimi-k3-1-pro` | 3/3 | 3/3 | 5,513 → **2,308（−58%）** | 110.4s → **46.0s** |

合计 6/9 → 9/9；`doubao` 只有 n=1，未计入（实验 11/24/1）。三项观察：救回效应成立（一个模型由全败变全胜）；成本效应只在一个模型上明显（`kimi` token、耗时各降约 58%）；`flash` 两条件均满分，说明该任务对它太简单，条件差异被天花板吞掉。

这项实验只有一条任务、一个难度，不能外推。它证明的是“精确断言在这个任务上有效”，不是“精确断言普遍有效”；它改变的是“模型该写什么”，不改变“模型会不会改代码”。

### 6.5.2 SEARCH/REPLACE 编辑格式

实验 11/25/1 在 `tabulate-366` 上连续失败 6 次，第 7 次才成立。失败序列把瓶颈指得很清楚：整文件重写会产生 3001 行改动、`rationale=PLACEHOLDER`、pytest 退出码 4；后端 B 则不断读文件凑内容，永远凑不齐。换成 SEARCH/REPLACE 片段替换、并给出目标文件内容后，一次通过（实验 11/25/1）。

这条结果说明：编辑格式解决的是“写不完”，不是“改不对”。11/25/3 里模型只改了 5 行，但改在异常之后、永远执行不到，闸门照样判红。格式对了，逻辑仍可能错。

### 6.5.3 上下文收窄

大文件整份塞进上下文，既贵又容易让模型“看不过来”。上下文收窄把输入改为“结构索引 + 报错位置窗口”：先给文件结构索引，再给失败位置前后若干行；没有行号时安全回退到全文。

实验 11/25/17 中，token 从 55,288 降到 9,069（**−84%**），同一任务的两条测试用例由全红变为过 1 条（用例维度 0/2 → 1/2）。随后 11/26/3 的 20 条任务基线里，`1248` 因同一改动从 0/3 变为 2/3（运行次数维度）；到 11/28/1，`1248` 已是 4/5（实验 11/25/17、11/26/3、11/28/1）。这说明上下文工程能改变“任务看起来有多难”，但它的效果不是确定性的：同一任务在不同日期仍会波动。

### 6.5.4 双后端对比

实验 11/25/2 在 `tabulate-366` 上对比后端 A 与 B：A 用 1 次调用、33,529 token；B 用 10 次调用、19,340 token（**−42%**），且 B 不需要任务配方告知目标文件，自己 grep 出来。B 的代价是调用次数多、更慢；该实验没有统计墙钟时间。

这条结果只来自一道 1 行修复，不能外推为“B 一定更省”。它说明的是成本结构不同：A 的成本由目标文件大小决定，B 的成本由调用次数与上下文体积共同决定。第 7 章把“多文件难任务上的成本反转点”列为后续工作。

## 6.6 协议对比：天花板效应

实验 11/27/3 在同一批 4 条任务（`1270`、`1285`、`1305`、`1342`）上、同一天、每格 3 次，对比单轮与双提案：

| 方案 | 通过 | 说明 |
|---|---|---|
| 单轮（1 次调用，无反馈） | **11/12** | 只有 `1270` 有 1 次失败 |
| 双提案（同模型两次采样） | **12/12** | 全部第 1 轮全绿 |
| 双提案（跨模型） | **12/12** | 全部第 1 轮全绿 |

单轮已经 92%，双提案 100%，差异只有 1 次；Fisher 精确检验双侧 **p=1.0**（单侧 p=0.5）（实验 11/27/3）。更麻烦的是跨天漂移：同样是这 4 条任务，11/26 的单轮结果是 8/12，11/27 变成 11/12；`1285` 在 24 小时内从 0/3 变成 3/3。

因此本节不能写“协作有增益”，也不能写“协作无增益”。正确的表述是：**协议层对比因天花板效应与跨天漂移而不具备统计效力，既不能证明也不能否证协作增益**。要回答“协作是否有效”，需要一批单轮稳定失败的任务，或换一个基线更低的模型；在当前任务集与 `deepseek-chat` 上，这个实验测不出来（实验 11/27/3）。

早期还有一组 2 人协议实验：在中档任务上，单轮 1/3、协议 1/8，没有增益（实验 11/25/7、11/25/9）。这组数据与 11/27/3 的任务、协议、样本量都不同，不能混在一起下结论；本章把它作为历史线索，而不是主结论。

## 6.7 负结果

**复核座位实质失效。** 每轮复核提出 5–8 条结论，但模型持续把 `gate` 字段当作“问题类别”填写，结论无法对应到四类闸门。早期实现会因此整条丢弃结论；现在改为记为 `unknown` 并降级保留（`BLOCKER` 降为 `MAJOR`），但这类结论不能参与阻断，复核座位在实际运行中只剩“触发下一轮”的作用（实验 11/27/1）。

**裁决存在首位偏置。** 6 次双提案中，5 次选中第一份；唯一一次选第二份的，恰好是修复轮（n=6，实验 11/27/1）。样本很小，不能据此断言“裁决总是偏第一位”，但足以说明“裁决”不是一个稳定的增益来源。

**模型对照只作定性。** `doubao-seed-2-1-pro` 在 tabulate 四条上 3/4（每条只跑 1 次），`deepseek` 同期的 5 次参考值是 366 5/5、386 4/5、410 3/5、362 1/5。两模型的可解集合互不包含：doubao 独有 `1285`，deepseek 独有 `1305`、`1342`（实验 11/26/4、11/28/1）。doubao 的整批数据不完整（3 条调用错误、5 条格式失败），只能用于“可解集合不包含”这一类定性判断，不能计算通过率，也不能与 deepseek 的 5 次结果比较“谁更稳”。

## 6.8 失败类型分解

把 100 次运行的失败原因合并，可以分成四类：

| 类型 | 例子 | 含义 |
|---|---|---|
| 测试未通过 | `362`、`1253`、`1322` | 真实能力边界，最常见 |
| 提案格式不合法 | `1251`、`1269`、`1294` | SEARCH 片段对不上，与上下文工程直接相关 |
| 改对功能但引入 lint 问题 | `1276`、`1285`、`1311` | 功能对、静态检查破，这类最不稳 |
| 超出改动预算 | `1285`（历史一次） | 属契约配置，已放宽，不应计入难度 |

`1285` 同时出现在“lint”和“diff”两行，是因为它历史上既触发过 lint，也触发过 diff 上限；统计失败类型时按主因归类，不重复计数。第三类失败最值得注意：它不是“模型不会改”，而是“改对了但写坏了静态检查”，因此会在测试红与 lint 红之间跳，跨天结果尤其不稳。

## 6.9 有效性威胁

- **任务分布**：20 条任务只来自 2 个仓库，模型可能熟悉这两个仓库；结论不能外推到跨仓库、多文件、重构类任务。
- **模型覆盖**：基线只用 `deepseek-chat`；`doubao` 数据不完整，`kimi` 主要作复核。53% 不能当作“模型通用通过率”。
- **重复次数**：5 次仍不足以稳定估计单条任务的通过率；`1285` 的 0/3→3/3→0/5 就是证据。
- **单条任务不稳定**：本章只按“本次测量”报告全败条数，不对任务做绝对难度断言；任何按 `tier` 分组的统计都要注明测量日期与次数。
- **协议对比样本小**：11/12 与 12/12 的差异只有 1 次，Fisher 双侧 p=1.0（单侧 p=0.5），不能支撑“协作有效/无效”的结论。
- **成本口径**：后端 A/B 的对比只来自一条任务，且没有墙钟时间；token 不能替代真实耗时。
- **CI 覆盖**：CI 跑离线测试（py3.10/3.11 双版本绿，数量以 pytest 输出为准），但不跑真实仓库端到端，也不跑 Windows；CRLF 这类问题不会被 CI 抓到。
- **无人工语义复核**：闸门判的是“契约下可交付”，不是“补丁在语义上正确”；本章的通过率不能解释为“修复正确率”。

## 6.10 小结

1. **总体通过率可复现**：两次独立测量为 31/60（51.7%）与 53/100（53.0%），差 1.3 个百分点；可以写“约 53%”，并注明样本与模型（实验 11/26/3、11/28/1）。
2. **单条任务档位不可复现**：`1285` 在三次测量中 0/3→3/3→0/5；只能写“本次测量中 6 条 0/5”，不能写“6 条属难档”。
3. **闸门判定用锚点表述**：官方修复必绿、未修复必红、`410` 的部分正确被拒；不作“误判率为零”的断言。
4. **工程手段有效但有限**：精确断言 6/9→9/9（单任务）、SEARCH/REPLACE 解决“写不完”、上下文收窄 −84%、后端 B −42% token（单任务）；每一条都有明确边界。
5. **协议对比不具统计效力**：单轮 11/12、双提案 12/12，差异 1 次，Fisher 双侧 p=1.0（单侧 p=0.5）；既不能证明也不能否证协作增益。复核与裁决的负结果说明，多角色协作的收益不是“加上座位就会有”，需要更难的任务与更稳的测量。

# 第 7 章 总结与展望

## 7.1 工作总结

本文围绕“生成便宜、判定昂贵”这一瓶颈，设计并实现了一个以可执行验收契约为唯一判定依据的多角色代码交付系统。系统把判定从人眼移到契约：契约在动手前由人确认，模型只负责产出，四类闸门负责判定，审计负责追溯。

主要工作包括：契约 DSL 与严格校验、四类闸门、精确断言的 AST 提取与漂移检查、三座位协议机、两套执行后端、SEARCH/REPLACE 编辑格式、上下文收窄、多供应商适配与 JSONL 审计。系统以 Python 实现，仓库现有离线测试（数量以 CI 的 pytest 输出为准），在 20 条真实仓库任务（2 个仓库）上运行；CI 在 Python 3.10 / 3.11 双版本通过（本文任务集，2026-11）。

## 7.2 主要结论

1. **契约作为唯一裁判是可行的，但边界由契约定义。** 20 条任务建立了双向锚点：官方修复必绿、未修复必红；`tabulate-410` 的 4 条用例过 3 条仍被判不可交付（实验 11/25/5）。闸门回答的是“在给定契约下是否可交付”，不是“修复在语义上是否正确”。本文没有做全量人工语义复核，因此不作“误判率为零”的断言（见 6.2 节）。

2. **精确断言有效但有限。** 在手写 fixture 上，它使一个模型由 0/3 变为 3/3，使另一个模型 token 消耗降低 58%（实验 11/24/1）；合计 6/9→9/9。但这项实验只有一条任务、三个模型、每格三次，不能外推为“精确断言普遍有效”。它改变的是“模型该写什么”，不改变“模型会不会改代码”。

3. **工程手段决定单轮交付的下限。** SEARCH/REPLACE 片段替换解决了整文件重写“写不完”的问题（实验 11/25/1）；上下文收窄把 token 从 55,288 降到 9,069（−84%，实验 11/25/17）；后端 B 在一次任务上比 A 省 42% token（实验 11/25/2）。三条结果都只来自单条任务，不能写成“已解决大文件修改”。

4. **总体通过率可复现，单条任务的档位不可复现。** 两次独立测量给出 31/60（51.7%）与 53/100（53.0%），差 1.3 个百分点，可以写“约 53%”（实验 11/26/3、11/28/1）；但 `1285` 在三次测量中是 0/3→3/3→0/5，`1311` 从 2/3 掉到 0/5。因此正文只写“本次测量中 6 条 0/5”，不写“6 条属难档”；难度是任务 × 模型 × 上下文的属性，不是任务的绝对属性。

5. **协议层对比不具统计效力。** 单轮 11/12、双提案 12/12（同/跨模型），差异只有 1 次；Fisher 精确检验双侧 p=1.0（单侧 p=0.5）（实验 11/27/3）。单轮基线已 92%，天花板效应使这个实验既不能证明、也不能否证协作增益。复核座位每轮提 5–8 条结论但无法参与阻断，裁决 6 次中 5 次选第一份（n=6，实验 11/27/1）；多角色协作的独立增益尚未被证实。

## 7.3 局限

- **任务分布**：20 条任务只来自 2 个仓库，模型可能熟悉这两个仓库；结论不能外推到跨仓库、多文件、重构类任务。
- **模型覆盖**：基线主要用 `deepseek-chat`；`doubao` 数据不完整，只作定性；`kimi` 主要作复核。
- **重复次数**：5 次仍不足以稳定估计单条任务的通过率；`1285` 的跨天翻转就是证据。
- **协议样本**：4 条任务 × 3 次，单轮已 92%，协议对比没有统计效力。
- **成本口径**：后端 A/B 的对比只来自一条任务，且没有墙钟时间；token 不能替代真实耗时。
- **系统边界**：当前是命令行系统与库，没有 HTTP 服务、工作台前端、安全沙箱与离线回放；执行环境只隔离工作目录与超时，不是沙箱。
- **人工复核**：闸门判的是“契约下可交付”，不是“补丁语义正确”；本文没有对每次运行的补丁做人工正确性复核。

## 7.4 后续工作

1. **把任务集扩到更多仓库，并找“单轮稳定失败”的任务。** 当前 20 条任务里，单轮通过率已接近上限；要检验“协作能否救回”，需要基线更低的难任务，或在固定采样预算下比较“多样性”与“次数”（实验 11/27/3 的建议）。
2. **把复核改成建议者。** 当前 `gate` 字段迫使复核结论对应四类闸门，模型持续把它当“问题类别”填写，结论无法参与阻断（第 6.7 节）。后续应把 `gate` 改为可选、新增 `category`，让复核只提可疑之处与证据，再用对照实验看建议是否改善下一轮提案。
3. **补离线回放。** 审计已经保存原始响应，但还没有按 `run_id` 离线重跑的工具；补上之后，实验可以脱离网络与账号状态复现。
4. **补系统外壳。** HTTP 服务与三视图工作台由前端实现线推进；本文只描述后端接口，不把未实现的部分写进已实现。
5. **补安全边界。** 容器化执行、断网、只读挂载、CPU/内存限额；当前 `LocalEnvironment` 只是受限执行环境，不是沙箱。
6. **补成本模型。** 后端 A 的成本近似由文件大小决定，后端 B 由调用次数与上下文体积共同决定；后续可按任务规模选择后端，而不是固定用一种。

## 7.5 结语

本文最重要的结论不是“系统能跑”，而是“判定可以被契约接管，而协作的收益必须被证明”。在 20 条真实任务上，契约与闸门站住了；多角色协作的独立增益没有站住。把这条负结果写出来，比把它藏起来更有价值：它告诉后续工作，应该先去找真正难的任务、把测量做稳，而不是继续调提示词。

# 地基选型：现有项目能不能直接坐底

> 数据为 2026-11-24 通过 GitHub API 实测。体积指仓库大小（含历史与资源文件），是"fork 成本"的粗略代理。

---

## 结论先行

**没有现成项目能当地基——但有三层可以借零件。**

原因是一句话：这些项目都在解决"**怎么让 agent 把活干出来**"，而本课题解决的是"**谁判定活干成了**"。两者正交。任何 agent 框架都把"决策权"内建在自己的循环里，你把契约闸门接进去，它就退化成外挂的评分器——而这恰好是本课题要反对的架构。

所以正确的做法不是 fork，是**分层借用**：

| 层 | 谁负责 | 从哪借 |
|---|---|---|
| 执行层 | 跑命令、隔离环境、迭代 | mini-swe-agent |
| 评测层 | 任务定义、轨迹记录、报告 | SWE-agent 的 trajectory 思路 |
| 编辑层 | 补丁怎么表达 | aider 的 SEARCH/REPLACE |
| **判定层** | **交付是否成立** | **无人可借，必须自研** ← 论文的立足点 |

## 五个候选

| 项目 | stars | 许可证 | 语言 | 体积 | 最近推送 | 形态 |
|---|---|---|---|---|---|---|
| OpenHands/OpenHands | 9.4 万 | MIT | TypeScript | **697 MB** | 2026-11-24 | 完整平台（前后端 + 沙箱） |
| SWE-agent/SWE-agent | 2.1 万 | MIT | Python | 70 MB | 2026-11-23 | 学术级 agent + 评测框架 |
| SWE-agent/mini-swe-agent | 1.0 万 | MIT | Python | 20 MB | 2026-11-23 | 极简 agent（约百行） |
| Aider-AI/aider | 5.0 万 | Apache-2.0 | Python | 137 MB | 2026-05-22 | 终端结对编程 |
| OpenAutoCoder/Agentless | 2.1 千 | MIT | Python | **0.6 MB** | 2024-12-22 | benchmark 流水线脚本 |

**许可证全部友好**（MIT / Apache-2.0），没有 AGPL 传染风险——这一条比预期干净。

## 逐个评述

### 1. mini-swe-agent —— 最适合当"执行层地基"

**特点**：把 agent 压缩到近百行，只做一件事——给模型一个 shell，让它在循环里跑命令、看结果、再决定。目录极简（`src/ tests/ docs/`）。

**优点**
- 体积 20 MB，一天就能读完；
- 不预设"怎么决策"，只提供"执行与观察"，**与契约闸门天然互补**（它管怎么试，我们管算不算过）；
- 仍在上游活跃维护；
- MIT，商用与改写都无限制。

**缺点**
- 太薄，没有任务管理、没有多轮协作、没有结构化产物；
- 没有审计与重放的概念——这些要自己补；
- 单 agent 单轨迹，不支持"提案 / 复核 / 裁决"的分工。

**能不能坐地基**：**能，作为"执行层"。** 这是五个里唯一推荐直接借鉴代码的。

---

### 2. SWE-agent —— 值得借"轨迹记录"，不值得 fork

**特点**：学术出身，把"agent–计算机接口"（ACI）抽象成一套可配置的工具集，配套完整的评测流水线与轨迹（`trajectories/`）落盘。

**优点**
- 轨迹记录的设计成熟：每一步的命令、观察、模型输入都留痕，与本课题的审计诉求高度一致；
- 评测框架可直接参考（任务定义、运行、汇总）；
- 活跃维护。

**缺点**
- 70 MB、配置体系庞杂，学习曲线陡；
- 深度绑定自家 ACI 与 benchmark 假设，改造成本高；
- 它的目标是"刷新分数"，不是"证明交付"。

**能不能坐地基**：**不能 fork，但值得抄"轨迹格式"与"评测流程"两处设计。**

---

### 3. Agentless —— 思想可抄，代码别碰

**特点**：0.6 MB 的脚本集合，"定位—修复—验证"三段式，无 agent 循环。

**优点**
- 极简，一下午能读完，**是理解"简单流程为何能赢"的最佳教材**；
- 论文（arXiv:2407.01489）本就是本课题的重要理论支撑。

**缺点**
- 2024-12 之后停更，是 benchmark 脚本而非系统；
- 没有可扩展点：没有适配层、没有测试、没有配置抽象；
- 依赖特定数据集格式。

**能不能坐地基**：**不能。** 它是一篇论文的附代码，不是工程底座。

---

### 4. OpenHands —— 太重，且架构立场冲突

**特点**：完整平台：agent 运行时、沙箱、Web UI、多后端模型接入。

**优点**
- 功能最全，产品化程度最高；
- 沙箱与运行时经过大规模验证，安全性设计成熟。

**缺点**
- **697 MB，TypeScript 主导**，Python 只是其中一部分，改造要先读懂整个前端架构；
- 它有自己的"agent 决定下一步"循环，**契约闸门只能外挂**，与本课题"判定权内建"的立场直接冲突；
- 上游迭代极快，本地改动会被淹没；
- 答辩时"哪部分是你做的"很难说清。

**能不能坐地基**：**不推荐。** 不是因为不好，是因为它太好了——好到你的贡献会被它的体量吃掉。

---

### 5. aider —— 借它的"编辑格式"

**特点**：终端结对编程，最成熟的是**代码编辑的表达方式**（SEARCH/REPLACE 块）与大仓库索引。

**优点**
- SEARCH/REPLACE 格式显著降低 token 消耗，比"整文件重写"高效得多；
- 我们目前的方案是整文件替换，这在真实仓库（几百行的文件）上会非常贵——它的方案正好补这个短板。

**缺点**
- 仓库 2026-05 后无更新；
- 137 MB，主体是产品逻辑，不适合整体借。

**能不能坐地基**：**不能，但"编辑格式"值得抄。** 这也是本课题第七章的明确改进项。

---

## 三个"不要 fork"的理由

**① 判定权会打架。** 这些框架的循环里，"下一步做什么"由模型决定；本课题里，"算不算过"由契约决定。fork 之后你必须不断对抗原有架构。

**② 工作量归属说不清。** 基于 9 万星项目改出来的东西，答辩时"你的贡献是什么"会被反复追问，而这个问题的答案恰恰是你论文的命门。

**③ 上游迭代会淹没你。** OpenHands 每天推送，你改的三个月后就是冲突。

---

## 具体怎么借

| 借什么 | 从哪 | 怎么用 |
|---|---|---|
| 执行循环骨架 | mini-swe-agent | 只借"调模型 → 执行 → 观察 → 再调"的循环，替换掉它的决策策略 |
| 轨迹记录格式 | SWE-agent `trajectories/` | 对齐字段名，使本系统产出的记录可被同类工具分析 |
| SEARCH/REPLACE 编辑格式 | aider | 替换当前的"整文件替换"，降低大文件任务的 token 成本 |

三处都是**思路与方法**层面，不是复制代码，工作量归属清晰。

## 附：如果把 OpenHands 接进来，它的职责是什么

先澄清一个容易混的地方：**"不基于它做地基" ≠ "不能把它接进来当组件"**。

- 不做地基 = 不 fork 它的架构、不让它决定系统形态；
- 接进来 = 把它当成一个**可替换的执行后端**，像插一个模型供应商那样。

这两件事不矛盾，而且后者恰好是"可插拔"主张的最强证据。

### 职责一句话

> **OpenHands 是"双手"，不是"大脑"，更不是"法官"。**

| 层 | 能不能交给它 | 说明 |
|---|---|---|
| 执行：改文件、跑命令、看报错、再改 | ✅ **强** | 它的主场 |
| 沙箱隔离（容器、网络、时限） | ✅ **强** | 可省掉排期里 W5 那 20 小时 |
| 模型接入 | ⚠️ 重叠 | 它走 litellm；我们的能力协商与降级台账更细，**不让** |
| 补丁表达 | ⚠️ 部分 | 它产出的是工作区终态，要自己转 diff |
| **判定** | ❌ **绝不让** | 它的"完成"是模型自我判断，不是客观裁判 |
| 契约表达 | ❌ | 无此概念 |
| 协作座位 | ⚠️ 部分 | 有多智能体委派，但不是固定三座位协议 |
| 审计台账 | ⚠️ 部分 | 有事件流，语义是"agent 做了什么"，不是"交付是否成立" |

### 接在哪一层

接在**提案座位背后**，作为一个执行后端：

```
座位（提案） → 后端选择器 ─┬─ direct：一次生成整份补丁（现状，便宜）
                          └─ runtime：交给 OpenHands 在工作区里迭代（贵，能啃难活）
                                        ↓
                                  统一归一化成 Patch
                                        ↓
                              复核 → 闸门（判定层完全不知道后端换了）
```

**硬约束：任何后端都必须归一化成 `Patch`。** 归一化点一旦破掉，派发、复核、闸门全要改，可插拔就成了空话。

接口形状：

```python
@dataclass(frozen=True)
class WorkerResult:
    patch: dict[str, str]      # 工作区终态转成的整文件内容
    stop_reason: str           # finished / budget / timeout / error
    claim_done: bool           # 它自称完成了 —— 仅作参考，不进判定
    transcript: list[dict]     # 嵌套轨迹，原样写入审计
    tokens: int
    calls: int

class WorkerRuntime(Protocol):
    name: str
    def run(self, *, workspace: Path, task: str, budget: Budget) -> WorkerResult: ...
```

`claim_done` 这个字段是关键的设计表态：**它可以自称完成，但没人会信**。闸门照跑。

### 代价

- **成本**：一个中等任务，OpenHands 要 30–80 次模型调用，token 是我们单次补丁的 10–50 倍；
- **延迟**：分钟级，不是秒级；
- **失败模式更复杂**：可能中途耗尽预算、可能卡在循环里、可能改出一堆无关文件（我们的 diff 预算能拦，但会浪费一轮）。

### 什么任务上值得用

**不是替代，是兜底。** 分级升级（escalation ladder）：

```
难易度          首选后端        失败后
易 / 中        direct          → 重试两轮 → 升级
难（0/3）      runtime         → 人工
```

这正好接上成长层的 L2 策略：**系统学会"什么任务不必开重型后端"**，就是"越用越省"的具体实现。

### 对论文的价值

接进来之后，"你的贡献是什么"这个问题的答案反而更清楚了：

> 判定层是我的，执行层是可以换的。换一个执行后端，判定结果不变——这就是解耦的证明。

比"我自己写了执行循环"更有说服力，因为后者永远比不过 9 万星的项目。

### 什么时候动

**1/31 硬节点之前不要碰。** 它需要容器环境、镜像拉取、几十次调用才能跑通一条任务，任何一处卡住都会挤占主线。

建议排在 2 月（春节低强度期）做一次"可行性验证"：能不能在 30 分钟内让它在 `tabulate` 那条任务上跑出一个补丁。能，就留作难档兜底；不能，就在论文第七章写成"已评估、未集成"。

## 附二：mini-swe-agent 的职责（真正建议接入的那个）

结论先给：**它和 OpenHands 坐同一个座位（执行后端），但成本低两个数量级，所以它是唯一需要真正接入的。**

### 实测结构（`src/minisweagent/`）

| 目录 | 内容 | 说明 |
|---|---|---|
| `environments/` | `docker.py` 6.4KB、`local.py` 3.6KB、`singularity.py` 5.5KB | **有沙箱**，不是裸跑 |
| `agents/` | `default.py` 8KB、`interactive.py` 10KB | 单智能体循环，两百来行 |
| `models/` | litellm 系列，6 个后端适配 | 可替换成我们自己的适配器 |

核心代码合计约 50KB，仓库 20MB（含文档与历史）。

### 职责边界

| 层 | 能不能交给它 | 说明 |
|---|---|---|
| 执行循环（调模型 → 跑命令 → 看结果 → 再调） | ✅ **就是它** | 我们的 `WorkerRuntime` 直接内嵌 |
| 沙箱隔离 | ✅ **有** | docker / local / singularity 三种环境 |
| 模型接入 | ⚠️ **可替换** | 默认走 litellm；我们注入自己的适配器，保住能力台账与降级登记 |
| 补丁表达 | ⚠️ 部分 | 它改的是工作区，终态由我们转成 `Patch` |
| **判定** | ❌ | 无此概念 |
| 契约表达 | ❌ | 无此概念，需把契约摘要写进它的 task 字符串 |
| 协作座位 | ❌ | 单轨迹，三座位在它外面 |

### 为什么选它而不是 OpenHands

| 维度 | mini-swe-agent | OpenHands |
|---|---|---|
| 仓库体积 | 20 MB | 697 MB |
| 核心代码 | ~50 KB | 整个平台 |
| 语言 | 纯 Python | TypeScript 主导 |
| 接入方式 | **当库用**（`pip install`，注入模型层） | 当外部服务编排 |
| 沙箱 | 有（docker/local/singularity） | 有（更强） |
| 读懂成本 | 一个下午 | 两周 |
| 出问题 | 能改 | 只能绕 |

一句话：**OpenHands 是"接管你的执行"，mini-swe-agent 是"把你缺的那一段补上"。**

### 三个后端的阶梯

```
① direct        自研，一次生成补丁          秒级   ~1–3k token   易 / 中
② mini-swe-agent 内嵌，多轮探索 + 沙箱      分钟级  ~20–60k token  难
③ OpenHands     外部服务，全功能            更慢    更贵           极端难 / 论文评估
```

**只接 ②。** ③ 写在论文第七章"已评估、未集成"即可——它需要容器编排、镜像拉取、几十次调用才能跑通一条任务，投入产出比在本科阶段不成立。

### 接入的四个技术要点

1. **模型层必须由我们注入**。它是 litellm 接口，要包一层把我们的 `ModelAdapter` 适配过去；否则能力协商、降级登记、token 台账全部绕过，实验数据不可比。
2. **契约摘要要写进 task 字符串**。它不认识 `exact` / `diff` 预算，不告诉它就会改出一堆无关文件——虽然 diff 闸门能拦，但浪费一轮。
3. **步数上限与预算打通**。它的 step limit 要映射到我们的 `Budget`，避免它跑满几十次调用才发现超支。
4. **轨迹字段对齐**。它的 trajectory 原样写进审计，但要补上 `run_id`、`contract_hash`、`seat`，否则无法与单次补丁的运行对比。

### 工时与时机

约 **4–6 小时**：读代码 2h、包模型层 2h、在 `tabulate` 任务上跑通 2h。

排在 **1/31 之后**（2 月春节低强度期），和 OpenHands 的可行性验证合并做一次即可。

## 答辩预案：为什么不用 OpenHands

> OpenHands 解决的是"让 agent 把活干出来"，我解决的是"谁说了算"。它的判定内建在自己的循环里，我如果接进去，契约就变成外挂的评分器——而我论文要论证的正是"判定权应该内建"。这是设计立场差异，不是能力差异。
>
> 我借了它的执行层思路（mini-swe-agent 的循环）、评测层思路（SWE-agent 的轨迹）、编辑层方案（aider 的 SEARCH/REPLACE），但判定层没有任何现成实现可借——这正是本课题的位置。

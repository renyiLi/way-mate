## 二、逐章材料地图

### 第 1 章 绪论

- **核心论点**：瓶颈已从"代码生成"移到"交付判定"。
- 可用材料：`docs/开题报告-初稿.md` §1、§2
- 可引数字：主流工具星标量级（codex 13.6 万、OpenHands 9.4 万、MetaGPT 7.1 万）；
  **闸门类细分项目规模都很小**（2026-11-28 实测：skillgate 10、proof-loop 12、qikly 25、contract-driven-development 2）
- ⚠️ 不要说"首创"。要说"截至 2026-11，公开项目中未见把验收契约作为唯一判定依据的完整实现"。

### 第 2 章 相关技术与现状

- **核心论点**：现有工作分成四层（通用 agent / 软件工程 agent / 多智能体编排 / 契约与闸门），
  前三层都在解决"怎么生成"，第四层才有"怎么判定"，而第四层最薄弱。
- 必须点名：MetaGPT、OpenHands、Agentless、SWE-agent、skillgate
- ⚠️ 审计/评审功能**不是卖点**（阿里 open-code-review 已 5.70 万星，2026-11-28 实测），要主动说"这不是本文贡献"。

### 第 3 章 需求分析

- **核心论点**：需求来自"人只验收、不写码"这一设定，因此系统必须能**自证交付成立**。
- 材料：`interface/API.md` §5–6、`tasks/*/task.json`
- 可写：任务配方的 5 个必要字段、契约的 5 类验收项、三类使用场景

### 第 4 章 系统设计

- **核心论点**：**契约是唯一裁判**；模型只提案，闸门只判定，二者职责不重叠。
- 材料：`interface/API.md` 全部、`src/dbw/protocol/interfaces.py`
- 必写内容：
  - 四类闸门与判定语义（tests/lint/api/diff）
  - 精确断言：从 `pytest.raises(match=...)` 用 AST 提取字面量，注入为硬约束
  - 座位模型：提案/复核/裁决三个座位，模型数量只改变排班不改变流程

### 第 5 章 系统实现

- **核心论点**：三个具体工程问题，每个都有可验证的解决方式。
- 材料：`src/dbw/`、`experiments/` 里的"方法论坑"

## 五、判定口径（写"闸门可靠"时必须用它）

**不能写"60 次运行无一误判"。** 我们没有对每次运行的补丁做人工复核，
所以"误判"没有可核对的真值，"无一误判"是不可辩护的表述。

可以写的是下面三条，每条都有验证方式：

| 表述 | 依据 | 验证方式 |
|---|---|---|
| **正向锚点**：20 条任务的官方修复都能通过闸门 | `prepare_task` 逐条跑过"加官方修复 → 全绿" | `task.json` 的 `verified.green_with_fix` |
| **负向锚点**：未打补丁时闸门必定判不通过 | `prepare_task` 逐条跑过"旧源码 → 红" | `task.json` 的 `verified.red_without_fix` |
| **部分正确会被拒绝**：`tabulate-410` 的 3/4 用例通过仍判不可交付 | 11/25/5 | 闸门按"全部用例通过"判定 |

因此推荐写法：

> 闸门的判定含义是**"在给定契约下可交付"**，不等于"修复在语义上正确"。
> 本文在 20 条任务上建立了双向锚点（官方修复必绿、未修复必红），
> 并观察到"部分正确"会被准确拒绝；但未对每次运行的补丁做人工正确性复核，
> 因此本文不作"误判率为零"的断言。

## 七、写作顺序建议（回答"一章一章写"）

**赞成按章写，但不建议按 1→7 的顺序写。**

理由：材料成熟度不同。第 4、5 章已经有实现和文档，几乎可以直接落笔；
第 1、2 章要等你写完正文才知道"自己到底做了什么"，否则容易写成空话。

推荐双轨：

| 阶段 | 内容 | 周期 |
|---|---|---|
| 第 0 步 | 只定**目录 + 每章 3–5 个论点**（一页纸） | 2 天 |
| 第 1 步 | 第 1 章出**骨架版**（约 1500 字，只求结构对，不求文采） | 2 天 |
| 第 2 步 | 第 4 章（设计）—— 材料最全，写起来最快 | 1 周 |
| 第 3 步 | 第 5 章（实现）—— 三个必写实现点 | 1 周 |
| 第 4 步 | 第 6 章（实验）—— 四张表，数字全部来自本文档 | 1 周 |
| 第 5 步 | 第 3 章（需求）—— 此时才写得准 | 3 天 |
| 第 6 步 | 第 2 章（现状）—— 回过头评价别人做了什么 | 3 天 |
| 第 7 步 | 第 1 章定稿 + 第 7 章 | 3 天 |

**为什么这样排**：先写能写的，正文会快速变厚，心理压力小；而且写第 4、5 章时会发现设计上的缺口，
还能回头改代码——这个反馈在新年之前还有时间消化。
